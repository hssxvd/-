## 1. 个性化推荐模块

### 1.1 合规边界（严格遵守约束 L759-L763）

#### ✅ 允许的个性化特征（来自约束 L759 原句）

| 特征 | 来源数据 | 实现方式 | 本方案采用 |
|---|---|---|---|
| 当前社区的爆款商品（销量排行） | `orders` + `order_item` JOIN 按 `community_id` 聚合 | 滑动窗口（近 14 天销量 DESC） | ✅ `RecommendService.hotByCommunity()` |
| 当前截单周期内即将到货商品 | `supply_plan` + `stock` JOIN 按 `expected_time` 过滤 | `expected_time BETWEEN NOW() AND NOW()+3DAYS` | ✅ `RecommendService.comingSoon()` |
| 当前用户的历史浏览分类 | 新增 `user_browse_history` 表 | 浏览商品时异步写入，按分类聚合权重 | ✅ 浏览事件采集 + 分类偏好快照 |
| 当前用户的加购/下单偏好分类 | `cart_item` + `orders` | 加购/下单时按分类累加权重 | ✅ 事件驱动（CartService/OrderService 写入） |

#### ❌ 禁止的特征（来自约束 L760 原句）

| 禁止项 | 原因 | 本方案如何避免 |
|---|---|---|
| 具体地址 | 敏感隐私 | 仅用 `community_id` 聚合，**从不**精确到 pick_up_point 以下 |
| 真实姓名 | 敏感隐私 | 用户行为聚合用 `user_id`（JWT subject），**绝不** JOIN `user.real_name` |
| 手机号 | 敏感隐私 | 同上 |
| 身份证号 | 敏感隐私 | 项目本就没存身份证号，天然合规 |
| 支付信息 | 敏感隐私 | 支付模块仅写订单聚合，推荐模块**从不** JOIN payment 表 |

#### 🔒 额外合规措施（来自约束 L761-L763）

- 个性化推荐**必须可关闭** → Home.vue 已有的 `personalized` 开关，后端 `/api/recommend/*` 接口必须接受 `personalized=false` 参数，直接降级为"综合排序"结果
- 个性化排序**不得影响分类筛选准确性** → 查询层保证 **WHERE 筛选条件先执行**，推荐仅作为 ORDER BY 的追加权重（`relevance_score DESC` 追加在已有排序字段后）
- 商家端和管理端**不得看到消费者的个性化结果** → 推荐接口仅在 ConsumerLayout 路由下暴露；商家仅能看 `GET /admin/products?sort=sales` 基础排序

### 1.2 算法原理：基于规则引擎 + 分类偏好快照

**为什么不用协同过滤 / 矩阵分解？**

| 算法 | 数据量需求 | 计算开销 | 毕设级可行性 | 合规性 |
|---|---|---|---|---|
| 协同过滤（CF） | 百万级用户行为 | 大（SVD/ALS） | ❌ 项目量级不够 | 用户×商品交互矩阵可能间接泄露隐私 |
| 矩阵分解 | 同上 | 大 | ❌ | 同上 |
| **规则引擎 + 分类偏好快照** | 百级用户 × 千级商品 | O(n) 排序 | ✅ 够用 | ✅ 完全基于约束 L759 白名单特征 |

**核心公式**（简化加权）：

```
relevance_score(product, user) =
    w1 * community_sales_rank(product.community_id, product.id)   // 社区爆款权重 0~100
  + w2 * coming_soon_bonus(product, user.community_id)             // 即将到货 +20（满足则加）
  + w3 * category_affinity_score(user.id, product.category_id)     // 用户分类偏好 0~100
  + w4 * buy_again_bonus(user.id, product.id)                      // 复购偏好 +15（买过同类）
```

**w 权重（可配置在 application.yml）**：

| 权重 | 值 | 含义 |
|---|---|---|
| w1 | 0.4 | 社区爆款（销量为王，团购场景核心） |
| w2 | 0.3 | 即将到货（团购"截单周期"的核心吸引力） |
| w3 | 0.2 | 用户分类偏好（个性化的主体） |
| w4 | 0.1 | 复购偏好（加购/下单过同类商品的加成） |

### 1.3 数据库设计（V19 migration）

#### 新增表 1：`user_browse_history`

**约束对照**：遵守"浏览分类偏好"特征采集，仅存 `user_id`、`product_id`、`category_id`、时间戳——**不存任何地址/电话/姓名**（约束 L760）。

```sql
-- V19__recommend_tables.sql
CREATE TABLE IF NOT EXISTS user_browse_history (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id       BIGINT       NOT NULL COMMENT '用户ID（JWT subject）',
    product_id    BIGINT       NOT NULL COMMENT '浏览的商品ID',
    category_id   BIGINT       NULL     COMMENT '商品所属分类（冗余，方便聚合偏好，约束 L759）',
    community_id  BIGINT       NULL     COMMENT '浏览时所在社区（方便分社区统计）',
    duration_ms   INT          DEFAULT 0 COMMENT '停留毫秒数（可选增强，约束未强制）',
    create_time   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_user_time    (user_id, create_time DESC),
    INDEX idx_product      (product_id),
    INDEX idx_category     (category_id),
    INDEX idx_user_category (user_id, category_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户浏览历史（个性化推荐数据源）';
```

#### 新增表 2：`user_category_preference`（快照表，加速推荐计算）

**设计原理**：浏览历史每次实时聚合太重，定时快照成权重表。每次用户浏览/加购/下单时**异步**更新快照（Redis 存实时增量，5 分钟刷一次）。

```sql
CREATE TABLE IF NOT EXISTS user_category_preference (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id       BIGINT       NOT NULL,
    category_id   BIGINT       NOT NULL,
    browse_weight DECIMAL(8,2) DEFAULT 0 COMMENT '浏览累积权重（每次浏览 +1，衰减 0.95/天）',
    cart_weight   DECIMAL(8,2) DEFAULT 0 COMMENT '加购累积权重（每次 +3）',
    buy_weight    DECIMAL(8,2) DEFAULT 0 COMMENT '下单累积权重（每次 +5）',
    total_weight  DECIMAL(8,2) DEFAULT 0 COMMENT '浏览+加购+下单加权总分',
    last_visit_at DATETIME     NULL,
    create_time   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_user_category (user_id, category_id),
    INDEX idx_user_weight_desc (user_id, total_weight DESC)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户分类偏好快照（推荐加速表）';
```

#### 为什么冗余 `category_id` 在 browse_history？

- 约束 L759 明确要求"历史浏览分类"作为推荐特征
- 如果不冗余，每次算分类偏好都要 JOIN product → 性能浪费 + 复杂度增加
- 冗余原则遵守约束 L274 的"订单快照"思想：**冗余是为了性能和业务正确性**

### 1.5 触发点分布（推荐数据采集的事件驱动）

| 事件 | 触发位置 | 写入目标 | 异步/同步 |
|---|---|---|---|
| 用户浏览商品详情页 | ConsumerProductDetail.vue → 调用 POST /api/recommend/browse | `user_browse_history` + Redis 分类权重增量 | **异步**（不阻塞详情页加载，丢失可接受） |
| 用户加购 | CartService.addItem() 末尾 | Redis 分类权重 +3 | 异步（@Async 注解） |
| 用户下单 | OrderService.create() 末尾 | Redis 分类权重 +5 | 异步 |
| 定时快照刷盘 | 5 分钟一次（`@Scheduled(fixedDelay=300000)`） | Redis 增量 → `user_category_preference` 表 | 定时任务 |
| 定时衰减 | 每天 00:30（`@Scheduled(cron="30 0 * * * ?")`） | `user_category_preference.total_weight *= 0.95` | 定时任务 |

### 1.6 与现有模块的协同（不违反约束 L762 排序优先级）

```
原始请求：GET /api/products?categoryId=3&priceMin=10&priceMax=50&sort=综合&communityId=1&personalized=true
                                              ↓
Step 1: WHERE category_id=3 AND price BETWEEN 10 AND 50 AND community_id=1    ← 筛选条件先执行（约束 L762）
Step 2: 个性化开启？查询 RecommendService.relevance_score 计算 relevance_score 列
Step 3: ORDER BY sales DESC, relevance_score DESC LIMIT 20                    ← 个性化权重作为次排序（不主导）
Step 4: 关闭个性化？ORDER BY sales DESC, create_time DESC LIMIT 20            ← 降级为综合排序
```

## 2. 社区团购模块（"团"的核心体现）

### 2.1 为什么需要团购模块？

**现状 vs 真正"社区团购"的差距**：

| 维度 | 现状（只有社区自提） | 社区团购（要实现的） |
|---|---|---|
| 下单模式 | 用户个体下单 → 单独履约 | 用户参团 → 凑够成团量 → 统一拿货 |
| 库存管理 | 即时扣减 | 成团前**预锁共享库存**（多个用户拼同一份大库存） |
| 供应链协同 | SupplyPlan → Stock → Orders | 成团量 → 驱动 SupplyPlan 生成（团购反向拉动供应链） |
| 核心吸引力 | "在社区自提更便宜" | "一起买更便宜 + 截单周期凑量 + 商家凑单" |
| 约束对照 | — | 项目名含"团购"二字，必须体现团特征 |

### 2.2 核心概念定义

#### 截单周期（Cutoff Cycle）

**原理**：社区团购不是用户随时买随时发，而是按周期凑单。例如"周三 24:00 截单 → 周五到货自提"。

```
cycle_start  cycle_end  expected_arrive
  │            │            │
  ▼            ▼            ▼
  ●────────────●────────────●
     拼团期       供应链备货      自提日
```

#### 拼团团（Group Buy Team）

**原理**：一个 SKU + 一个社区 + 一个截单周期 = 一个"团"。用户可以"一键开团"（当团长）或"参团"。凑够最小成团量（`min_group_qty`）→ 团自动成团 → 触发统一下单到供应商 → 到货后用户到自提点取。

#### 为什么用"SKU × Community × Cycle"做团的唯一键？

| 方案 | 问题 |
|---|---|
| 按 product_id 建团 | 同一个商品多个 SKU（如 500ml 和 1L）必须各自拼，否则库存对不上 |
| 按 community_id 建团 | 不同社区不共享库存（约束 6 的库存隔离），必须分社区拼 |
| **SKU × Community × Cycle** | ✅ 自然形成唯一团实例 |

#### 为什么冗余 `group_price` 在 member 里？

- 遵守约束 L274 订单快照思想：**下单后价格变化不影响已拍下的成员**
- 团购场景：商家可能在同一周期内微调团购价（如前 10 人 9 折，后 40 人 95 折），参团时必须锁定当时的价格

### 2.4 团购状态机（严格遵守约束 L68 状态一致性校验）

#### 活动状态 + 订单状态 + 库存状态 三者协同矩阵

```
group_buy_activity.status → 驱动 → 订单状态 → 驱动 → 库存状态
─────────────────────────────────────────────────────────────
OPEN（拼团中）
  ├── 参团人数 < min_group_qty
  │     → 不生成订单
  │     → 不扣库存
  │
  └── 参团人数 >= min_group_qty  （自动或手动成团）
        ↓
FULFILLED（已成团）
  ├── 为每个 member 生成订单（PENDING_PAY）
  ├── 预锁库存 SUM(member.quantity) × activity.sku_id
  └── 生成 SupplyPlan（团购驱动供应链）
        ↓
SHIPPED（已备货/到自提点）
  ├── 商家确认配送 → Fulfillment 创建
  └── 订单进入 PENDING_PICKUP
        ↓
COMPLETED（全部自提完成）
  ├── 所有 member 订单 COMPLETED
  └── 库存 LOCK → DEDUCT（约束 §6 生命周期）

异常分支：
  OPEN → 到 cycle_end 仍不足 min_group_qty
    → CANCELLED（团失败）
    → 所有 member 已生成订单的 → 自动 CANCELLED + 库存 UNLOCK
```

### 2.5 与现有模块的集成点（不破坏已有流程）

| 现有模块 | 集成点 | 约束条目 |
|---|---|---|
| **OrderService.create()** | 团购订单额外标记 `order.source='GROUP_BUY'`，走 `orders.orderNo` 雪花 ID 范式 | 约束 L247 单号生成统一 |
| **StockService** | 团购预锁走 `lock()`，但锁的是 **shared pool**（多个成员共享同一预锁），需要 `lock_batch()` 支持一个团整体锁 | 约束 L282-283 库存不变量 |
| **SupplyPlanService** | 成团后触发 `supplyService.createFromGroupBuy(groupId)`，反向拉动供应链（团购的核心价值） | 约束 L264 SupplyPlan 关联 Forecast |
| **FulfillmentService** | 团购 activity 级创建 Fulfillment，一次履约整团 | 约束 L374 履约状态机 |
| **PaymentService** | 参团用户**个人支付**，团活动只负责"成团/开团"决策 | 支付仍是个人行为 |

### 2.6 后端接口契约

| Method | Path | 鉴权 | 核心参数 | 约束条目 |
|---|---|---|---|---|
| GET | `/api/group-buys` | 可选 | `communityId`, `status=OPEN` | L757 按社区筛选 |
| POST | `/api/group-buys/{id}/join` | 必须 | `quantity=1-5` | 限购（可在 activity 表加字段） |
| POST | `/api/group-buys/{id}/lead` | 必须 | `quantity` | 开团（等同于 join + isLeader=1） |
| GET | `/api/group-buys/{id}/progress` | 可选 | — | 实时进度（聚合 member 表） |
| POST | `/api/admin/group-buys/{id}/fulfill` | admin | — | 手动触发成团（cycle_end 前） |
| GET | `/api/admin/group-buys?status=OPEN` | admin | — | 商家查看自己的团 |
| POST | `/api/admin/group-buys` | merchant | `{ skuId, minQty, price, cycleStart, cycleEnd, expectedArrive }` | 商家建团 |

### 2.7 定时任务（遵守约束 L68 状态一致性自动校验）

| 任务 | cron | 逻辑 |
|---|---|---|
| 截单成团处理 | `0 */10 * * * ?`（每 10 分钟） | OPEN + cycle_end 已到 + joined_qty >= min_group_qty → FULFILLED |
| 截单失败处理 | 同上 | OPEN + cycle_end 已到 + joined_qty < min_group_qty → CANCELLED + 库存 UNLOCK + member 已下单的 → 自动 CANCELLED |
| 自动履约推进 | `0 */30 * * * ?` | FULFILLED + expected_arrive < NOW() → SHIPPED |

## 3. 种子数据扩容（让推荐和团购真正有数据）

### 3.1 扩容目标

| 维度 | 现状 | 目标 | 原因 |
|---|---|---|---|
| community（社区） | 2 | 4 | 推荐按社区聚合，至少 3 个不同社区 |
| merchant（商家） | 2 | 5 | 团购按商家隔离，多商家有多品类可选 |
| category（分类） | ~8 | 12 | 分类偏好需要足够宽的分类树 |
| product（商品） | ~20 | 60 | 社区爆款需要 60 个基准商品才能出销量差 |
| product_attribute（特色属性） | 稀疏 | 每商品 3+ | 约束 L287-L298 特色属性必须有筛选器数据 |
| user_browse_history | 0 | 1000+ | 推荐分类偏好必须有浏览事件 |
| group_buy_activity | 0 | 10 | 团购功能要有真实活动展示 |

### 3.2 种子数据生成脚本设计

**原则**：遵守约束 L29、L73 —— 用模拟/脱敏数据，不存真实隐私。

| 表 | 生成策略 |
|---|---|
| community | 固定 4 个：崇明岛社区、松江社区、浦东社区、浦东张江社区（有明确地域区分） |
| merchant | 5 个：生鲜店、水果店、粮油店、百货店、烘焙店（覆盖团购高频品类） |
| category | 12 个：根分类 ×3 + 子分类 × 9（每个根分类 3 个子） |
| product | 60 个：每商家 × 12 商品，每商品 2-3 个 SKU，每商品 3-5 个 product_attribute（特色属性） |
| stock | 每 SKU × community × pickup_point 各一条，可用 batchGetBySkusAndCommunity 验证 |
| user_browse_history | 用 Python/powershell 脚本生成 100 个用户 × 1000 条浏览记录（固定 user_id 范围 1-100，product_id 随机 1-60） |
| group_buy_activity | 10 条固定模板（覆盖不同 SKU、不同社区、不同 min_group_qty） |
