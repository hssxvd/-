# 社区团购电商系统 开发约束文档

> 版本：v1.0  
> 适用范围：本毕设全部后端、前端、数据库、测试、文档工作  
> 约束级别：**【必须】** 为强制项，违反需在周会说明；**【建议】** 为推荐项，允许有理由的偏离  
> 目标：保证系统在业务闭环、状态一致性、并发安全、预测可信、权限合规、可测试性上达到可答辩标准

## 课题描述

### 项目定位

面向消费者、商家，围绕社区团购电商的核心对象和业务流程开展服务。

### 用户角色与术语映射

| 课题原文 | 本项目统一术语 | user_type | 主要职责 |
|---|---|---|---|
| 居民 / 服务对象 | 消费者 | CONSUMER | 浏览、加购、下单、支付、自提、评价 |
| 服务提供人员 | 商家 | MERCHANT | 商品建档、库存管理、订单履约、售后处理 |
| 自提点工作人员 | 自提点核销员 🆕 | PICKUP_STAFF | 绑定到某个自提点，只能看自己自提点的 PENDING_PICKUP 订单并核销自提（履约→COMPLETED） |
| 社区 / 平台管理人员 | 社区管理员 | ADMIN | 用户/角色/权限管理、商品审核、全局统计、预测管理、操作日志 |
| — | 超级管理员 | ADMIN（同 ADMIN，superadmin 账号） | 跨社区管理、全部权限 |

> **v1.7 自提点核销员补充说明**：
> 课题原文未单独列核销员角色，项目初版将自提点联系人仅作为 `pickup_point.contact_name/phone` 展示字段（无系统账号）。
> 答辩前扩展为独立 RBAC 角色 `ROLE_PICKUP_STAFF`，绑定到 `pickup_point.staff_user_id`。
> **权限最少集**：product:view、pickup:view、order:view、fulfillment:view、fulfillment:verify。
> **数据隔离**：`FulfillmentService.listMine()` 内按 `userType = PICKUP_STAFF` 自动过滤 `orders.pickup_point_id = pickupPointMapper.selectOne(staff_user_id=当前用户)`。
> **商家 vs 核销员的本质区别**：
> - 商家（MERCHANT）= 供货商，管商品/库存/供应计划/全履约流程（标记已到自提点 + 核销）
> - 核销员（PICKUP_STAFF）= 自提点现场人员，只负责消费者取货时核销自提码，**看不到商品/库存/订单管理**
> 两者账号隔离、端隔离（`/merchant` vs `/pickup`）、数据隔离（merchant_id vs pickup_point_id）。

### 核心业务对象

商品、特色属性、库存、购物车、订单、模拟支付、履约记录。

### 核心功能模块

1. 供应与库存协同
2. 分类检索与个性化展示
3. 购物车和订单管理
4. 模拟支付与履约跟踪
5. 售后评价与经营分析

### 业务闭环

```text
商品建档 → 浏览选购 → 购物车 → 订单确认 → 模拟支付 → 履约交付 → 售后评价
```

### 核心智能化功能：社区团购电商需求预测

- 使用符合业务周期的历史模拟数据完成清洗和时间特征构造；
- 采用移动平均、线性回归或树模型中的一种预测短期需求；
- 给出预测区间或误差指标；
- 以 MAE 等指标与简单基线比较；
- 预测结果仅用于计划辅助。

### 工程实现要求

- 身份认证、角色权限、数据校验组合；
- 分页查询、必要统计可视化；
- 操作日志、异常处理；
- 数据库应反映核心对象的真实关系；
- 重点校验状态一致性：商品上下架、库存扣减、订单取消、模拟支付、履约、售后；
- 完成核心模块主要接口和典型异常流程测试。

### 数据合规

- 演示采用模拟或脱敏数据；
- 按最小必要原则授权；
- 不收集与业务无关的个人信息。

## 0. 开发前建议

1. **先定状态机，再写代码。** 订单、支付、履约、售后四套状态必须画成状态流转图，每个状态允许哪些操作、禁止哪些操作，落到代码里的枚举和校验方法。
2. **库存策略必须唯一。** 建议采用“下单预占 + 超时释放 + 支付确认扣减”或“下单直接扣减 + 取消回滚”中的一种，全系统统一。
3. **权限做两层。** 角色权限 + 数据范围权限，两层都要在 Service 层校验，不能只靠前端隐藏按钮。
4. **订单明细必须做商品快照。** 价格、名称、规格、图片都要冗余进订单明细。
5. **幂等从第一天做。** 模拟支付回调、取消订单、履约确认、售后退款，全部要支持幂等。
6. **预测模块与交易主流程解耦。** 预测失败不能影响下单支付。
7. **预测评估必须与基线比较。** 至少和“昨天销量”“上周同日销量”“近 7 天移动平均”比较。
8. **异常流程单独设计用例。** 正常流程只占测试的 30%，异常和并发才是拉开差距的地方。
9. **日志和脱敏从第一天做。** 后期补日志和脱敏成本极高。
10. **约束文档要可执行。** 每条约束最好能对应到检查点、单元测试或 Code Review 清单。

## 1. 技术栈与版本约束

### 1.1 后端

- 【必须】JDK 17 及以上，Spring Boot 3.x。
- 【必须】持久层统一使用 MyBatis-Plus（v1.1 定型，禁止混用 JPA）。
- 【必须】数据库使用 MySQL 8.x，字符集 `utf8mb4`，排序规则 `utf8mb4_general_ci`。
- 【必须】缓存使用 Redis 7.x，仅用于会话、库存预占、验证码、热点商品，不得当作唯一数据源。
- 【必须】接口文档使用 Knife4j / SpringDoc OpenAPI，所有对外接口必须可在文档中调试。
- 【建议】定时任务使用 Spring Task 或 XXL-Job，预测任务与库存释放任务分开调度。

### 1.2 前端

- 【必须】统一使用 Vue 3 + Vite + Element Plus（v1.1 定型，禁止换 React/Angular）。
- 【必须】状态管理使用 Pinia。
- 【必须】请求统一封装 axios，统一处理 token、错误码、loading、异常提示。
- 【必须】图表使用 ECharts，统计图表与后端统计口径必须一致。

### 1.3 版本与依赖

- 【必须】所有依赖版本在 `pom.xml` / `package.json` 中锁定，禁止使用 `LATEST`。
- 【必须】禁止引入来源不明的第三方包。
- 【建议】使用 Maven Wrapper 或 pnpm，保证环境一致。

## 2. 项目结构与分层约束

### 2.1 后端分层

```text
controller  -> 只做参数接收、校验、调用 service、返回统一结果
service     -> 业务编排、事务边界、状态机校验、权限数据范围校验
manager     -> 跨模块组合、缓存、外部调用（可选）
mapper/dao  -> 只做数据访问，禁止写业务判断
entity      -> 与数据库表一一对应
dto/vo      -> 对外传输对象，禁止直接暴露 entity
enums       -> 所有状态、类型、错误码必须用枚举
```

- 【必须】Controller 不得直接调用 Mapper。
- 【必须】Entity 不得直接作为接口返回值。
- 【必须】事务注解 `@Transactional` 只加在 Service 层，`rollbackFor` 必须显式指定 `Exception.class`。
- 【必须】跨模块调用通过 Service 接口，禁止直接访问对方 Mapper。

### 2.2 包命名

- 【必须】`com.xxx.community.<模块>.<层>`，模块如 `product`、`cart`、`order`、`pay`、`fulfillment`、`aftersale`、`forecast`、`auth`、`admin`。
- 【必须】模块内禁止循环依赖，如出现需引入中间模块或事件解耦。

## 3. 命名与编码规范

- 【必须】类名 UpperCamelCase，方法名/变量名 lowerCamelCase，常量全大写下划线。
- 【必须】数据库表名、字段名使用 snake_case，表名不加前缀 `t_`，关联表用 `_rel` 结尾。
- 【必须】布尔字段用 `is_xxx`，状态字段用 `xxx_status`，时间字段用 `xxx_time`。
- 【必须】枚举值禁止用魔法数字，必须定义枚举类并入库为字符串或明确的数字编码。
- 【必须】单个方法不超过 80 行，单个类不超过 800 行，超过需拆分。
- 【必须】禁止在循环中查数据库，批量场景使用批量查询。
- 【必须】所有金额使用 `BigDecimal`，禁止用 `double`/`float`。
- 【必须】所有时间使用 `LocalDateTime`，禁止用 `Date`。
- 【建议】统一使用 Lombok，但禁止滥用 `@Data` 在 Entity 上。

## 4. 数据库设计约束

### 4.1 通用约束

- 【必须】每张表必须有主键 `id`（bigint 自增或雪花 ID）、`create_time`、`update_time`。
- 【必须】逻辑删除字段 `is_deleted`（0/1），查询默认过滤已删除数据。
- 【必须】所有外键关系必须在数据库层面或应用层面明确，推荐应用层维护 + 必要索引。
- 【必须】关键唯一约束必须建唯一索引，如订单号、支付流水号、购物车（用户+SKU）。
- 【必须】金额字段 `decimal(12,2)`，数量字段 `int`，状态字段 `varchar(32)` 或 `tinyint` 统一。
- 【必须】禁止在数据库中存储明文密码、明文手机号、明文身份证号。

#### 4.1.1 DDL 与 Entity 字段一致性校验（v1.2 新增，实战踩坑）

> **实战背景**：V1 DDL 创建了 30 张表，但漏了 stock、payment、fulfillment、aftersale、forecast_task、forecast_result、forecast_metric、operation_log、cart_item 共 9 张表的 is_deleted 列，而 Entity 都继承了 BaseEntity（自带 @TableLogic + is_deleted），导致应用启动后第一个查询就报 `Unknown column 'is_deleted' in 'field list'`。

**校验脚本**（DDL 提交前必须执行，返回空行才合规）：

```sql
-- MySQL 8.0+
SELECT TABLE_NAME
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'community_group_buy'
  AND TABLE_NAME NOT IN (
    SELECT TABLE_NAME
    FROM information_schema.COLUMNS
    WHERE COLUMN_NAME = 'is_deleted'
  );
```

**校验标准**：返回 0 行 = 所有表都有 is_deleted，合规。

**修复方式**：

```sql
-- 漏了 is_deleted 的表，逐张补上
ALTER TABLE stock ADD COLUMN is_deleted TINYINT NOT NULL DEFAULT 0;
ALTER TABLE payment ADD COLUMN is_deleted TINYINT NOT NULL DEFAULT 0;
ALTER TABLE fulfillment ADD COLUMN is_deleted TINYINT NOT NULL DEFAULT 0;
ALTER TABLE aftersale ADD COLUMN is_deleted TINYINT NOT NULL DEFAULT 0;
ALTER TABLE forecast_task ADD COLUMN is_deleted TINYINT NOT NULL DEFAULT 0;
ALTER TABLE forecast_result ADD COLUMN is_deleted TINYINT NOT NULL DEFAULT 0;
ALTER TABLE forecast_metric ADD COLUMN is_deleted TINYINT NOT NULL DEFAULT 0;
ALTER TABLE operation_log ADD COLUMN is_deleted TINYINT NOT NULL DEFAULT 0;
ALTER TABLE cart_item ADD COLUMN is_deleted TINYINT NOT NULL DEFAULT 0;
```

#### 4.1.2 复合唯一索引必须覆盖完整业务维度（v1.2 新增，实战踩坑）

> **实战背景**：forecast_result 原唯一索引 `uk_sku_community_date(sku_id, community_id, forecast_date)` 漏了 task_id，导致 MA/LR/RF 三个模型对同一 SKU 同一天的预测互相冲突（Duplicate entry）。同一 SKU 可以被不同 task_id（不同模型/不同批次）预测，唯一索引必须包含 task_id。

**唯一索引设计三问**：

1. 这张表的一条记录到底由什么**业务唯一标识**？
2. 有没有"同 XX 不同 YY"的合法场景？（如：同 SKU 不同模型的预测、同用户不同时间的购物车）
3. 索引字段顺序是否匹配高频查询条件？

**本项目核心唯一索引对照**：

| 表 | 唯一索引 | 业务维度（必须覆盖） |
|---|---|---|
| forecast_result | `uk_task_sku_community_date(task_id, sku_id, community_id, forecast_date)` | 任务×SKU×社区×日期 |
| supply_plan | `uk_plan_no(plan_no)` | 计划号全局唯一 |
| order | `uk_order_no(order_no)` | 订单号全局唯一 |
| payment | `uk_payment_no(payment_no)` | 支付流水号全局唯一 |
| stock | `uk_sku_community_pickup(sku_id, community_id, COALESCE(pickup_point_id, 0))` | SKU×社区×自提点（NULL 自提点用 0 占位） |
| cart_item | `uk_user_sku(user_id, sku_id)` | 用户×SKU（同一购物车同一 SKU 不应重复） |
| review | `uk_order_item(order_item_id)` | 同一订单明细只能评一次 |

### 4.2 核心表清单（最小集）

- 用户与权限：`user`、`role`、`permission`、`user_role`、`role_permission`、`operation_log`
- 商品：`product`、`product_sku`、`product_attribute`、`category`、`community`、`pickup_point`
- 供应：`supply_plan`（供应计划，关联需求预测）
- 库存：`stock`、`stock_record`（库存流水，变更类型含 LOCK/UNLOCK/DEDUCT/ROLLBACK/INBOUND/SUPPLY_IN）
- 购物车：`cart_item`
- 订单：`order`、`order_item`（含商品快照 + 特色属性快照）、`order_status_log`
- 支付：`payment`、`payment_callback_log`
- 履约：`fulfillment`、`fulfillment_record`
- 售后：`aftersale`、`aftersale_record`
- 评价：`review`
- 预测：`forecast_task`、`forecast_result`、`forecast_metric`

### 4.3 订单快照约束

- 【必须】`order_item` 必须冗余：商品 ID、SKU ID、商品名称、规格、单价、数量、小计、图片、分类。
- 【必须】`order_item` 必须包含特色属性快照字段（JSON 存储），下单时从 `product_attribute` 拷贝。
- 【必须】下单后商品改价、改名、下架、改属性，订单明细不得变化。

### 4.4 库存表约束

- 【必须】`stock` 表至少包含：`sku_id`、`community_id`（或 `pickup_point_id`）、`total_qty`、`locked_qty`、`available_qty`、`version`。
- 【必须】`available_qty = total_qty - locked_qty`，且 `available_qty >= 0`。
- 【必须】库存变更必须写 `stock_record`，记录变更类型、数量、前后值、关联订单号。
- 【必须】库存唯一索引必须同时覆盖 `community_id` 和 `pickup_point_id`（若业务允许社区级库存为空自提点级库存），建议 `uk_sku_community_pickup(sku_id, community_id, COALESCE(pickup_point_id, 0))`。

### 4.5 特色属性约束（课题核心对象）

> 课题原文明确将「特色属性」列为核心业务对象，本节补充约束。

- 【必须】`product_attribute` 表至少包含：`id`、`product_id`、`attr_key`（属性键，预定义字典，禁止随意新增）、`attr_value`（属性值）、`attr_unit`（单位，可为空）、`icon_url`（可选，标签图标）、`is_filterable`（是否可用于分类检索/筛选，0/1）、`is_highlight`（是否在商品卡片/详情页高亮展示，0/1）、`sort_order`、`create_time`、`update_time`、`is_deleted`。
- 【必须】`attr_key` 预定义字典：产地、品牌、保质期、规格、重量、适用人群、特色标签（枚举表或常量类维护）。
- 【必须】分类检索必须按 `is_filterable = 1` 的属性生成筛选器，如按产地、品牌筛选。
- 【必须】商品详情页必须高亮展示 `is_highlight = 1` 的特色属性，如「产地：崇明岛」「当日直达」「无农药」。
- 【必须】特色属性不得重复造 SKU：同一商品规格差异通过 SKU 表，特色标签差异通过属性表。
- 【必须】特色属性必须纳入订单快照：下单时特色属性冗余进 `order_item`（JSON 格式），商品改属性后订单明细不得变化。
- 【必须】`product` 表禁止冗余 `origin`、`shelf_life`、`storage_condition`、`tags` 等特色属性字段，统一走 `product_attribute` 表存储。
- 【必须】`product_sku_attribute` 与 `product_attribute` 边界明确：前者存 **SKU 固有属性**（如颜色=红/蓝、尺寸=120ml/200ml，这些是定义 SKU 差异的维度），后者存 **商品公共特色属性**（如产地、品牌、保质期，同 SKU 所有变体共享）。禁止混淆。

## 5. 核心状态机约束

### 5.1 商品状态

```text
DRAFT(草稿) -> ON_SHELF(上架) -> OFF_SHELF(下架) -> ON_SHELF
ON_SHELF -> SOLD_OUT(售罄)
SOLD_OUT -> ON_SHELF
```

- 【必须】只有 `ON_SHELF` 商品可被浏览、加购、下单。
- 【必须】下架时必须校验是否有未完成订单，如有需提示或禁止下架。

### 5.2 订单状态

```text
PENDING_CONFIRM(待确认) -> PENDING_PAY(待支付) -> PAID(待处理)
PENDING_PAY -> CANCELLED(已取消)
PAID -> PROCESSING(处理中)
  │              ├── 自提支线：PROCESSING -> PENDING_PICKUP(待自提) -> COMPLETED(已完成)
  │              └── 配送支线：PROCESSING -> COMPLETED(已完成)

全额退款支线（v1.14）：
PAID | PROCESSING | PENDING_PICKUP -> REFUNDING(退款中) -> REFUNDED(已退款)
COMPLETED -> 保持 COMPLETED，售后进度由 orders.aftersale_status 表达
```

- 【必须】状态流转必须通过统一状态机方法，禁止直接 update 状态字段。
- 【必须】每次状态变更写 `order_status_log`，记录前状态、后状态、操作人、原因、时间。
- 【必须】非法流转直接抛业务异常，不允许静默失败。
- 【必须 v1.6】**自提订单**必须走 `FULFILLING → PENDING_PICKUP → COMPLETED` 支线，商家标记已到自提点时推 `PENDING_PICKUP`，核销自提时推 `COMPLETED`；**配送订单**不走 `PENDING_PICKUP`。
- 【必须 v1.6】`PENDING_PICKUP` 状态下消费者端必须展示自提核销码（`orders.pickup_code`），格式 `ZT` + 订单号后 6 位 + 2 位随机数；支付成功时由后端 `PaymentService` 自动生成，自提订单且 `pickup_point_id IS NOT NULL` 时立即写入。
- 【必须 v1.6】**履约状态与订单状态必须双写一致**（约束 5.4 同一条双保险）：
  - `fulfillment.toStatus = PENDING_PICKUP` → `orders.order_status = PENDING_PICKUP`
  - `fulfillment.toStatus = PICKED_UP` / `COMPLETED` → `orders.order_status = COMPLETED` + `orders.finish_time = NOW()`
  - 禁止只改 fulfillment 不改 orders，禁止两个表状态不一致（v1.6 前代码曾犯此错）
- 【必须 v1.6】前端 Orders.vue / OrderDetail.vue 必须识别 `PENDING_PICKUP` 状态：
  - 状态标签显示"待自提"（红色/橙色高亮，不是普通 info 色）
  - 订单卡片中间显示自提码 banner（可点击放大）
  - 详情页突出展示自提码大卡片 + 时间线"货到自提点"节点标记完成+进行中
  - 操作按钮显示"出示自提码"，点击放大后方便给自提点工作人员扫/念
  - Tab 区新增"待自提"筛选入口
- 【必须 v1.14】`REFUNDING`(退款中) / `REFUNDED`(已退款) 为**订单主状态终态**，准入与流转规则：
  - 仅当订单原状态为 `PAID` / `PROCESSING` / `PENDING_PICKUP` 且**全额退款**时，主状态才流转 `REFUNDING → REFUNDED`
  - 订单原状态为 `COMPLETED` 的售后：**主状态保持 `COMPLETED` 不变**，售后进度一律由 `orders.aftersale_status` 表达
  - **部分退款不改变订单主状态**，只累加 `orders.refunded_amount`
  - 进入 `REFUNDING` / `REFUNDED` 后禁止再取消、再履约、再评价（`OrderStatusConstant.isTerminal()` 守卫）
- 【必须 v1.14】`orders.aftersale_status` 为订单维度的售后聚合进度，取值 `NONE` / `APPLYING` / `REFUNDING` / `REFUNDED`，与售后单据状态机联动写入，不得独立修改。
- 【必须 v1.14】前端所有订单状态文案/颜色统一取自 `frontend/src/config/business.js`，并同时兼容历史值 `FULFILLING`（等价 `PROCESSING`）。

### 5.3 支付状态

```text
PENDING(待支付) -> SUCCESS(成功) | FAILED(失败) | TIMEOUT(超时)
SUCCESS -> REFUNDING(退款中) -> REFUNDED(已退款)
```

- 【必须】模拟支付回调必须幂等：同一支付流水号重复回调只处理一次。
- 【必须】支付成功必须驱动订单状态从 `PENDING_PAY` 到 `PAID`，且在同一事务或可靠事件中完成。

### 5.4 履约状态

```text
PENDING_ASSIGN(待分配) -> PENDING_PICKUP(待自提) | DELIVERING(配送中)
DELIVERING -> DELIVERED(已送达)
PENDING_PICKUP -> PICKED_UP(已自提)
任意 -> EXCEPTION(异常)
```

- 【必须】履约完成必须校验订单已支付。
- 【必须】履约状态与订单状态必须一致，履约完成时订单才能进入 `COMPLETED`。

### 5.5 售后状态

```text
APPLYING(待审核) -> APPROVED(待退款) | REJECTED(已驳回)
APPROVED -> REFUNDING(退款中) -> REFUNDED(已退款)
```

- 【必须】售后金额不得超过订单实付金额。
- 【必须】同一订单同一明细的售后次数受限制，需记录累计退款金额。
- 【必须】售后通过后必须联动支付退款、订单状态、库存（如需回库）。
- 【必须 v1.14】售后单据状态（`aftersale.aftersale_status`）完整流转：
  - `APPLYING → APPROVED`（商家 / Admin 审核通过）后，**在同一事务内继续** `REFUNDING → REFUNDED` 完成退款
  - `APPLYING → REJECTED`（驳回，终态；仍允许 Admin 强制退款二次介入）
  - 每次变更必须写 `aftersale_record` 轨迹：前状态、后状态、操作人、操作角色、备注、时间
- 【必须 v1.14】售后单据状态必须与订单维度状态联动双写：
  - 单据 `APPLYING` → `orders.aftersale_status = APPLYING`
  - 单据 `REFUNDING` / `REFUNDED` → `orders.aftersale_status = REFUNDING` / `REFUNDED`
  - `order_status` 主状态是否流转 `REFUNDING → REFUNDED` 严格遵循 5.2 准入规则（`COMPLETED` 订单保持 `COMPLETED`）
- 【必须 v1.14】同一订单明细有效售后单上限 **2 次**（`MAX_AFTERSALE_PER_ITEM`），超限抛 `AFTERSALE_COUNT_EXCEED`。
- 【必须 v1.14】退款必须**幂等**：以 `aftersaleNo` 作为支付退款的 `bizNo`，重复调用不得重复退款；执行退款前必须二次校验「明细可退额 = 小计 − 已退」与「订单可退额 = 实付 − 已退」，不足抛 `AFTERSALE_AMOUNT_INVALID`。
- 【必须 v1.14】**退货退款（`RETURN`）** 审核通过后必须联动库存回库：按 `sku_id + community_id + pickup_point_id` 定位 `stock`，调用 `StockService.inbound()` 增加 `total_qty` / `available_qty` 并写 `INBOUND` 流水（备注含售后单号）；**仅退款（`REFUND_ONLY`）不回库**。
- 【必须 v1.14】Admin 端售后为**只读监控 + 强制介入**：`POST /admin/aftersales/{id}/audit`（强制审核）、`POST /admin/aftersales/{id}/force-refund`（强制退款，跳过商家审核）；两者必须记录 `operator_role = ADMIN`，强制退款需二次确认 + 必填介入原因，退款金额取 `approved_amount ?? apply_amount`，**前端不得传入金额**。

## 6. 库存与并发约束

- 【必须】库存扣减采用条件更新，禁止先查后减。

```sql
UPDATE stock
SET locked_qty = locked_qty + #{qty}, version = version + 1
WHERE sku_id = #{skuId}
  AND community_id = #{communityId}
  AND available_qty >= #{qty};
```

- 【必须】影响行数为 0 时判定库存不足，抛业务异常并回滚。
- 【必须】库存预占必须设置超时释放时间，默认 15 分钟，由定时任务扫描释放。
- 【必须】支付成功后，预占转实扣：`locked_qty - qty`，`total_qty - qty`，写流水。
- 【必须】订单取消/超时，释放预占：`locked_qty - qty`，写流水。
- 【必须】禁止在库存不足时部分扣减，必须整单原子扣减或整单失败。
- 【必须】并发测试必须验证不超卖，建议用 JMeter 或 JUnit 多线程模拟 200 并发。

### 6.1 供应与库存协同约束（课题核心功能）

> 课题原文要求「供应与库存协同」，本节补充约束。

- 【必须】供应计划表 `supply_plan` 必须包含：`id`、`plan_no`、`sku_id`、`merchant_id`、`community_id`、`plan_date`（计划日期/截单日）、`plan_qty`（计划采购量）、`adjusted_qty`（调整后数量）、`adjust_reason`（调整原因）、`forecast_qty`（关联需求预测值）、`status`（DRAFT / CONFIRMED / ARRIVED / CANCELLED）、`arrive_time`、`operator_id`、`remark`、`create_time`、`update_time`、`is_deleted`。
- 【必须】供应计划创建时必须关联需求预测结果（`forecast_result`），允许商家人工调整 `plan_qty`，调整后必须记录 `adjusted_qty` + `adjust_reason` + `operator_id`。
- 【必须】供应到货后必须驱动库存：`total_qty += qty`，写 `stock_record`（变更类型 **SUPPLY_IN**），与供应计划状态 `ARRIVED` 在同一事务中完成。
- 【必须】库存流水变更类型完整枚举：LOCK（预占）、UNLOCK（释放预占）、DEDUCT（实扣）、ROLLBACK（回滚）、INBOUND（人工入库/调拨）、**SUPPLY_IN**（供应到货入库）。
- 【必须】供应计划与库存必须双写一致：供应计划确认后锁定预估到货量，到货后实际入库，差异（实际 vs 计划）必须写 `stock_record` 备注。
- 【必须】库存预警必须联动供应：当 `available_qty` 低于安全阈值时，自动生成供应建议（参考预测结果 + 当前库存），但不自动创建供应计划。
- 【必须】供应计划失败（如供应商缺货）必须回滚库存预估状态，并记录原因，支持重新创建。
- 【必须】供应与库存协同操作必须写操作日志，记录操作人、调整前后值、关联预测值。

## 7. 接口设计约束

### 7.1 统一响应

- 【必须】统一响应体：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "traceId": "xxx"
}
```

- 【必须】业务错误码统一定义在枚举中，禁止硬编码字符串。
- 【必须】HTTP 状态码与业务码分离，业务异常统一返回 200 + 业务错误码，或按团队约定统一。
- 【必须】**前端 axios 拦截器必须检查 `res.code !== 0`（成功码为 0），禁止写成 `res.code !== 200`（HTTP 200 不代表业务成功）**。v1.2 实战踩坑：前端写了 `code !== 200`，后端返回 `code:0` 导致所有请求被误判为失败，登录/购物车/订单全挂。

#### 7.1.1 前后端响应码契约（v1.2 新增，实战踩坑）

> **实战背景**：后端成功码 `SUCCESS(0)`，但前端 request.js 拦截器写了 `res.code !== 200`，导致所有后端返回的成功响应被误判为失败，ElMessage 弹"请求失败"。后端日志显示 `HTTP 200 + code:0` 完全正常，但前端体验为"登录失败"。

**三端必须完全对齐此表**：

| code | 含义 | HTTP 状态 | 前端处理 |
|---|---|---|---|
| **0** | **业务成功** | 200 | 正常取 `res.data` |
| 400 | 参数错误 | 200 | ElMessage.error(res.message) |
| 401 | 未登录/token 过期 | 200 | 跳登录页 |
| 403 | 越权访问 | 200 | ElMessage.error(res.message) |
| 404 | 资源不存在 | 200 | ElMessage.error("资源不存在") |
| 500 | 系统异常 | 200 | ElMessage.error("系统异常，请稍后重试") |

**前端拦截器正确写法**：

```javascript
// request.js 响应拦截器
request.interceptors.response.use(
  response => {
    const res = response.data
    // ✅ 正确：后端成功码为 0
    if (res.code !== 0) {
      // 错误处理...
      return Promise.reject(new Error(res.message || '请求失败'))
    }
    return res.data // 直接返回 data 部分
  }
)
```

**后端 R.java 正确返回**：

```java
public class R<T> {
    private Integer code;    // 成功 = 0，失败 = 4xx/5xx
    private String message;
    private T data;
    private String traceId;

    public static <T> R<T> ok(T data) {
        R<T> r = new R<>();
        r.setCode(ErrorCode.SUCCESS.getCode()); // 0
        r.setMessage(ErrorCode.SUCCESS.getMessage());
        r.setData(data);
        return r;
    }
}
```

### 7.2 RESTful 规范

- 【必须】资源命名使用复数名词，如 `/api/orders`、`/api/products`。
- 【必须】查询用 GET，创建用 POST，更新用 PUT/PATCH，删除用 DELETE。
- 【必须】分页参数统一：`pageNum`、`pageSize`，默认 1 和 10，最大 100。
- 【必须】分页返回统一：`{ total, pages, current, size, records }`。

### 7.3 接口安全

- 【必须】所有非公开接口必须校验登录态。
- 【必须】所有写操作必须校验角色权限和数据范围。
- 【必须】敏感接口（支付、退款、售后审核、库存修改）必须记录操作日志。
- 【必须】接口参数必须做合法性校验，使用 `@Valid` + 自定义校验注解。

### 7.2 Controller 路由命名规范（v1.2 新增，实战踩坑）

> **实战背景**：`ProductController` 用 `@GetMapping("/{id}")` 匹配商品详情，但 Spring 的 `/{id}` 是贪婪匹配，把 `/filterable-attr-keys`、`/attr-dict` 等单段字符串路径也吞掉了，导致 `NumberFormatException`。5 个 Controller 共 12 处裸 `/{id}` 全部需要修复。

#### 7.2.1 路径变量必须加正则限制

**【强制】所有裸 `/{数字型变量}` 必须加正则限制，禁止无约束的 `/{id}`**：

```java
// ❌ 禁止：贪婪匹配，会吞掉 /search、/filterable-attr-keys 等字符串路径
@GetMapping("/{id}")
public R<Product> detail(@PathVariable Long id) { ... }

// ✅ 正确：只匹配数字，字符串路径由其他端点处理
@GetMapping("/{id:\\d+}")
public R<Product> detail(@PathVariable Long id) { ... }
```

**注意**：Java 字符串里反斜杠需要转义，所以正则 `\d+` 在 Java 注解里写成 `\\d+`（双反斜杠）。Spring 在解析路径模板时会正确处理。

**批量修复命令**（PowerShell）：

```powershell
$files = Get-ChildItem "backend/src/main/java" -Recurse -Filter "*Controller.java"
foreach ($f in $files) {
    $c = [System.IO.File]::ReadAllText($f.FullName)
    $c = $c.Replace('/{id}', '/{id:\\d+}')   # 先替换裸 id
    [System.IO.File]::WriteAllText($f.FullName, $c, [System.Text.UTF8Encoding]::new($false))
}
```

#### 7.2.2 路径命名风格统一

| 类型 | 风格 | 例子 | 说明 |
|---|---|---|---|
| 列表查询 | `GET /资源` | `GET /products?keyword=崇明` | 用 query params 传搜索条件，不要用 `/search` 路径 |
| 详情 | `GET /资源/{id:\d+}` | `GET /products/1` | id 必须是数字 |
| 子资源操作 | `GET /资源/{id:\d+}/子资源` | `GET /products/1/attributes` | 两段路径，不会被 `/{id}` 吞掉 |
| 字典/枚举 | `GET /资源/xxx-dict` | `GET /products/attr-dict` | 用 `-dict` 后缀，避免单词路径 |
| 业务动作 | `POST /资源/{id:\d+}/动作` | `POST /products/1/shelf` | shelf/off-shelf/attributes 等 |

**禁止**：
- ❌ `GET /products/search`（用 `GET /products?keyword=xxx` 替代）
- ❌ `GET /products/list`（多余，`GET /products` 就是列表）
- ❌ `GET /products/{name}`（字符串路径变量必须加正则或放到 query params）

#### 7.2.3 前端 API 路径必须与后端一一对应

**【强制】前端 api/index.js 每个函数必须对应后端真实存在的端点，命名风格统一**：

```javascript
// ✅ 正确：对应后端 GET /products?keyword=xxx
export const searchProducts = (params) => request.get('/products', { params })

// ❌ 错误：后端根本没有 /products/search 端点
export const searchProducts = (params) => request.get('/products/search', { params })

// ✅ 正确：路径完全匹配后端
export const getFilterableAttrs = () => request.get('/products/filterable-attr-keys')

// ❌ 错误：后端是 filterable-attr-keys 不是 filterable-attrs
export const getFilterableAttrs = () => request.get('/products/filterable-attrs')
```

**前端脚手架生成时必须对照后端 Controller 签名写 API 路径**，不要凭感觉命名。

> **v1.5 实战踩坑补**：`Orders` 表同时存在自增主键 `id`（Long）和业务编号 `order_no`（String, `ORD`+时间戳），后端 `@GetMapping("/{id:\\d+}")` 正则限制只接受纯数字，前端误用了 `GET /orders/ORD1790067809425` → Spring 找不到匹配路径 → **404 Not Found**。
>
> **结论**：后端必须为每个业务查询维度都提供入口。正确做法：
> ```java
> // 按主键
> @GetMapping("/{id:\\d+}") public R detail(@PathVariable Long id) { ... }
> // 按业务编号（新增）
> @GetMapping("/no/{orderNo}") public R detailByOrderNo(@PathVariable String orderNo) { ... }
> ```
> 前端：`getOrder = (orderNo) => request.get('/orders/no/${orderNo}')`

## 8. 认证授权与数据隔离约束

- 【必须】认证使用 JWT 或 Session，全项目统一，token 有效期明确。
- 【必须】密码使用 BCrypt 加密存储，禁止 MD5、SHA1。
- 【必须】权限模型采用 RBAC：用户-角色-权限。
- 【必须】数据范围权限必须在 Service 层校验，例如：
  - 消费者：只能操作 `user_id = 当前用户` 的购物车、订单、售后、评价；
  - 商家：只能操作 `merchant_id = 当前商家` 的商品、库存、订单、履约；

### 8.1 JWT 鉴权错误码契约（v1.3 实战踩坑补）

> **踩坑背景（2026-09-22）**：后端 `ErrorCode.UNAUTHORIZED = 1002`，但前端 `request.js` 只识别 `res.code === 401`；同时后端 `JwtAuthInterceptor.write401()` 方法名叫 "write401" 却实际写 **HTTP 200 + code=1002**，导致 token 无效时：① HTTP status 不是 401 前端 error 拦截器不触发；② code 不是 401 前端 response 拦截器不触发 logout；最终 ElMessage.error("请求失败") 了事，用户卡死。

- 【必须】后端 `ErrorCode.UNAUTHORIZED` 的 **code 值必须统一为 401**（与 HTTP 语义对齐），禁止使用 1002/401 两套并行。
- 【必须】`JwtAuthInterceptor.write401()` 必须真的写 `response.setStatus(401)`，禁止硬编码 200。
- 【必须】前端 `request.js` 必须同时拦截：
  - HTTP status 401（网络层，用于 `setStatus(401)` 场景）；
  - `res.code === 401`（业务层，用于 `setStatus(200)` 但 code=401 场景）；
  - 两者任一触发，都必须：`userStore.logout()` → 清除 localStorage → `router.push('/login')`。
- 【必须】JWT 签名密钥必须固定写入 `application.yml` 的 `business.jwt.secret`（禁止随机生成、禁止用临时 env 变量覆盖），否则每次重启后端浏览器 token 全部失效。
- 【必须】前端登录成功后必须覆盖性写入 `localStorage.setItem('token', newToken)`，禁止追加或保留旧 token。

### 15.2 Layout 路由切换禁止 Transition mode="out-in"（v1.4 实战踩坑补）

> **问题现象**：点击「我的」后再切换到其他 Tab（分类 / 购物车 / 订单），目标页面 `<main>` 只剩 `<!---->` 注释占位，整页空白。
>
> **根因链**：
> ```
> ConsumerLayout <router-view> 用了 <transition name="fade" mode="out-in">
>     + Profile.vue 是 Vue 3 fragment（<template> 下两个根：<div class="consumer-profile"> + <el-dialog>）
>     → Transition 找不到单一 DOM 节点做 leave 动画
>     → leave 永远不会 "完成"（mode="out-in" 要求旧组件 leave 完成后新组件才 mount）
>     → 新组件 mount 永久卡死 → 只剩 <!----> 占位
> ```

- 【必须】ConsumerLayout / MerchantLayout / AdminLayout 的 `<router-view>` **禁止**使用 `<Transition mode="out-in">` 包裹。
- 【必须】正确写法：
  ```vue
  <main class="consumer-main">
    <router-view v-slot="{ Component }">
      <component :is="Component" />
    </router-view>
  </main>
  ```
- 【可选替代】如果必须用 Transition，有两种方式：
  1. 改用不带 `mode` 的单向 enter 动画：`<transition name="fade"><component :is="Component" /></transition>`
  2. 确保所有被 Transition 包裹的组件都是**单根**（用外层 `<div>` 包裹 fragment 根节点），例如 Profile.vue：
     ```vue
     <template>
       <div class="profile-wrapper">    <!-- 外层 wrapper，让组件变成单根 -->
         <div class="consumer-profile">...</div>
         <el-dialog>...</el-dialog>
       </div>
     </template>
     ```

### 15.3 前端错误处理约束（v1.4 实战踩坑补）

> **问题现象**：Category 页面筛选器渲染失败但 Console 无报错，Network 请求发了但页面空白，排查时看不到任何异常信号。
>
> **根因**：多个组件的 `onMounted` / watch / 事件处理里用了**空 catch {}**，把后端返回字段错配、API 500、数据结构不匹配等错误**全部静默吞掉**。

- 【必须】所有 try/catch 的 catch 块**禁止空实现**，必须给用户可见反馈。
  - ✅ 正确：`} catch (e) { ElMessage.error('操作失败：' + (e.message || '网络异常')) }`
  - ❌ 禁止：`} catch {}`
- 【建议】在 axios 拦截器里统一处理通用错误（401 token 过期 → 跳登录、500/502 → ElMessage.error），业务层 catch 只处理业务异常（库存不足、金额超限等）。
- 【建议】Vite dev server 修改代码后如果页面空白，先做 **Ctrl+Shift+R 硬刷新**（绕过浏览器缓存），再看 Console 是否有 `Component inside <Transition> renders non-element root node` 警告。

## 20. 核心原则总结

> 状态机是骨架，库存并发是底线，预测评估是亮点，权限脱敏是合规，异常测试是加分项。
> 数据库选型要稳，版本控制要清，UI 风格要统一，布局骨架要固定，数据库改动要版本化，技术定型要写 ADR，技术转换要有回滚。

开发过程中，所有模块设计和代码实现都应围绕以下闭环展开：

```text
商品建档 → 浏览选购 → 购物车 → 订单确认 → 模拟支付 → 履约交付 → 售后评价
```

同时，需求预测作为核心智能化功能，必须满足：

```text
历史模拟数据 → 数据清洗 → 时间特征构造 → 模型训练 → 基线对比 → MAE/RMSE 评估 → 预测区间 → 计划辅助
```

本项目最终应形成统一工程规范：

```text
统一技术栈 → 统一数据库迁移 → 统一 UI 风格 → 统一布局骨架
-> 统一状态机 → 统一权限校验 → 统一异常处理 → 统一测试标准
-> 完整业务闭环 → 可信预测评估 → 可答辩交付
```

以上约束自项目启动之日起执行，作为开发、Code Review、测试和答辩自检的统一标准。

## 21. 数据库技术选型

### 21.1 选型结论

| 类别 | 选型 | 版本 | 用途 | 约束 |
|---|---|---|---|---|
| 关系型数据库 | MySQL | 8.0+ | 核心业务数据 | 必须 InnoDB，utf8mb4 |
| 缓存 | Redis | 7.x | 会话、库存预占、热点商品、验证码 | 不得作为唯一数据源 |
| ORM | MyBatis-Plus | 3.5.x | 数据访问 | 全项目统一，禁止混用 JPA |
| 连接池 | HikariCP | Spring Boot 默认 | 数据库连接 | 必须配置最大连接数、超时 |
| 数据库迁移 | Flyway | 9.x+ | 版本化 DDL/DML | 禁止手工改库 |
| 测试数据库 | H2 / Testcontainers | 按需 | 单元/集成测试 | 优先 Testcontainers MySQL |
| 可视化 | ECharts | 5.x | 经营分析、预测展示 | 统计口径以后端为准 |
| 预测实现 | Java 内置 / Python 离线 | - | 移动平均、线性回归、树模型 | 优先 Java，Python 仅离线 |

### 21.2 MySQL 约束

- 【必须】存储引擎统一 InnoDB。
- 【必须】字符集 `utf8mb4`，排序规则 `utf8mb4_general_ci`。
- 【必须】时区统一 `Asia/Shanghai`，时间字段用 `datetime` 或 `timestamp`，应用层用 `LocalDateTime`。
- 【必须】事务隔离级别默认 `REPEATABLE-READ`，如无特殊需要不得修改。
- 【必须】金额 `decimal(12,2)`，禁止 `float`/`double`。
- 【必须】主键 `bigint`，订单号、支付流水号等业务编号另建唯一索引。
- 【必须】高频查询字段必须建索引：`user_id`、`merchant_id`、`community_id`、`order_no`、`sku_id`、`status`、`create_time`。
- 【必须】禁止 `select *`，禁止无分页全表查询。
- 【建议】复杂统计走独立统计 SQL 或定时汇总表，避免拖垮交易表。

### 21.3 Redis 约束

- 【必须】Redis key 必须带业务前缀：`cart:user:{userId}`、`stock:sku:{skuId}:community:{communityId}`、`token:user:{userId}`。
- 【必须】库存预占 key 必须设置过期时间，默认 15 分钟。
- 【必须】Redis 与 MySQL 双写时，以 MySQL 为准，Redis 只做加速。
- 【必须】禁止把订单、支付、售后等强一致数据只存 Redis。
- 【建议】热点商品缓存、首页分类缓存、预测结果缓存设置合理 TTL。

### 21.4 预测模块数据库选型

- 【必须】预测结果独立表：`forecast_task`、`forecast_result`、`forecast_metric`。
- 【必须】预测数据与交易数据物理隔离，预测失败不得影响订单、支付、库存。
- 【必须】预测结果表必须记录模型版本、生成时间、预测日期、区间下限、区间上限。
- 【建议】树模型用 Python 离线训练，结果导出 CSV 或直接写库，不在线调用。

## 22. 版本控制规范

### 22.1 分支模型

```text
main        稳定可演示分支，只接受 release/hotfix 合并
dev         日常集成分支
feature/*   功能分支，如 feature/order-cancel
fix/*       缺陷修复分支
release/*   答辩前冻结分支，如 release/v1.0.0
hotfix/*    紧急修复分支
```

- 【必须】禁止直接向 `main`、`dev` 推送，必须通过 PR/MR。
- 【必须】功能分支从 `dev` 切出，完成后合并回 `dev`。
- 【必须】答辩前从 `dev` 切 `release/v1.0.0`，冻结功能，只修 bug。
- 【必须】`main` 每次合并必须打 tag，如 `v1.0.0`。

### 22.2 提交信息规范

格式：`type(scope): subject`

| type | 含义 |
|---|---|
| feat | 新功能 |
| fix | 修复缺陷 |
| docs | 文档 |
| style | 格式 |
| refactor | 重构 |
| test | 测试 |
| chore | 构建/工具 |
| perf | 性能优化 |

示例：

```text
feat(order): 新增订单取消接口
fix(stock): 修复并发扣减超卖问题
docs(db): 更新订单表数据字典
test(pay): 增加支付回调幂等测试
```

- 【必须】提交必须能编译通过。
- 【必须】禁止提交 `target/`、`node_modules/`、`*.log`、`.env`、IDE 配置。
- 【必须】敏感配置用环境变量或本地配置，不得入库。
- 【建议】数据库迁移脚本单独提交，提交信息注明版本号。

### 22.3 版本号规范

- 【必须】使用语义化版本：`MAJOR.MINOR.PATCH`。
- 【必须】毕业设计建议：`v0.1.0` 骨架，`v0.5.0` 核心闭环，`v1.0.0` 答辩版。
- 【必须】每次发布更新 `CHANGELOG.md`。
- 【必须】接口版本统一 `/api/v1`，后续大改才升 `/api/v2`。

### 22.4 代码评审

- 【必须】PR 必须至少一人 Review。
- 【必须】Review 重点：状态机、库存并发、权限校验、异常处理、日志脱敏、SQL 索引。
- 【必须】PR 描述必须写：改了什么、为什么、影响范围、测试方式、是否涉及数据库改动。

## 25. 数据库改动规则

### 25.1 总原则

- 【必须】所有数据库改动必须通过 Flyway/Liquibase 迁移脚本，禁止手工改库。
- 【必须】已执行的迁移脚本禁止修改，只能新增脚本。
- 【必须】迁移脚本必须纳入 Git，随代码一起评审。
- 【必须】数据库改动必须同步更新：ER 图、数据字典、实体类、DTO、Mapper、测试用例。
- 【必须】禁止在迁移脚本中写与业务无关的 DML。
- 【必须】初始化数据、字典数据可以写 DML，但必须可重复执行或明确只执行一次。

### 25.2 命名规范

```text
V1__init_schema.sql
V2__add_order_snapshot.sql
V3__add_stock_record.sql
V4__add_forecast_tables.sql
V5__refactor_product_attribute.sql
V6__add_supply_plan.sql
V7__add_order_item_attr_snapshot.sql
```

- 【必须】版本号连续，禁止跳号。
- 【必须】描述用 snake_case，简洁明确。
- 【必须】回滚脚本可选：`U{版本}__{描述}.sql`，答辩项目建议至少准备关键表回滚说明。

### 25.3 字段改动规则

- 【必须】新增字段必须有默认值或允许 NULL，避免影响旧数据。
- 【必须】新增非空字段必须分三步：加可空字段 → 回填数据 → 改非空。
- 【必须】删除字段必须先标记废弃，保留至少一个版本，再删除。
- 【必须】修改字段类型必须评估数据兼容、索引、代码影响。
- 【必须】禁止直接重命名字段，建议新增字段 + 数据迁移 + 废弃旧字段。
- 【必须】金额、状态、时间字段必须遵守第 4 章约束。

### 25.4 索引与约束改动

- 【必须】新增索引必须说明查询场景，并用 `EXPLAIN` 验证。
- 【必须】唯一索引必须考虑历史数据重复问题。
- 【必须】外键约束推荐应用层维护，如使用数据库外键必须评估删除顺序。
- 【必须】库存表必须保留 `version` 乐观锁字段或条件更新字段。
- 【必须】订单、支付、售后状态变更必须写状态日志表。

### 25.5 环境与执行

- 【必须】开发、测试、答辩环境数据库结构必须一致。
- 【必须】CI 或启动时自动执行 Flyway，禁止人工执行 SQL。
- 【必须】每次数据库改动必须在测试环境验证：全新执行、增量执行、回滚说明。
- 【必须】答辩前必须备份一份稳定数据库快照。
- 【建议】提供 `docs/db/ER.md`、`docs/db/data-dictionary.md`、`docs/db/migration-log.md`。

## 26. 技术定型与转换规则

### 26.1 技术定型清单

| 层次 | 定型技术 | 定型后约束 |
|---|---|---|
| 后端框架 | Spring Boot 3 + JDK 17 | 禁止中途换 Quarkus/Micronaut |
| ORM | MyBatis-Plus | 禁止混用 JPA |
| 数据库 | MySQL 8 | 禁止换 PostgreSQL/H2 作为主库 |
| 缓存 | Redis 7 | 禁止用本地 Map 替代分布式缓存 |
| 认证 | JWT | 禁止混用 Session |
| 前端 | Vue 3 + Vite + Pinia + Element Plus | 禁止换 React/Angular |
| 图表 | ECharts | 禁止混用多图表库 |
| 迁移 | Flyway | 禁止手工改库 |
| 预测 | Java 内置 / Python 离线 | 禁止在线强依赖 Python 服务 |
| 文档 | Knife4j/OpenAPI | 接口必须同步更新 |

- 【必须】以上技术定型后，任何替换必须走 ADR 流程。
- 【必须】禁止在 `feature/*` 分支中混入技术栈替换。
- 【必须】技术定型文档放在 `docs/adr/`。

### 26.2 技术转换触发条件

只有满足以下至少一条，才允许评估技术转换：

- 当前技术无法满足核心业务需求，如库存并发、状态一致性。
- 当前技术存在严重安全漏洞且无法修复。
- 当前技术导致性能无法达标，且有数据证明。
- 答辩或交付要求必须更换。
- 团队完全无法维护，且迁移成本可控。

### 26.3 技术转换评估维度

| 维度 | 说明 |
|---|---|
| 收益 | 性能、稳定性、开发效率、可维护性 |
| 成本 | 人力、时间、学习成本、联调成本 |
| 风险 | 数据迁移、状态一致性、回滚难度 |
| 影响范围 | 模块、接口、数据库、前端、测试 |
| 迁移方案 | 双跑、灰度、数据同步、兼容层 |
| 回滚方案 | 回滚条件、回滚步骤、数据恢复 |
| 测试方案 | 单元、集成、并发、回归 |
| 文档更新 | ADR、README、接口文档、ER 图 |

### 22.6 IDE 配置必须与 pom.xml 对齐（v1.2 新增，实战踩坑）

```xml
        <plugin>

            <artifactId>maven-compiler-plugin</artifactId>
            <configuration>
                <source>17</source>
                <target>17</target>
                <release>17</release>
                <encoding>UTF-8</encoding>
            </configuration>
        </plugin>
    </plugins>
</build>
```

| Module SDK | File → Project Structure → Modules → Dependencies | Project SDK (17) |
| Maven Runner JRE | Settings → Build → Execution, Deployment → Build Tools → Maven → Runner | JRE 17 |
| Import 后刷新 | 右键 pom.xml → Maven → Reload Project | 让 IDEA 读 compiler-plugin |

**三端 Java 版本必须统一**：

| 位置 | 版本 | 说明 |
|---|---|---|
| pom.xml java.version | 17 | Spring Boot parent 用 |
| pom.xml maven-compiler-plugin release | 17 | IDEA 必须显式声明 |
| IDEA Project SDK | 17 | 不配对就报"不支持发行版本 5" |
| application.yml | 无 | 不需要配，Java 版本由编译期决定 |

**验证方法**：


## 27. 后端启动与操作纪律（v1.3 新增，实战踩坑）

> 本章专门约束"不要随便启动/重启后端、不要随便操作浏览器"的纪律。每次后端重启都会触发连锁反应：浏览器旧 token 失效、前端 API 路径不一致、页面状态丢失。v1.3 开发周期（2026-09-22）因无纪律重启导致前后端联调反复。

### 27.1 后端启动前必须做的三件事

- 【必须】**先跑 mvn compile**，确认编译通过再 spring-boot:run。禁止跳 compile 直接 run 然后在运行时才发现编译错误。
- 【必须】**确认端口 8080 已释放**，使用项目根目录 .kill-port.ps1 或 
etstat -ano | findstr 8080 + 	askkill /PID /F，禁止硬等或盲目 Ctrl+C。
- 【必须】**确认 MySQL + Redis 已启动**，否则后端启动后 10 秒内会抛连接异常（DruidDataSource init fail / RedisConnectionFailureException）。

### 27.2 后端重启后必然发生的事

- 【必然】浏览器 localStorage 里的 token 与当前后端签名密钥**可能不一致**（取决于 YAML usiness.jwt.secret 是否改过），旧 token 的每次请求后端都会打 WARN [JWT] token 无效。
- 【必然】Vite 前端 Dev Server 不需要重启（热更新），但**浏览器页面状态全部丢失**（Pinia store 重置、路由守卫重新执行）。
- 【必然】Flyway 如果启用会校验 schema 版本（当前 lyway.enabled=false，**禁止随便改为 true**，否则会校验整个 DDL 历史）。

### 27.3 "不操作浏览器"纪律

- 【必须】后端重启后，先用 **PowerShell 直连验证**（Invoke-RestMethod），确认接口返回正确再打开浏览器。禁止先开浏览器瞎点。
- 【必须】浏览器只做三件事：① 视觉验收；② 控制台抓错误；③ 截图留档。**禁止用浏览器写代码、禁止用浏览器当 API 客户端**（PowerShell/Postman 才是 API 客户端）。
- 【必须】浏览器遇到"请求失败"时，**先看后端日志**（有没有 [JWT] token 无效？有没有 SQL 异常？），再看前端控制台。禁止只盯着前端控制台。
- 【必须】每次进入浏览器前，**先确认后端最近一次启动的时间**（看日志最后一行 Started GroupBuyApplication 的时间戳），如果比上次操作早，说明中间有重启过，先直连验证。

### 27.4 JWT Secret 锁死规则

- 【必须】pplication.yml 中 usiness.jwt.secret 必须固定为 community-group-buy-secret-key-must-be-at-least-256-bits-long-for-hs256，**禁止**：
  - 用 ${JWT_SECRET} env 变量覆盖（Windows 本机没设就会拿到一个不一致的值）；
  - 每次启动随机生成；
  - 不同 profile 用不同 secret。
- 【必须】secret 一旦写入 YAML，视为"运行时常量"，改动前要通知所有人清浏览器 localStorage。

## 28. v1.3 实战踩坑全记录（2026-09-22）

> 本章记录 v1.3 开发周期（消费者端三页面修复）暴露的全部问题，按"现象 → 根因 → 修复 → 教训"四要素记录，后续开发遇到类似问题直接对照。

### 28.1 分类页：前端 API 路径写错

- **现象**：分类检索页左侧"分类"筛选栏整个消失（-if="categories.length" 求值为 0 导致 div 不渲染）。
- **根因**：前端 pi/index.js 写 GET /categories，但后端实际嵌在 ProductController 下，路径是 GET /products/categories/tree。属于前后端路由各自为政。
- **修复**：前端 pi/index.js 改路径一行，对齐后端实际路由。
- **教训**：前端脚手架生成 API 时**必须对照后端 Controller 的 @RequestMapping + @GetMapping 拼接完整路径**，禁止凭模块名猜路径。

### 28.2 购物车：后端返回纯 CartItem，前端缺商品名

- **现象**：购物车渲染时 -for item in items 里的 item.productName 是 undefined，全部显示空。
- **根因**：CartService.listMine() 直接 eturn cartItemMapper.selectList() 返回 List<CartItem> 实体，CartItem 只有 skuId / productId 外键，没有商品名/SKU 名/图片。前端需要做三次补全。
- **修复**：改 Service 层，批量查 SKU Map 和 Product Map，组装 List<Map<String, Object>> 返回，一次查全。
- **教训**：凡是前端列表需要跨表展示的，**必须在 Service 层聚合**，禁止让前端再调二次接口补数据（违背约束 11.1 前端只调一次）。

### 28.3 订单页：后端 listMine 没带 OrderItem

- **现象**：订单卡片里的商品名、数量、合计全部显示 undefined 或 0。
- **根因**：OrderService.listMine() 直接返回 List<Orders> 主表实体，没聚合 order_item 子表。而 detail() 方法已经正确实现了聚合。同一个 Service 里两套实现不一致。
- **修复**：参照 detail() 模式，批量查 OrderItem 分组聚合，返回 List<Map<String, Object>>。
- **教训**：Service 层的 list/detail 方法**返回结构必须一致**（要么都聚合要么都不聚合），禁止 detail 带子项 list 不带。

### 28.4 JWT 错误码契约不一致（终极连锁坑）

- **现象**：后端重启后浏览器所有受保护页面同时报 "请求失败"，控制台一片 equest.js:50。
- **根因链**（三层锁死）：
  1. 后端 ErrorCode.UNAUTHORIZED = 1002（不是 401）；
  2. 后端 JwtAuthInterceptor.write401() 方法名叫 write401，却写 esponse.setStatus(200) 硬编码；
  3. 前端 equest.js 只识别 es.code === 401 和 HTTP status 401，不识别 code === 1002 也不识别 HTTP 200；
  → 结果：后端写 HTTP 200 + code=1002，前端两个拦截器都不触发 logout，只弹一个通用错误消息。
- **修复**：
  1. ErrorCode.UNAUTHORIZED code 值统一为 **401**（对齐 HTTP 语义）；
  2. write401() 真写 esponse.setStatus(HttpServletResponse.SC_UNAUTHORIZED)；
  3. 前端 equest.js 同时拦截 es.code === 401 || res.code === 1002（防御旧后端）。
- **教训**（已写入约束 8.1）：**前后端错误码是一份契约**，必须：
  - HTTP 状态码与业务 code 语义一致（401=未授权=未登录=token 失效）；
  - 后端签名和前端解析都用同一个数值（禁止 1002 和 401 两套并行）；
  - 前端必须防御性处理历史遗留值。

### 28.5 PowerShell Set-Content 生成的 BOM 导致 Java 编译失败

- **现象**：mvn compile 报 [ERROR] 找不到符号: class interface enum record + 首行 \\ufeff。
- **根因**：PowerShell Set-Content 默认加 UTF-8 BOM（\\ufeff），Java 编译器把 BOM 当成非法字符。
- **修复**：用 [System.IO.File]::WriteAllText(path, content, [System.Text.UTF8Encoding]::new(False)) 写入无 BOM 文件。
- **教训**：改 Java 文件时**禁止用 PowerShell 的 Set-Content**，用 IDEA / VS Code / 带无 BOM 选项的 IO API。

### 28.6 登录后立刻被踢回登录页：存储层 vs 请求层 key 不统一

- **现象**：刚登录成功（Pinia userStore 状态正常、首页商品列表正常），点购物车/订单 tab 立刻被踢回登录页。控制台报 GET /api/cart 401 (Unauthorized)，后端日志 [JWT] token 无效。
- **根因链**（四层锁死）：
  1. storage.js 封装了统一工具，set(key, value) 写入 localStorage['cg:' + key] = JSON.stringify(value)（PREFIX='cg:' + JSON.stringify 加引号）；
  2. userStore.login() 正确调用 storage.set('token', token)，token 被写入 localStorage['cg:token'] = "\"eyJhbGci...\""（注意外层引号是 JSON.stringify 加的）；
  3. equest.js 的请求拦截器**绕过 storage 工具**，直接写 const token = localStorage.getItem('token')——key 是 'token'，而 storage 存的是 'cg:token'，**永远读不到**；
  4. token 读不到 → Authorization 头为空 → 后端返回 HTTP 401 → request.js error 拦截器 status===401 → logout + router.push('/login')。
- **修复**：request.js 必须通过统一入口拿 token，不能直接读写 localStorage。方案二选一：
  - 方案 A（推荐）：request.js 请求拦截器从 useUserStore().token 拿（Pinia state 已经在 login 里赋值正确）；
  - 方案 B：从 storage.get('token') 拿，但注意 storage.get 返回 JSON.parse 后的值（字符串 token 会去掉 JSON.stringify 加的引号）。
- **教训**（已写入约束 1.2）：
  - localStorage 的 **key 前缀**和**序列化方式**（JSON.stringify）是一份契约，必须由 storage.js 统一封装；
  - **禁止任何组件/工具类绕过 storage.js 直接 localStorage.setItem/getItem**；
  - Pinia 的 state 是 localStorage 的"实时镜像"，请求层应该读 Pinia state（内存），不是读 localStorage（磁盘）。
### 28.7 Jackson non_null + DB NULL = JSON 缺字段

- **现象**：后端 CartService.listMine() 代码里明明有 m.put("image", p.getMainImage())，但前端拿到的 JSON 里**没有 image 键**。前端 <img :src="item.image"> → undefined → 灰色占位图。
- **根因链**（三层锁死）：
  1. pplication.yml 配了 jackson.default-property-inclusion: non_null，Jackson 序列化 Map 时**跳过值为 null 的属性**；
  2. DB seed 里 product.main_image 和 product_sku.image 都是 NULL 或空字符串，p.getMainImage() 返回 null；
  3. m.put("image", null) → Jackson 过滤 → JSON 里没有 "image" 键（不是 "image": null，是**整个键不存在**）；
  4. 前端 template 直接访问 item.image 得到 undefined → <img> 渲染失败 → 显示灰色占位图。
- **修复**：在 Service 层给所有可能为 null 的展示字段**设默认值**，禁止让 Jackson 过滤掉键：
  - image → 默认占位图 /assets/placeholder-product.png；
  - productName / skuName / unit → 空串 ""（防止 p/sku 为 null 时 NPE）；
  - priceSnapshot → 默认 BigDecimal.ZERO（防止 priceSnapshot 为 null）。
- **教训**：
  - 约束 Jackson 的 
on_null 是一把双刃剑——它能让 API 响应更干净，但**Service 层必须防御性给默认值**，不能指望 null 被前端处理；
  - 所有前端要渲染的字段，后端必须保证**键一定存在**（值可以是空串/0/false），不能让 Jackson 把键过滤掉；
  - Map 手动 put 聚合 vs 返回实体类：实体类如果字段有 @TableField(exist=false) 映射到 JSON 的 @JsonProperty(required=true)，就不会丢键；Map 是纯动态结构，更要注意 null 值过滤。

### 28.8 后端缺 Controller（PickupPointController）

- **现象**：checkout 页面点"去结算"后，GET /api/pickup-points 返回 HTTP 404。控制台警告"请求的资源不存在"。
- **根因**：后端 Controller 列表里**完全没有 PickupPointController 或 CommunityController**，只有 CartController/OrderController/FulfillmentController 内部引用了 communityId/pickupPointId 外键字段，但公开的自提点查询接口从未实现。前端 API 定义了 equest.get('/pickup-points') 但后端根本没这个路由。
- **修复**：新建 PickupPointController（@RequestMapping("/pickup-points")）+ PickupPointService，实现按 communityId 查询自提点列表。数据来自 DB pickup_point 表（V1__init_schema.sql 已定义）。
- **教训**：
  - 前端 API 定义**必须与后端 Controller 一一对应**，前端不能"先写接口定义等后端实现"——约束文档 7.2 要求前后端接口契约先对齐再开发；
  - Controller 缺失是**最高优先级**问题（直接 HTTP 404），开发阶段每做完一个页面要 grep 所有 request.xxx 调用，确保后端都有对应路由。

### 28.9 Checkout 页面用 sessionStorage 存数据导致字段丢失

- **现象**：checkout 页面商品清单显示"灰色占位图 + ¥0.00"，控制台 AmountText amount=undefined。
- **根因链**：
  1. CartService 聚合缺 image/priceSnapshot → Cart 页面显示时也没图；
  2. Cart 页面点"去结算"时把购物车 items **原样存入 sessionStorage.setItem('checkoutItems', JSON.stringify(cartItems))**；
  3. Checkout 页面 onMounted 从 sessionStorage.getItem('checkoutItems') 取，取到的就是 Cart 页面当时塞进去的**缺字段版本**；
  4. 结果：Cart 页面的任何字段问题都会被原样传导到 Checkout 页面，无法自愈。
- **修复**：Checkout 页面**不要从 sessionStorage 读 items**，应该**直接调 /cart 接口拿最新数据**（约束 11.1：前端每次进入页面都要从后端拉最新数据，不能信任 sessionStorage）。
- **教训**：
  - sessionStorage 仅用于**临时路由传参**（比如从列表页跳详情页的 itemId），禁止用于**业务数据缓存**；
  - 业务数据必须每次页面进入时从后端拉，否则中间任何字段变化都无法同步；
  - 这次 Cart→Checkout 的字段丢失，本质是 **Cart 页面的缺陷被 sessionStorage 固化传导**。

### 28.10 DB Seed 图片字段全 NULL

- **现象**：所有商品图/sku 图在前端都显示灰色占位。
- **根因**：V3__init_business_data.sql 里 INSERT INTO product(main_image, images) 和 product_sku(image) 的 seed 值全是 NULL。即使 CartService 正确返回了 image 字段，值也是 null/空串。
- **修复**：
  - 临时方案：Service 层给 image 设统一占位图 URL（/placeholder-product.png）；
  - 长期方案：补充 seed 数据，给每个商品/sku 配真实图片 URL（可以用 Unsplash/Picsum 的占位图）。
- **教训**：seed 数据必须**包含前端展示需要的所有字段**，禁止只填外键 ID 不填展示字段。约束文档 5.1：seed 数据要保证"直接启动能跑通完整链路"。
### 28.11 按钮 disabled=!pickupPointId 但后端允许 pickupPointId=null 下单

- **现象**：checkout 页面底部"提交订单"按钮灰着，无法点击。
- **根因链**：
  1. 前端 Checkout.vue L63 写死按钮 :disabled="!pickupPointId"——强制要求用户选自提点；
  2. L113 写 if (pickupPoints.value.length) pickupPointId.value = pickupPoints.value[0].id——只有后端返回非空数组才赋值；
  3. 后端刚重启后第一次前端还没刷新 → 拿到的是上一次的 404 残留状态，pickupPoints 空数组；
  4. pickupPointId.value 永远是初始值 null → !null = true → 按钮 disabled；
  5. **但后端 OrderService.create 对 pickupPointId 根本没做必填校验**（约束 27.3：V3 seed 库存是社区级 pickup_point_id = NULL，意味着"无自提点"是合法业务状态）；
  6. 约束冲突：前端把一个可空字段设成必填。
- **修复**：
  - 前端：去掉按钮 disabled 条件，只在 pickupPoints 非空时**建议**选择（给默认值），为空时允许直接提交（pickupPointId=null）；
  - 后端（已有，无需改）：OrderService.create 不校验 pickupPointId 必填，正确。
- **教训**：
  - 约束文档 7.3：**后端的必填校验才是真正契约**，前端 disabled 只是 UX 体验，禁止前端比后端更严格；
  - 后端允许 null → 前端就不能强制 disabled。
  - 所有 disabled / required 条件必须 grep 后端 Controller 里对应的 if (xxx == null) throw BusinessException。

### 28.12 V2 seed pickup_point 字段缺失

- **现象**：V2__init_rbac_data.sql 的 pickup_point INSERT 只插了 6 个字段（id, community_id, point_name, address, contact_name, open_time），V1 schema 定义了更多字段（contact_phone, status）。
- **根因**：V1 schema pickup_point.status 有 DEFAULT 'ACTIVE' 兜底，所以不报错，但 seed 数据不完整（缺手机号）。
- **修复**：V2 seed 补全所有字段。
- **教训**：约束 5.1：seed 数据必须覆盖所有 NOT NULL 字段，有 DEFAULT 的也要显式写明（方便后续调整 DEFAULT 值时不影响 seed）。
### 28.13 业务模型：社区团购 + 自提，无快递收货地址

- **重要声明**：本项目是**社区团购自提**模式，业务模型**没有快递配送**、**没有 user_address 收货地址表**、**没有运费逻辑**。订单流程：下单 → 支付 → 商家备货 → 自提点通知 → 用户自提。
- **DB schema 确认**：V1__init_schema.sql 无 user_address 表，orders.pickup_point_id 是可选字段（NULL 表示社区级库存直接自提，不指定具体自提点）。
- **前端"收货地址"入口处理**：Profile 页面的"收货地址"快捷入口**脚手架占位**，实际应改为"自提点设置"或移除。禁止硬加快递地址功能（与业务模型冲突）。
- **自提点 vs 收货地址**：社区团购中，"自提点"就是传统电商的"收货地址"的替代品——是用户提货的固定物理地点。自提点由社区预先配置，用户无法自由增删（和收货地址的"用户可自定义添加"不同）。
- **约束（新增）**：
  - 【必须】禁止在项目中引入 user_address 表和"快递配送"概念（偏离业务模型）；
  - 【必须】checkout 页面的自提点选择**必须按用户所属社区 communityId 过滤**，不能展示全局全部自提点；
  - 【必须】选中自提点后展示详情面板（名称、详细地址、联系人、营业时间、营业电话），供用户确认。

### 28.14 前端模板字段名与后端 DTO 不一致

- **现象**：Checkout.vue 自提点区域的 radio button label 全部显示为空（{{ pp.name }} 渲染 undefined），但后端 API 正常返回了 pointName 字段。
- **根因**：前端模板凭习惯写 {{ pp.name }}（来自 Element Plus Demo 里的示例），但后端 PickupPoint 实体字段名是 pointName（不是通用的 
ame）。这是典型的"前端字段命名猜测"反模式。
- **修复**：{{ pp.name }} → {{ pp.pointName }}。
- **教训**（已写入约束 7.3）：前端模板访问后端返回对象的字段时，**必须与后端实体/DTO 的字段名严格一致**，禁止猜测通用名（name/label/value 等）。正确做法：拿到接口 JSON 后对着字段名写模板。
### 28.15 userStore.login() 漏写 communityId → getPickupPoints(null) 返回全社区自提点

- **现象**：checkout 页面自提点区域显示了"绿地香颂南门自提点"（id=3，属于 community_id=2），但当前登录用户 consumer01 属于 community_id=1。用户选了跨社区自提点后下单 → StockService.getBySkuAndCommunity(17, 1, 3) → V3 seed 库存是 pickup_point_id=NULL 社区级 → 精确匹配失败 → 库存不足。
- **根因链**：
  1. 后端 /auth/login 返回的 user.communityId = 1（PowerShell 直连验证正确）；
  2. **前端 userStore.login() 只从 res 里取了 token/userId/username/userType/permissions 五个字段，完全没写 communityId/merchantId**（state.communityId 初始 null，login 后仍是 null）；
  3. getPickupPoints(userStore.communityId) → getPickupPoints(null) → 后端 PickupPointService.listByCommunity(null) → MyBatis-Plus eq(null, PickupPoint::getCommunityId, null) 条件不生效 → 返回**全社区 3 条自提点**；
  4. 用户能看到不属于自己社区的自提点 → 选中 → 下单带跨社区的 pickup_pointId → 库存精确匹配失败。
- **修复**：
  - 前端 userStore.login() 补 	his.communityId = res.communityId；
  - 后端 PickupPointController.getPickupPoints() 加兜底：如果 communityId 为 null，从登录态 SecurityContext.getUserId() 反查 user.communityId（双保险）。
- **教训**（已写入约束 1.2 / 8）：
  - **登录返回的所有字段必须同步写入 Pinia state**——后端返回 user.communityId，前端 store.communityId 就必须赋值；
  - storage.get('communityId') || null 初始值兜底**不能替代 login 里显式赋值**（刷新后能从 storage hydrate，但首次登录 state 必须正确）；
  - 后端 Service 查询"按用户过滤"的数据时，必须**自己从 SecurityContext 拿用户归属，不能信任前端传来的参数**（约束 8：数据范围权限 Service 层校验）。

### 28.16 StockService 查库存必须做"自提点级 → 社区级"降级

- **现象**：用户选了社区 A 下的自提点 P，seed 库存只有社区 A 级别（pickup_point_id=NULL）没有自提点 P 级别 → getBySkuAndCommunity(sku, communityId, pickupPointId=P) 精确匹配 0 条 → 下单失败。
- **根因**：StockService.getBySkuAndCommunity(skuId, communityId, pickupPointId) 只做一次精确匹配 WHERE sku_id=? AND community_id=? AND pickup_point_id=?，没做 fallback 到 pickup_point_id=NULL 的社区级库存。
- **修复**：查询顺序（双保险）：
  1. 先查 pickup_point_id = 指定 ID（自提点级专属库存，精确匹配）；
  2. 查不到 → fallback 查 pickup_point_id IS NULL（社区级默认库存）；
  3. 都没有 → 返回 null（真·缺货）。
- **教训**：
  - 约束文档 4.1 stock 表允许"sku×社区×自提点（NULL 表示社区级）"，语义是**自提点级优先，社区级兜底**；
  - 任何引用了 pickup_point_id 的查询（StockService/FulfillmentService/SupplyService）必须体现这个**优先级降级**逻辑，不能只做一次精确匹配。
### 28.17 Orders 实体未 SET discountAmount/freightAmount/refundedAmount → INSERT NULL 违反 NOT NULL DEFAULT 0

- **现象**：consumer01（community 1）下单 HTTP 500；但跨社区 community=2 下单返回 2001 业务异常（库存不足）。
- **根因链**：
  1. V1 schema orders 表 discount_amount / freight_amount / refunded_amount 是 DECIMAL(12,2) NOT NULL DEFAULT 0（MySQL 不接受显式 INSERT NULL）；
  2. OrderService.create() 只 SET 了 totalAmount 和 payAmount，**漏了这三个字段**；
  3. MyBatis-Plus 默认 FieldStrategy.DEFAULT → 字段为 null 时 INSERT SQL 里显式写 NULL；
  4. community=1 有有效库存 → 校验通过 → 走到 orders INSERT → MySQL 拒绝 NULL 写入 **NOT NULL DEFAULT 0** 列 → SQL 异常 → GlobalExceptionHandler 兜底成 5000/系统异常；
  5. community=2 库存 avail=0 → 校验阶段 throw BusinessException 返回 2001 → 根本没走到 INSERT → 看起来"没崩"。
- **修复**：OrderService.create() 补 order.setDiscountAmount(ZERO) / setFreightAmount(ZERO) / setRefundedAmount(ZERO)。
- **教训**（已写入约束 4.1）：
  - 【必须】所有 NOT NULL DEFAULT X 的字段，Service 层 SET 默认值，**不能依赖 MySQL DEFAULT**——MyBatis-Plus INSERT 会显式传 NULL 覆盖 DEFAULT；
  - 【必须】写完 Orders 实体后 grep set[A-Z] 数量与实体字段数对齐，确认没有遗漏；
  - 社区团购**没有运费/退款/优惠**概念，这三个字段必须显式设为 ZERO。
### 28.19 软删除 + 唯一索引冲突 → 改用硬删除

- **现象**：订单提交 → CartService.clearSelected() 软删除 UPDATE cart_item SET is_deleted=1 WHERE selected=1 → SQLIntegrityConstraintViolationException: Duplicate entry '1-17-1' for key 'cart_item.uk_user_sku'
- **根因链**：
  1. V1 schema cart_item 唯一索引 uk_user_sku(user_id, sku_id, is_deleted) 已经包含 is_deleted；
  2. 软删除后记录变成 (user=1, sku=17, is_deleted=1) 永远留在库；
  3. 用户再次加同一 SKU → MyBatis-Plus selectOne 只查 is_deleted=0 → 没找到 → INSERT 新记录（is_deleted=0）；
  4. 第二次下单 → clearSelected 又要把 is_deleted=0 改成 is_deleted=1 → **库里已经有一条同 (1,17,1) 了** → 撞唯一键！
  5. 只有 is_deleted 同时出现在"被改的记录"和"已存在的旧记录"里才会撞，软删除天然无法避免这种"历史遗留"冲突。
- **修复**：CartService.clearSelected() 改用**硬删除** cartItemMapper.delete(Wrapper) 物理删。
- **约束（新增）**：
  - 购物车 cart_item 表**不需要软删除**——清空/结算后物理删，审计需求由订单表 order_item 的商品快照承担（约束 4.3 已规定 order_item 冗余 productName/skuName/price/image）；
  - 软删除只用于需要**审计追溯**的表（orders/stock/freeze），对于"临时状态"表（cart_item）硬删更合理；
  - 【必须】uk_user_sku 唯一索引既然包含了 is_deleted，就不能再用软删除（MySQL 唯一键冲突是"硬"的，不会因为是软删除就放过）。

## 29. 禁止硬编码铁律（v1.9 新增，2026-09-23）

### 29.1 什么是硬编码（定义）

以下三类字符串 **禁止直接写在业务代码（Service/Controller/前端组件）里**：

| 类型 | 举例 | 违反后果 |
|------|------|---------|
| 状态枚举 | "PENDING_PICKUP"、"COMPLETED"、"PAID" | 拼错一个字母 → 状态机断裂 |
| 角色枚举 | "MERCHANT"、"PICKUP_STAFF"、"CONSUMER" | RBAC 鉴权失效 |
| 枚举类业务常量 | "PICKUP"、"DELIVERY"（履约类型）| 逻辑分支漏处理 |

|------|------|

### 31.2 Seeder 通用化（零硬编码）

**旧代码（硬编码版）：**
`java
String[][] data = {{"1","veggie-greens"}, {"2","tomato-red"}, ... {"7","green-apple"}};
for (String[] row : data) {
    jdbc.update("UPDATE product SET main_image = ? WHERE id = ?", url, row[0]);
}
`

**新代码（通用版）：**
`java
// 1. 扫全表找 IS NULL 的行
jdbc.query("SELECT id FROM product WHERE main_image IS NULL OR main_image = ''",
    rs -> {
        long id = rs.getLong("id");
        // 2. 公式生成：同 id → 同 URL（picsum.photos 确定性）
        String url = "https://picsum.photos/seed/groupbuy-product-" + id + "/400/400";
        // 3. UPDATE 只改 IS NULL 的（幂等）
        jdbc.update("UPDATE product SET main_image = ? WHERE id = ? AND (main_image IS NULL OR main_image = '')", url, id);
    });
`

**设计原则：**
- ✅ 零硬编码 id / URL
- ✅ 确定性 seed（picsum.photos 同 seed 永远同一张图）
- ✅ 幂等（只改 IS NULL，已填跳过）

### 32.3 数据隔离三层 JOIN（约束 584）

**关键事实：** stock 表没有 merchant_id 列！必须三层 JOIN 确认归属：

`sql
SELECT s.*, sku.sku_name, sku.price, sku.image AS sku_image,
       p.product_name, p.main_image, p.merchant_id,
       c.category_name, com.community_name
FROM stock s
JOIN product_sku sku ON s.sku_id = sku.id AND sku.is_deleted = 0
JOIN product p       ON sku.product_id = p.id AND p.is_deleted = 0
LEFT JOIN category c ON p.category_id = c.id
LEFT JOIN community com ON s.community_id = com.id
WHERE p.merchant_id = #{当前商家}
ORDER BY s.available_qty ASC   -- 预警的排最前
`

**归属校验（每个写操作必经）：**
`sql
SELECT COUNT(1) FROM stock s
JOIN product_sku sku ON s.sku_id = sku.id
JOIN product p       ON sku.product_id = p.id
WHERE s.id = #{stockId} AND p.merchant_id = #{merchantId} AND p.is_deleted = 0
`

### 32.4 inboundAdjust SQL 三重守卫（约束 6）

`sql
UPDATE stock
SET total_qty = total_qty + #{qty},
    available_qty = available_qty + #{qty},
    version = version + 1
WHERE id = #{id} AND version = #{version}
  AND total_qty + #{qty} >= 0                              -- ① 总量不能负
  AND available_qty + #{qty} >= 0                          -- ② 可用量不能负
  AND available_qty + #{qty} >= locked_qty                 -- ③ 可用 >= 锁定
`

**约束 6 三种保护全在一条 SQL 里：**
1. **乐观锁**（version = #{version}）
2. **三重数据完整性守卫**（三个 >= 0 条件）
3. **影响行数 = 0 判定失败**（StockService.adjust 里 catch）

## v1.13 订单状态机语义重构（FULFILLING → PROCESSING）（2026-09-23）

### 33.1 问题回顾

| 问题 | 根因 |
|------|------|
| 前端显示「履约中」商家/消费者看不懂 | FULFILLING 是内部实现词，不是业务用语 |
| 商家看到「履约中」不知道该做什么 | 实际语义是「PAID 之后商家已分配履约，正在备货/发货/运输」—— 但用 FULFILLING 表达不出来 |

### 33.2 核心改动（语义对齐，逻辑不变）

设计原则：对外改 label，对内常量加 PROCESSING 替代 FULFILLING，历史数据 Flyway 迁移，零业务逻辑改动。

| 改动点 | 旧值 | 新值 |
|--------|------|------|
| OrderStatusConstant | FULFILLING 常量（主用）| PROCESSING 常量（主用）+ FULFILLING 作 Deprecated 兼容 |
| OrderStatusConstant.label() | FULFILLING → 履约中 | PROCESSING / FULFILLING → 处理中（兼容旧值）|
| OrderStatusConstant.label() | PAID → 已支付 | PAID → 待处理（暗示商家还没干活）|
| FulfillmentService | 全用 FULFILLING | 全换成 PROCESSING（5 处）|
| PaymentService | FULFILLING 出现在 cancel 守卫 | PROCESSING |

| Flyway V4 | — | UPDATE orders SET order_status=PROCESSING WHERE order_status=FULFILLING |

### 33.3 状态机完整流转（重构后）

PENDING_PAY(待支付) → PAID(待处理) → PROCESSING(处理中)

  └── 配送支线：PROCESSING → COMPLETED(已完成)

注意：自提场景 assign 时直接 PAID → PENDING_PICKUP（一步到位），不经过 PROCESSING。PROCESSING 主要用于配送场景中间态。
