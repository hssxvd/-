## 一、并发与性能类问题

### 1. 库存超卖，且测试环境测不出来

- **现象**：本地单线程测试正常，答辩演示多人同时下单时出现负库存。
- **原因**：先查后减、无锁、事务隔离级别理解错误、Redis 与 MySQL 双写不一致。
- **建议**：
  - 库存扣减必须用条件更新：`where available_qty >= #{qty}`。
  - 用 JUnit 多线程或 JMeter 做 200 并发测试，断言库存不为负。
  - Redis 预占只做加速，最终以 MySQL 条件更新为准。

### 2. 超时释放库存与支付回调并发冲突

- **现象**：用户 15 分钟刚好支付，释放任务同时把库存放了，导致“支付成功但库存没了”。
- **建议**：
  - 释放库存前先查订单状态，只有 `PENDING_PAY` 才释放。
  - 释放和支付回调都走同一把订单级锁或状态机条件更新。
  - 释放时写库存流水，记录原因。

### 3. 购物车价格与下单价格不一致

- **现象**：加入购物车时 9.9，下单时商品改价成 12.9，用户看到的价格和订单价格不一致。
- **建议**：
  - 购物车只存 SKU + 数量 + 加入时价格快照。
  - 下单时重新计算价格，并明确提示“价格已变动”。
  - 订单明细必须存下单时价格快照。

### 4. 分页查询慢，统计接口拖垮交易库

- **现象**：订单列表越翻越慢，经营分析一跑数据库 CPU 飙升。
- **建议**：
  - 高频查询字段建索引，禁止 `select *`。
  - 统计走独立汇总表或定时任务，不要实时扫订单表。
  - 分页用游标或延迟关联，避免大 offset。

### 5. 热点商品缓存击穿

- **现象**：秒杀/团购爆款，缓存过期瞬间大量请求打到数据库。
- **建议**：
  - 热点商品缓存加互斥锁或逻辑过期。
  - 库存预占用 Redis 原子操作，但最终一致性落 MySQL。

## 二、数据一致性与状态机类问题

### 6. 订单状态与支付状态不一致

- **现象**：支付成功但订单还是待支付，或订单已取消但支付流水是成功。
- **建议**：
  - 支付回调必须幂等，用支付流水号 + 订单状态双重判断。
  - 支付成功驱动订单状态变更，放在同一事务或可靠事件中。
  - 定时对账任务，扫描不一致数据并告警。

### 7. 取消订单后库存没释放

- **现象**：用户取消订单，库存没回来，商品显示售罄。
- **建议**：
  - 取消订单和库存释放必须在同一事务。
  - 库存释放写流水，记录关联订单号。
  - 定时任务扫描“已取消但库存未释放”的异常单。

### 8. 履约完成但订单没完成

- **现象**：商家点了已送达，订单状态还是履约中。
- **建议**：
  - 履约状态变更必须联动订单状态。
  - 用状态机统一驱动，禁止各模块直接 update。
  - 写状态变更日志，方便排查。

### 9. 售后通过但没退款

- **现象**：售后审核通过，支付流水没退款，用户投诉。
- **建议**：
  - 售后通过 → 退款 → 订单状态 → 库存回库，形成链路。
  - 退款必须幂等，记录退款流水。
  - 售后金额不得超过实付金额，累计退款不能超。

### 10. 商品下架后历史订单显示异常

- **现象**：商品下架或删除，历史订单详情查不到商品信息。
- **建议**：
  - 订单明细必须做商品快照。
  - 商品逻辑删除，不物理删除。
  - 下架商品仍可查看历史订单。

### 11. 逻辑删除与唯一索引冲突

- **现象**：用户删除购物车商品后再加购，唯一索引冲突。
- **建议**：
  - 唯一索引加 `is_deleted` 或使用“删除时间戳”方案。
  - 或者物理删除购物车项，订单类数据逻辑删除。

## 三、业务逻辑与边界类问题

### 12. 订单金额计算错误

- **现象**：优惠、运费、满减、退款后金额对不上。
- **建议**：
  - 金额统一 `BigDecimal`，禁止 double。
  - 金额计算集中在一个 Service，禁止多处重复计算。
  - 订单存：商品总额、优惠、运费、实付、已退款。
  - 单元测试覆盖边界：0 元、满减、部分退款。

### 13. 部分退款与多次售后

- **现象**：一个订单多次售后，累计退款超过实付。
- **建议**：
  - 记录订单累计退款金额。
  - 每次售后校验 `已退款 + 本次退款 <= 实付`。
  - 售后单关联订单明细，精确到 SKU。

### 14. 截单时间与团购批次

- **现象**：社区团购有截单时间，截单后还能下单。
- **建议**：
  - 商品/团购批次加 `deadline_time`。
  - 下单时校验当前时间 < 截单时间。
  - 截单后自动转下期或提示。

### 15. 自提点库存与总库存

- **现象**：总库存有，但用户所在社区自提点没货。
- **建议**：
  - 库存按 `sku_id + community_id/pickup_point_id` 维度管理。
  - 下单时校验对应自提点库存。
  - 跨社区调拨需单独业务，毕设可简化。

### 16. 模拟支付重复回调

- **现象**：前端重复点支付，或回调重试，订单被多次处理。
- **建议**：
  - 支付流水号唯一索引。
  - 回调处理前查支付状态，已成功直接返回。
  - 用分布式锁或数据库唯一约束防重。

### 17. 订单超时未支付

- **现象**：用户下单不付款，库存一直被占。
- **建议**：
  - 订单创建时记录 `expire_time`。
  - 定时任务扫描超时未支付订单，取消并释放库存。
  - 前端显示倒计时。

### 18. 评价与售后状态冲突

- **现象**：售后中的订单还能评价，或已评价还能售后。
- **建议**：
  - 明确规则：售后完成才能评价，或评价后限制售后时间。
  - 用状态机约束，禁止非法操作。

## 四、权限与安全类问题

### 19. 水平越权

- **现象**：消费者 A 改 orderId 看到 B 的订单。
- **建议**：
  - Service 层校验 `order.user_id == currentUserId`。
  - 商家校验 `order.merchant_id == currentMerchantId`。
  - 越权返回统一无权限，不泄露数据是否存在。

### 20. 垂直越权

- **现象**：普通用户调用管理员接口。
- **建议**：
  - 接口级权限注解 + Service 层二次校验。
  - 前端隐藏菜单只是体验，不是安全。
  - 敏感接口记录操作日志。

### 21. JWT 过期与续期

- **现象**：token 过期后用户体验差，或续期逻辑有漏洞。
- **建议**：
  - access token 短期，refresh token 长期。
  - 续期接口校验 refresh token 有效性。
  - 退出登录使 token 失效（Redis 黑名单）。

### 22. 敏感信息泄露

- **现象**：日志打印完整手机号、地址、token。
- **建议**：
  - 日志脱敏工具类统一处理。
  - 接口返回脱敏。
  - 演示数据模拟或脱敏。

### 23. 文件上传漏洞

- **现象**：商品图片上传可传可执行文件。
- **建议**：
  - 校验后缀、MIME、大小。
  - 重命名存储，禁止原名。
  - 存储路径与 Web 根隔离。

## 五、工程与架构类问题

### 24. 循环依赖

- **现象**：订单依赖库存，库存依赖订单，启动报错。
- **建议**：
  - 模块分层，用事件或中间 Service 解耦。
  - 禁止 Mapper 互相调用。
  - 定期用 ArchUnit 或人工检查依赖。

### 25. 事务失效

- **现象**：`@Transactional` 加了但没回滚。
- **原因**：自调用、异常被吞、方法非 public、rollbackFor 没指定。
- **建议**：
  - 事务方法必须 public。
  - `rollbackFor = Exception.class`。
  - 禁止在同类中自调用事务方法。

### 26. 缓存与数据库不一致

- **现象**：商品改价后缓存还是旧价。
- **建议**：
  - 更新数据库后删除缓存，而不是更新缓存。
  - 延迟双删或订阅 binlog。
  - 毕设可简化为“改价后主动清缓存”。

### 27. 定时任务重复执行

- **现象**：多实例部署，库存释放任务跑两次。
- **建议**：
  - 用 Redis 分布式锁或数据库锁。
  - 毕设单机可简化，但要有注释说明。

### 28. 接口幂等性缺失

- **现象**：重复提交订单、重复支付、重复售后。
- **建议**：
  - 前端防抖 + 后端幂等 token。
  - 业务唯一键 + 状态判断。
  - 关键接口记录请求 ID。

### 29. 异常处理不统一

- **现象**：有的返回 500，有的返回 200，前端无法统一处理。
- **建议**：
  - 全局异常处理器。
  - 统一错误码枚举。
  - 系统异常只返回 traceId。

### 30. 日志无 traceId，排查困难

- **现象**：出问题不知道哪条日志对应哪次请求。
- **建议**：
  - MDC + traceId，贯穿请求全链路。
  - 日志格式统一，包含 traceId、用户、接口。

## 六、需求预测与供应计划模块类问题

### 31. 数据泄漏

- **现象**：用未来数据构造 lag 特征，评估指标好得离谱。
- **建议**：
  - 按时间切分训练/测试。
  - lag、滑动窗口只能用历史数据。
  - 用时间滚动验证。

### 32. 稀疏销量与零销量

- **现象**：很多商品每天销量 0，MAPE 爆炸。
- **建议**：
  - 用 SMAPE 或加权 MAE。
  - 低频商品用移动平均或分类均值。
  - 分层建模：高频用树模型，低频用基线。

### 33. 冷启动

- **现象**：新品没历史数据，无法预测。
- **建议**：
  - 用同类商品、价格、社区特征。
  - 或标注“新品暂无预测”。

### 34. 预测结果被误解为确定值

- **现象**：用户以为预测就是一定会卖这么多。
- **建议**：
  - 展示预测区间。
  - 标注“仅供计划参考”。
  - 不自动扣库存、不自动定价。

### 35. 模拟数据不体现周期

- **现象**：随机生成销量，模型学不到规律。
- **建议**：
  - 模拟数据加入周末、节假日、促销、截单日。
  - 加入缺货、退货、取消等噪声。
  - 保存生成脚本，保证可复现。

### 36. 基线对比缺失

- **现象**：只报 MAE，不和简单基线比，无法说明模型有价值。
- **建议**：
  - 至少和“昨天销量”“上周同日”“近 7 天均值”比。
  - 表格展示：模型 vs 基线，MAE/RMSE/SMAPE。

### 37. 预测任务影响主流程

- **现象**：预测跑批时数据库锁表，下单卡死。
- **建议**：
  - 预测读从库或离线数据。
  - 预测结果写独立表。
  - 失败不影响交易。

### 38. 模型 MAE 比"昨天销量"还差，答辩被问

- **现象**：花了一周调 XGBoost，MAE 0.82；但"昨天销量"基线 MAE 只有 0.35，答辩被质疑模型无用。
- **原因**：复杂模型对稀疏数据过拟合，或特征噪声大于信号。
- **建议**：
  - 提前跑基线（昨天/上周同日/近 7 天均值），再选模型方向。
  - 若模型不如基线，诚实记录原因，改用更简单的移动平均或线性回归。
  - 答辩时主动承认"低频商品用基线更稳"，体现工程判断力。
  - 至少高频商品（销量前 20%）的 MAE 必须优于基线。

### 39. 供应计划 forecast_qty 与 plan_qty 差异未记录

- **现象**：供应计划表没存 adjusted_qty 和 adjust_reason，改了多少次、为什么改都说不清。
- **建议**：
  - supply_plan 必须存 forecast_qty、plan_qty、adjusted_qty、adjust_reason。
  - 每次调整写操作日志，记录 operator_id。
  - 这是答辩"供应与库存协同"必问点。

### 40. 供应到货入库与计划状态双写不一致

- **现象**：supply_plan 改了 ARRIVED，但 stock.total_qty 没加，或加了但没写 SUPPLY_IN 流水。
- **建议**：
  - 供应到货必须在同一事务完成：supply_plan→ARRIVED + stock.total_qty 增加 + stock_record（SUPPLY_IN）。
  - 定时对账任务扫描 ARRIVED 但无 SUPPLY_IN 流水的异常。

### 41. 库存预警自动创建供应计划（违反约束）

- **现象**：库存低于阈值系统自动创建供应计划发邮件，商家觉得被替他做决定了。
- **建议**：
  - 预警只做提醒（红点 + 建议补货量），不自动创建供应计划。
  - 符合约束文档 6.1 节"不自动创建供应计划"。

### 42. 供应计划取消后库存未回滚

- **现象**：供应计划 CANCELLED 但库存已加（之前已 ARRIVED），导致虚库存。
- **建议**：
  - 计划 CANCELLED 时若已到货入库，必须回滚：stock.total_qty 减少 + stock_record（ROLLBACK）。
  - 若未到货，清理预估量即可。

## 七、测试类问题

### 38. 只测正常流程

- **现象**：答辩被问异常流程，答不上来。
- **建议**：
  - 异常用例清单化：未登录、越权、库存不足、重复支付、重复售后、非法状态流转。
  - 每个异常有断言和预期错误码。

### 39. 测试数据不可复现

- **现象**：换台电脑数据对不上。
- **建议**：
  - 提供初始化 SQL 或数据工厂。
  - 测试数据模拟或脱敏。
  - 用 Testcontainers 保证环境一致。

### 40. 并发测试缺失

- **现象**：库存超卖没被发现。
- **建议**：
  - JUnit 多线程或 JMeter。
  - 断言库存不为负、订单数正确。
  - 记录并发测试报告。

### 41. 单元测试覆盖低

- **现象**：核心逻辑没测试，改一处崩三处。
- **建议**：
  - 状态机、库存、金额、权限必须有单测。
  - 覆盖率目标 ≥ 60%。

### 42. 前后端联调困难

- **现象**：接口字段对不上，状态码不统一。
- **建议**：
  - 先定 OpenAPI 文档，再并行开发。
  - Mock 数据统一。
  - 联调前先跑接口测试。

## 八、部署与环境类问题

### 43. 本地能跑，服务器跑不起来

- **现象**：JDK 版本、MySQL 版本、端口、环境变量不一致。
- **建议**：
  - Docker Compose 一键启动 MySQL、Redis、后端。
  - README 写清环境要求。
  - 配置外置，禁止硬编码。

### 44. 数据库迁移脚本冲突

- **现象**：多人开发，Flyway 版本号撞车。
- **建议**：
  - 版本号连续，提交前先拉最新。
  - 脚本只增不改。
  - CI 自动校验。

### 45. 演示环境数据被改乱

- **现象**：答辩前演示数据被误操作。
- **建议**：
  - 准备数据库快照。
  - 演示脚本固定流程。
  - 演示账号权限受限。

### 46. 前端打包后接口 404

- **现象**：开发环境正常，打包后路径不对。
- **建议**：
  - 统一 API 前缀 `/api/v1`。
  - Nginx 反向代理配置。
  - 环境变量区分 dev/prod。

### 47. 跨域问题

- **现象**：前端调后端跨域被拦。
- **建议**：
  - 开发环境后端配置 CORS。
  - 生产环境用 Nginx 同源代理。
  - 禁止 `*` + credentials 混用。

## 九、演示与答辩类问题

### 48. 演示流程不闭环

## 十一、最容易被忽略但最容易翻车的 12 个点

1. 库存超卖，且没做并发测试。
2. 支付回调不幂等，重复回调导致重复处理。
3. 订单明细没做商品快照，历史订单失真。
4. 取消订单没释放库存，或释放与支付并发冲突。
5. 售后通过没联动退款和订单状态。
6. 水平越权没校验，改 ID 就能看别人订单。
7. 预测数据泄漏，评估指标虚高。
8. 预测没和基线比，或模型比基线还差却不说明原因。
9. 日志没脱敏，打印完整手机号。
10. 演示流程不闭环，异常场景答不上来。
11. 供应计划到货与库存入库双写不一致，或没写 SUPPLY_IN 流水。
12. 特色属性存在 product_attribute 和 product_sku_attribute 边界混淆，改漏字段。

## 十二、建议的应对策略

- **先定状态机、库存策略、权限矩阵、接口文档**，再动手写代码。
- **每个核心模块写异常用例**，异常流程比正常流程更能体现能力。
- **库存、支付、售后必须幂等 + 状态校验 + 日志**。
- **供应计划到货入库必须同一事务**，SUPPLY_IN 流水与订单/支付流水同等重要。
- **特色属性边界必须先定**：product_attribute（公共）vs product_sku_attribute（SKU 固有），禁止混用。
- **预测模块独立开发、独立评估、独立展示**，不影响主流程；基线必须跑，模型差就诚实说明。
- **测试报告、ER 图、状态机图、预测评估报告**提前准备。
- **答辩冻结后（release 分支切出后）**冻结功能，只修 bug、补文档、彩排演示。

一句话总结：

> 这个毕设真正会翻车的不是页面写不出来，而是**状态不一致、库存超卖、支付不幂等、权限越权、预测评估不可信、演示不闭环**。把这六件事盯住，基本就稳了。

## 十四、实战踩坑记录（2026-09-22 后端开发）

> 以下是本次后端开发 Phase 0~9 实际遇到的问题（共 14 个坑，本次新增 #13 响应码不一致、#14 IDEA 发行版本），编号与前面风险条目不重复，每条标注"踩坑原因 → 修复方案 → 改进建议"。

### 坑 1：DDL 与 Entity 不一致 — 9 张表缺 is_deleted 列

- **现象**：应用启动后第一个查询就报 `Unknown column 'is_deleted' in 'field list'`，stock、payment、fulfillment、aftersale、forecast_task、forecast_result、forecast_metric、operation_log 等 9 张表全部命中。
- **原因**：BaseEntity 基类自带 `@TableLogic` + `is_deleted` 字段，但 V1 DDL 创建表时**没有给所有表都加 is_deleted 列**。设计文档里只给了核心表（user/product/orders）加了，关联表和日志表漏了。
- **修复**：`ALTER TABLE xxx ADD COLUMN is_deleted TINYINT NOT NULL DEFAULT 0` 逐张补上。
- **改进建议**：
  - V1 DDL 生成后，必须写一个校验 SQL：`SELECT TABLE_NAME FROM information_schema.TABLES WHERE TABLE_SCHEMA='xxx' AND TABLE_NAME NOT IN (SELECT TABLE_NAME FROM information_schema.COLUMNS WHERE COLUMN_NAME='is_deleted')`。
  - 或者 V1 DDL 里用模板统一生成：每张表结尾固定 `is_deleted TINYINT NOT NULL DEFAULT 0`。
  - **约束文档 4.1 明确要求"每张表必须有 is_deleted"**，V1 DDL 必须逐条对齐。

### 坑 2：forecast_result 唯一索引设计错误 — 不同模型预测冲突

- **现象**：V3 种子数据导入报 `Duplicate entry '1-1-2026-09-22' for key 'uk_sku_community_date'`，MA/LR/RF 三个模型对同一 SKU 同一天的预测互相冲突。
- **原因**：V1 DDL 定义 `UNIQUE KEY uk_sku_community_date (sku_id, community_id, forecast_date)`，但同一 SKU 可以被不同 task_id（不同模型）预测，唯一索引必须包含 task_id。
- **修复**：`ALTER TABLE forecast_result DROP INDEX uk_sku_community_date, ADD UNIQUE KEY uk_task_sku_community_date (task_id, sku_id, community_id, forecast_date)`。V1 DDL 和 resources/db/migration/V1 同步修正。
- **改进建议**：
  - 复合唯一索引必须覆盖**所有维度**，Forecast × SKU × 社区 × 日期 = 一个预测结果，task_id 不能丢。
  - 写 DDL 时先问自己："这张表的一条记录到底由什么唯一标识？"
  - 种子数据设计时先跑一遍唯一索引检查，避免导入时才发现。

### 坑 3：Druid WallFilter 拦截 Flyway SQL

- **现象**：Spring Boot 启动 Flyway 执行 V1 DDL 时被 WallFilter 拦截，报 SQL 语法错误，但手动执行 MySQL 正常。
- **原因**：`application.yml` 里 Druid 配了 `filters: stat,wall,slf4j`，wall filter 会对 DDL 做严格校验（禁止某些 ALTER、禁止批量 INSERT 等）。
- **修复**：改为 `filters: stat,slf4j`，去掉 wall。
- **改进建议**：
  - 毕设级项目没必要上 wall filter，增加复杂度和排障成本。
  - 如果保留，需要配置 `wall-multi-statement-allow=true` + 白名单，调试时先注释掉。
  - **快速判断**：WallFilter 报错时，SQL 本身没语法问题，是 wall 认为"危险"。

### 坑 4：Flyway 与手动导入冲突 — data 重复

- **现象**：先用 MySQL 客户端手动导入了 V1/V2/V3，再启动 Spring Boot 时 Flyway 又尝试执行一遍，V3 报主键/唯一键冲突。
- **原因**：Flyway 的设计是"要么全自动，要么全手动"，手动导入后 Flyway 的 schema_history 表为空，会认为 V1/V2/V3 没执行过。
- **修复**：两种方案：① 在 MySQL 里手动向 flyway_schema_history 插入 V1/V2/V3 记录；② 禁用 Flyway（`flyway.enabled=false`），手动导入 SQL。
- **改进建议**：
  - 毕设开发期**先手动导入**，避免 Flyway 干扰开发调试。
  - 答辩前再启用 Flyway（干净环境一键启动）。
  - 或者固定用 Flyway，**绝对不要手动导入**，两者选其一。

### 坑 5：PowerShell 管道导入 SQL 的编码坑

- **现象**：`Get-Content V1.sql | mysql.exe` 导入失败，报 `Unknown command '\P'`（BOM 头被误识别为 MySQL 命令）。
- **原因**：Windows PowerShell 默认 UTF-16 LE，管道传给 mysql.exe 时字符集不对；或文件带 UTF-8 BOM。
- **修复**：用 `[System.IO.File]::ReadAllBytes()` + `MemoryStream` 按字节读取，或用 `--default-character-set=utf8mb4`。
- **改进建议**：
  - PowerShell 下导入 SQL 最稳的方式：`Get-Content file.sql -Raw -Encoding UTF8 | mysql.exe --default-character-set=utf8mb4 ...`。
  - 或者用 MySQL Workbench / Navicat 直接执行，绕开 PowerShell。

### 坑 6：OrderController.items 为 null 时 NPE

- **现象**：调用 `POST /orders` 只传 `{"communityId":1}`（想从购物车取），报 `Cannot invoke "java.util.List.stream()" because "itemMaps" is null`。
- **原因**：OrderController 假设 body.items 永远存在，直接强转后调 stream()。
- **修复**：判空 `if (itemMaps != null && !itemMaps.isEmpty())`。
- **改进建议**：
  - Controller 层对所有 `@RequestBody Map` 的字段必须判空，不能假设前端永远按规范传。
  - **更好的做法**：用 DTO + `@NotNull` / `@NotEmpty` 注解，让 Bean Validation 自动校验。

### 坑 7：订单创建后不清空购物车 — 购物车数据残留

- **现象**：订单创建成功后购物车选中项还在，用户再次下单会重复。
- **原因**：OrderService.create() 里忘了调 `cartService.clearSelected()`。
- **修复**：在"库存预占成功"后加 `cartService.clearSelected()`。
- **改进建议**：
  - **事务原子性清单化**：每个事务方法在注释里列清楚"事务内必须完成的 1/2/3/4 步"，写完后逐条对照。
  - 订单创建的事务步骤：①校验 →②下单 →③库存预占 →④清空购物车 →⑤写日志，5 步缺一不可。

### 坑 8：ProductService.offShelf() 全表扫描性能坑

- **现象**：下架商品时 `ordersMapper.selectList(null)` 加载全表到内存，再用 stream filter 过滤未完成订单。数据量大时 OOM。
- **原因**：想简单实现"检查有没有未完成订单"，但用了 Java 内存过滤而非 SQL 子查询。
- **修复**：改用 `.inSql(orderId, "SELECT id FROM orders WHERE order_status IN (...)")`，DB 层完成过滤。
- **改进建议**：
  - **禁止 `selectList(null)` 无参查询**，必须有限制条件。
  - MyBatis-Plus 的 `inSql()` / `apply()` 是复杂查询的利器，学会用。
  - 写代码时问自己："这条 SQL 走不走索引？数据量大了会不会炸？"

### 坑 9：支付回调接口路径与前端调用不匹配

- **现象**：用 `POST /payments/callback?orderNo=xxx&payStatus=SUCCESS` 调用，报 `Request method 'POST' not supported`。
- **原因**：PaymentController 定义的是 `@PostMapping("/callback/{paymentNo}")`（路径参数），而测试用 query 参数传 orderNo。
- **修复**：先调 `POST /payments?orderId=1` 创建支付单拿到 paymentNo，再调 `POST /payments/callback/{paymentNo}`。
- **改进建议**：
  - **接口文档必须先写**，前后端按同一文档联调。
  - 支付回调的路径设计要统一：要么全路径参数，要么全 query 参数，不要混。
  - Knife4j 在开发阶段早点启用，接口一览无余。

### 坑 10：端口 8080 被占用

- **现象**：Spring Boot 启动报 `Port 8080 was already in use`。
- **原因**：上次启动的 Java 进程没关干净，或其他程序占了 8080。
- **修复**：`Get-NetTCPConnection -LocalPort 8080 | Select-Object OwningProcess | Stop-Process -Force`。
- **改进建议**：
  - 开发期端口改到 8081 或用随机端口 `server.port=0`，避免冲突。
  - 项目根目录加 `.kill-port.ps1` 一键杀端口进程。

### 坑 11：Maven spring-boot:run 参数写法错误

- **现象**：`mvn spring-boot:run -Dspring-boot.run.profiles=dev` 报 `Unknown lifecycle phase ".run.profiles=dev"`。
- **原因**：PowerShell 里 `-D` 后面的点号被解析成路径分隔符，需要加引号或用环境变量。
- **修复**：用 `$env:SPRING_PROFILES_ACTIVE="dev"; mvn spring-boot:run`。
- **改进建议**：
  - PowerShell 下所有 Maven `-D` 参数都用引号包起来：`mvn spring-boot:run "-Dspring-boot.run.profiles=dev"`。
  - 或直接用环境变量，更直观。

### 坑 12：Spring Boot 启动后 Bean 注入顺序导致 CartService NPE

- **现象**：OrderService 加了 `CartService cartService` 字段后启动成功，但第一次调用 create() 报 CartService 为 null（后来没复现，但风险存在）。
- **原因**：Spring 构造器注入循环依赖（OrderService → CartService → 可能又间接依赖 OrderService）。
- **修复**：本次没复现，但如果出现，用 `@Lazy` 延迟注入或改为 Setter 注入。
- **改进建议**：
  - **启动时检查依赖图**：`mvn dependency:tree` 或 ArchUnit 检测循环。
  - 毕设级项目用构造器注入 + `@Lazy` 兜底，简单有效。

## 十五、文档一致性补强建议

> 基于本次实战，发现三份文档有以下不一致，建议维护时关注。

### 15.1 V1 DDL 必须包含 Entity 的所有字段

- **问题**：V1 DDL 漏了 9 张表的 is_deleted，而 Entity 都继承了 BaseEntity。
- **建议**：V1 DDL 写完后，逐个对比 Entity 字段清单。写一个校验脚本：

```sql
-- 找出 DDL 里有 Entity 里没有的字段（或反过来）
SELECT '表名: ' || TABLE_NAME;
-- 逐表对比
```

### 15.2 唯一索引必须覆盖完整业务维度

- **问题**：forecast_result 的唯一索引漏了 task_id，业务上同 SKU 不同模型预测是合法的。
- **建议**：建唯一索引前，先回答"一条记录的业务唯一标识是什么"。
  - forecast_result：task_id + sku_id + community_id + forecast_date
  - order_item：order_id + sku_id（同一订单同一 SKU 可以有多行吗？）
  - stock：sku_id + community_id + pickup_point_id（pickup_point_id 为 NULL 时是社区级库存）

### 15.3 Controller 方法签名必须与前端调用契约对齐

- **问题**：PaymentController 用路径参数 `{paymentNo}`，但测试用 query 参数 `?orderNo=xxx`。
- **建议**：接口文档里必须写清楚参数位置（path/query/body），并标注示例请求/响应。

### 15.4 约束文档"每张表必须有 is_deleted"要加校验方法

- **建议**：约束文档 4.1 节补充一条：
  > V1 DDL 提交前必须执行校验 SQL，确认所有表都有 is_deleted：
  > ```sql
  > SELECT TABLE_NAME FROM information_schema.TABLES
  > WHERE TABLE_SCHEMA='community_group_buy'
  >   AND TABLE_NAME NOT IN (
  >     SELECT TABLE_NAME FROM information_schema.COLUMNS
  >     WHERE COLUMN_NAME='is_deleted'
  >   );
  > ```

### 15.5 PowerShell 环境下的开发建议

- **建议**：约束文档补充一个"Windows 开发环境快速上手"小节：
  - MySQL 导入：`Get-Content file.sql -Raw -Encoding UTF8 | mysql.exe --default-character-set=utf8mb4`
  - Maven profile：用 `$env:SPRING_PROFILES_ACTIVE="dev"` 而非 `-D` 参数
  - 端口占用：`Get-NetTCPConnection -LocalPort 8080 | % { Stop-Process -Id $_.OwningProcess -Force }`
  - 进程杀不掉：`taskkill /F /PID <pid>`
### 坑 13：前后端响应成功码不一致 — 前端 code !== 200 vs 后端 code:0

- **现象**：前端登录按钮点了弹"请求失败"，后端日志显示 HTTP 200 + code:0 + data:{token:...} 完全正常，curl 命令行也能拿到正确 token。
- **根因**：后端 ErrorCode.SUCCESS 定义为  （约束文档 7.1 已明确），但前端 equest.js 拦截器写了 if (res.code !== 200)，**把业务成功误判为失败**。这是典型的"接口契约没对齐"。
- **修复**：前端拦截器改为 if (res.code !== 0)（一行改动）。
- **改进建议**：
  - 接口契约必须写成代码：约束文档已定义成功码=0，前端脚手架直接按约束写，不要自己猜。
  - 加前端 smoke test：调 /auth/login 断言 es.code === 0。
  - 三端共享 request.js，一处改全部生效。

### 坑 14：IDEA 不读 Spring Boot parent 的 java.version 推导 — 报"不支持发行版本 5"

- **现象**：IDEA 打开项目后构建报错 java: 错误: 不支持发行版本 5，但命令行 mvn compile 正常。
- **根因**：pom.xml 只写了 <java.version>17</java.version>，依赖 Spring Boot parent 推导 compiler source/target，但 **IDEA 不读这个推导值**，自己默认最低发行版本 5。
- **修复**：pom.xml 显式声明 maven-compiler-plugin，source/target/release 都设 17；IDEA 里 Project SDK 也设 17。
- **改进建议**：
  - pom.xml 必须显式声明 maven-compiler-plugin，不能只靠 java.version 属性。
  - IDEA 打开项目后必须手动检查：Project SDK → 17 / Language level → 17。
  - 详见约束文档 22.6。

### 坑 15：Spring @GetMapping("/{id}") 贪婪匹配吞掉字符串路径

- **现象**：前端调 /products/filterable-attr-keys 和 /products/search，后端报 NumberFormatException: For input string: "filterable-attrs"。后端日志显示 Spring 把 /filterable-attr-keys 当成了 /{id} 的路径变量，尝试转 Long 失败。
- **根因**：@GetMapping("/{id}") 是贪婪匹配，会匹配所有单段路径（除了被子路径抢先匹配的）。/filterable-attr-keys、/attr-dict 这些单词路径全部被 /{id} 吞掉。另外前端 api/index.js 的路径也写错了（后端没有 /search 端点、/filterable-attrs vs 后端 /filterable-attr-keys 不匹配）。
- **修复**：
  1. 后端所有裸 /{id} 加正则限制：@GetMapping("/{id:\\d+}")（注意 Java 字符串里必须双反斜杠 \\d）
  2. 前端 API 路径修正：/search → /（用 query params）、/filterable-attrs → /filterable-attr-keys
  3. 扫一遍所有 Controller，确保 /{id} 只有数字能匹配
- **改进建议**：
  - 所有 Controller 的 /{id} 必须加 :\\d+ 正则，禁止裸 /{id}。
  - 定义统一路径前缀规范：查询类用 /search、字典类用 /dict，避免用单词做路径变量。
  - 详见约束文档 7.2。
