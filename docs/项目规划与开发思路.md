# 社区团购电商系统 项目规划与开发思路

> 版本：v1.0  
> 配套文档：《约束文档》《数据库设计文档》《项目开发风险规避文档》《sql/V1~V3 SQL 脚本》  
> 核心原则：**每次开发前先读文档，按文档规避风险和冲突**  
> 开发节奏：按业务闭环分阶段，每阶段交付可运行可演示的最小增量

## 一、总体开发路线图

```text
Phase 0 ── 环境与基础设施 ── 搭建脚手架 + 执行 V1~V3 SQL + 统一响应/异常/日志
  │
Phase 1 ── 认证与权限 ── RBAC 完整实现 + 数据隔离拦截器
  │
Phase 2 ── 商品中心 ── 分类/商品/SKU/特色属性 + 上下架状态机 + 分类检索
  │
Phase 3 ── 供应与库存 ── 供应计划/库存/库存流水 + 条件更新防超卖 + SUPPLY_IN 事务
  │
Phase 4 ── 购物车与订单 ── 购物车 + 订单创建 + 订单状态机 + 特色属性快照
  │
Phase 5 ── 模拟支付 ── 支付流水 + 幂等回调 + 预占转实扣 + 超时释放并发
  │
Phase 6 ── 履约与售后 ── 履约状态机 + 售后状态机 + 退款联动 + 库存回库
  │
Phase 7 ── 评价与经营分析 ── 评价 CRUD + 商家/社区隔离的统计接口
  │
Phase 8 ── 需求预测 ── 历史数据生成 + MA/LR/RF 模型 + MAE/RMSE/SMAPE vs 基线
  │
Phase 9 ── 前端三端 ── 消费者端(移动优先) + 商家端 + 管理端 + 个性化展示
  │
Phase 10 ── 测试与演示 ── 并发/状态机/异常流程 + 彩排演示 + 答辩
```

**阶段依赖关系**：Phase 0→1→2→3→4→5→6 是强制串行（前一阶段是后一阶段的地基）；Phase 7 可与 5/6 并行；Phase 8 依赖 Phase 3 的库存和 Phase 6 的历史订单数据；Phase 9 依赖后端接口，但可与后端并行（Mock）。

### 开发目标

搭建可运行的 Spring Boot + Vue 3 工程，执行 V1~V3 SQL，统一响应体、异常处理、日志规范。

### 必读清单

| 序号 | 文档 | 必读章节 |
|---|---|---|
| 0-1 | 约束文档 | 1. 技术栈与版本约束 |
| 0-2 | 约束文档 | 2. 项目结构与分层约束 |
| 0-3 | 约束文档 | 7. 接口设计约束（7.1 统一响应） |
| 0-4 | 约束文档 | 9. 参数校验与异常处理约束 |
| 0-5 | 约束文档 | 10. 日志与审计约束 |
| 0-6 | 数据库设计文档 | 20. Flyway 迁移规范 |
| 0-7 | 风险规避文档 | 5. 工程与架构类问题 |

### 开发步骤

```text
1. 后端脚手架
   ├─ Spring Boot 2.7+ + MyBatis-Plus + MySQL 8 + Redis + Flyway + JWT
   ├─ 包结构：com.project.groupbuy
   │   ├─ controller / service / mapper / entity / dto / vo
   │   ├─ config / common / exception / util / security / aspect
   │   └─ modules  (按业务分模块)
   ├─ 统一响应体 R<T>：code + message + data + traceId
   ├─ 全局异常处理器 GlobalExceptionHandler
   │   ├─ BusinessException → 业务错误码
   │   ├─ MethodArgumentNotValidException → 参数校验
   │   ├─ AccessDeniedException → 权限
   │   └─ Exception → 系统异常（只返回 traceId）
   └─ Logback 配置：脱敏 pattern + 异步 appender

2. 数据库初始化
   ├─ 执行 V1__init_schema.sql（30 张表 DDL）
   ├─ 执行 V2__init_rbac_data.sql（角色 + 权限 + 用户 + 社区 + 分类）
   ├─ 执行 V3__init_business_data.sql（商品 + SKU + 属性 + 库存 + 供应计划 + 预测）
   └─ 验证：SHOW TABLES → 30 张；SELECT COUNT(*) FROM role_permission → 136+ 条权限分配

3. 前端脚手架
   ├─ Vue 3 + Vite + Element Plus + Pinia + Vue Router + Axios
   ├─ 目录：api / assets / components / views / stores / router / utils
   ├─ 三端骨架：consumer/（移动优先）、merchant/、admin/
   ├─ Axios 拦截器：token 注入 + 401 跳转 + 统一错误提示
   └─ 路由守卫：未登录跳转 + 角色路由权限

4. 基础设施验证
   ├─ 健康检查接口 GET /actuator/health → UP
   ├─ 统一响应体测试：GET /api/health → {"code":0,"message":"success","data":null,"traceId":"xxx"}
   ├─ 异常处理器测试：GET /api/bad → 业务异常返回码
   └─ 日志测试：SLF4J 打印，检查手机号是否脱敏
```

### 风险规避

| 风险 | 来源 | 规避 |
|---|---|---|
| Flyway V1~V3 已执行后被修改 | 约束文档 25 | 永远不要改已执行的 V1~V3，改就加 V4+ |
| 中文 COMMENT 导致 MySQL 1064 | 风险文档 #28 | V1 已用 utf8mb4 + SET NAMES utf8mb4 开头，PowerShell 导入用 mysql -u root -p --default-character-set=utf8mb4 < file.sql |
| 统一响应体不统一 | 约束文档 7.1 | 强制所有 Controller 返回 R\<T\>，禁止 Map 或 Object |
| 系统异常堆栈泄露 | 约束文档 9 | GlobalExceptionHandler 对 Exception 只返回 traceId，error_msg 字段不返回 |

### 交付标准

- [ ] 后端启动成功，Flyway 自动执行 V1~V3
- [ ] 30 张表全部建好，种子数据完整
- [ ] 健康检查、异常处理、日志脱敏正常
- [ ] 前端三端骨架可访问，路由守卫正常

## 四、Phase 1：认证与权限

### 开发目标

JWT 登录 + RBAC 权限校验 + 数据范围隔离。

### 必读清单

| 序号 | 文档 | 必读章节 |
|---|---|---|
| 1-1 | 约束文档 | 8. 认证授权与数据隔离约束 |
| 1-2 | 约束文档 | 14. 数据合规与脱敏约束 |
| 1-3 | 数据库设计文档 | 四、用户与权限模块（表 1~6） |
| 1-4 | 风险规避文档 | 4. 权限与安全类问题 |

### 开发步骤

```text
1. JWT 认证
   ├─ JwtUtil：生成/解析 token，有效期 2 小时，用户类型 + userId 写入 claims
   ├─ JwtAuthInterceptor：拦截器，解析 token → 存入 SecurityContext
   ├─ 登录接口 POST /api/auth/login：BCrypt 校验 → 返回 token
   ├─ 注册接口 POST /api/auth/register：消费者自助注册
   └─ 密码加密：BCryptPasswordEncoder，强度 10

2. RBAC 权限校验
   ├─ @RequiresPermission 自定义注解：如 @RequiresPermission("product:add")
   ├─ PermissionAspect：AOP 切面，从 SecurityContext 取当前用户 → 查 role_permission → 比对
   ├─ 权限缓存：Redis 缓存用户权限列表（key=perm:user:{userId}，TTL=30min）
   └─ 权限变更时清理缓存

3. 数据范围隔离（Service 层硬校验，禁止只靠前端）
   ├─ 消费者：所有查询/操作强制 WHERE user_id = 当前用户
   ├─ 商家：所有查询/操作强制 WHERE merchant_id = 当前商家
   ├─ 管理员：可全局，但敏感操作（删除用户、角色变更）需操作日志
   └─ 实现：抽象 BaseEntityService，子类注入 communityId/merchantId 过滤条件

4. 操作日志 AOP
   ├─ @OpLog 注解：标记需要记录的方法
   ├─ OpLogAspect：记录操作人、角色、模块、操作类型、对象 ID、前后状态
   └─ 脱敏：手机号 138****0001，token 只保留前 8 位

5. 前端权限控制
   ├─ pinia 存用户信息 + 权限列表 + 角色
   ├─ 动态路由：根据权限动态注册菜单
   ├─ 按钮级：v-permission="'product:add'" 指令
   └─ 敏感数据脱敏展示：手机号、地址
```

### 风险规避

| 风险 | 来源 | 规避 |
|---|---|---|
| 水平越权：改 ID 看别人订单 | 约束文档 8 | Service 层硬校验 user_id = 当前用户，前端隐藏 + 后端校验双保险 |
| 垂直越权：消费者调商家接口 | 约束文档 8 | PermissionAspect 比对 role_permission，越权返回 403 |
| 密码明文存储 | 约束文档 8 | BCrypt，禁止 MD5/SHA1 |
| 权限缓存不一致 | 风险文档 #4 | 权限变更时主动删 Redis 缓存，或 TTL 设短（30min） |
| 操作日志未脱敏 | 约束文档 10 | OpLogAspect 统一脱敏，手机号用正则替换中间 4 位 |

### 交付标准

- [ ] consumer01/merchant01/admin01/superadmin 登录成功
- [ ] 消费者无法访问商家接口（403）
- [ ] 消费者无法通过改 user_id 查询别人订单（空结果或 403）
- [ ] 商家只能看到自己的商品，看不到 merchant02 的
- [ ] 敏感操作（登录/权限变更）有 operation_log 记录

### 开发目标

分类树 + 商品 CRUD + SKU CRUD + 特色属性 CRUD + 上下架状态机 + 分类检索（按特色属性筛选）。

### 必读清单

| 序号 | 文档 | 必读章节 |
|---|---|---|
| 2-1 | 约束文档 | 4.5 特色属性约束 |
| 2-2 | 约束文档 | 5.1 商品状态 |

| 2-4 | 数据库设计文档 | 六、商品模块（表 9~13） |

| 2-6 | 风险规避文档 | 3. 业务逻辑与边界类问题 |

### 开发步骤

```text
1. 分类树
   ├─ GET /api/category/tree：返回父子结构
   ├─ 新增/编辑/删除：商家不可操作分类，只有管理员可
   └─ 删除校验：有子分类或关联商品时禁止删除

2. 商品 CRUD
   ├─ POST /api/products：商家建档 → 初始状态 DRAFT
   ├─ PUT /api/products/{id}：编辑，仅 DRAFT/OFF_SHELF 可编辑
   ├─ DELETE /api/products/{id}：逻辑删除
   ├─ PUT /api/products/{id}/shelf：上架 → ON_SHELF（校验所有 SKU 有库存）
   ├─ PUT /api/products/{id}/off-shelf：下架 → OFF_SHELF（校验无未完成订单）
   └─ 商品状态机：DRAFT → ON_SHELF → OFF_SHELF → ON_SHELF / ON_SHELF → SOLD_OUT

3. SKU CRUD
   ├─ POST /api/products/{productId}/skus
   ├─ PUT /api/skus/{id}
   ├─ SKU 固有属性（product_sku_attribute）：定义 SKU 差异的维度
   │   例：sku1 属性=规格:500g/把，sku2 属性=规格:1kg/捆
   └─ SKU 固有属性 ≠ 商品特色属性，禁止混用

4. 特色属性 CRUD（核心！课题要求）
   ├─ POST /api/products/{productId}/attributes
   ├─ attr_key 预定义字典：产地/品牌/保质期/规格/重量/适用人群/特色标签
   ├─ 商品详情页高亮：is_highlight=1 的属性突出显示
   ├─ 分类检索筛选：is_filterable=1 的属性生成筛选器
   │   例：按产地筛选 → WHERE product_attribute.attr_key='产地' AND attr_value IN ('崇明岛','山东烟台')
   └─ 特色属性与 SKU 固有属性边界：
       product_attribute    → 公共特色属性（同 SKU 变体共享，服务检索/展示/快照）
       product_sku_attribute → SKU 固有属性（定义 SKU 差异，服务规格选择）

5. 分类检索接口
   ├─ GET /api/products：
   │   ├─ 必选：communityId（当前社区）
   │   ├─ 可选：categoryId（分类）、keyword（关键词）
   │   ├─ 可选：attrFilters（特色属性筛选，JSON：[{"key":"产地","value":"崇明岛"}]）
   │   ├─ 可选：priceMin/priceMax（价格区间）
   │   ├─ 可选：sortBy（综合/sales/priceAsc/priceDesc/createTime）
   │   └─ 分页：pageNum/pageSize
   ├─ 索引必须覆盖：category_id + community_id + status + attr_key + attr_value
   └─ 禁止 select *，必须按需返回字段

6. 商品快照准备
   └─ 商品改价/改名/改属性后，历史订单不受影响（order_item 存了快照）
```

### 风险规避

| 风险 | 来源 | 规避 |
|---|---|---|
| product_attribute 与 product_sku_attribute 混用 | 约束文档 4.5 / 风险文档 #12 | 开发前先画边界图：公共属性→product_attribute，SKU 差异维度→product_sku_attribute |
| 商品表冗余 origin/shelf_life/tags | 数据库设计文档 v1 | V1 DDL 已删除这些字段，特色属性统一走 product_attribute |
| 下架时校验不足 | 约束文档 5.1 | 下架前查 orders WHERE product_id=? AND order_status NOT IN (COMPLETED,CANCELLED,REFUNDED)，有则禁止下架 |
| 分类检索性能差 | 约束文档 11 | attr_key + attr_value 必须有联合索引，筛选走 INNER JOIN product_attribute |
| 特色属性字典随意新增 | 约束文档 4.5 | attr_key 用枚举或常量类维护，数据库 CHECK 约束或应用层校验 |

- [ ] 商家可登录后看到自己的商品
- [ ] 商品详情页展示高亮特色属性（如「产地：崇明岛」「特色标签：有机」）

## 六、Phase 3：供应与库存

### 开发目标

库存条件更新防超卖 + 供应计划（关联预测）+ 供应到货三动作事务 + SUPPLY_IN 流水。

### 必读清单

| 序号 | 文档 | 必读章节 |
|---|---|---|
| 3-1 | 约束文档 | 6. 库存与并发约束 |
| 3-2 | 约束文档 | 6.1 供应与库存协同约束 |
| 3-3 | 约束文档 | 4.4 库存表约束 |
| 3-4 | 数据库设计文档 | 七、库存模块（表 14~16） |
| 3-5 | 数据库设计文档 | 17. 索引与约束汇总 |
| 3-6 | 风险规避文档 | 1. 并发与性能类问题 + 6. 供应计划类问题 |

### 开发步骤

```text
1. 库存条件更新（防超卖核心）
   ├─ 预占（下单时）：
   │   UPDATE stock SET locked_qty = locked_qty + #{qty}, version = version + 1
   │   WHERE sku_id = #{skuId} AND community_id = #{cId}
   │     AND available_qty >= #{qty} AND version = #{version}
   │   影响行数 = 0 → 抛 BusinessException("库存不足")
   ├─ 实扣（支付后）：
   │   UPDATE stock SET locked_qty = locked_qty - #{qty},
   │                    total_qty = total_qty - #{qty}, version = version + 1
   │   WHERE id = #{stockId} AND locked_qty >= #{qty}
   ├─ 释放（取消/超时）：
   │   UPDATE stock SET locked_qty = locked_qty - #{qty}, version = version + 1
   │   WHERE id = #{stockId} AND locked_qty >= #{qty}
   └─ 每次变更必须写 stock_record（change_type 六枚举）

2. 库存流水 stock_record
   ├─ 六种变更类型：LOCK(预占) / UNLOCK(释放) / DEDUCT(实扣) / ROLLBACK(回滚)
   │                / INBOUND(人工入库) / SUPPLY_IN(供应到货入库)
   ├─ 所有 stock 变更操作必须写流水，流水不得异步（事务内完成）
   └─ 流水字段：before_total/after_total/before_locked/after_locked

3. 供应计划（课题核心功能）
   ├─ POST /api/supply-plans：创建计划，forecast_qty 从 forecast_result 取
   │   商家可调整 plan_qty，调整后写 adjusted_qty + adjust_reason + operator_id
   ├─ PUT /api/supply-plans/{id}/confirm：确认计划
   ├─ PUT /api/supply-plans/{id}/arrive：标记到货 → ⚠️ 三动作事务
   │   BEGIN:
   │     ① UPDATE supply_plan SET status='ARRIVED', arrive_time=NOW()
   │     ② UPDATE stock SET total_qty = total_qty + #{qty}
   │     ③ INSERT stock_record(change_type='SUPPLY_IN', ...)
   │   COMMIT;
   ├─ PUT /api/supply-plans/{id}/cancel：取消计划
   │   如果已 ARRIVED 需先回滚库存：total_qty 减少 + ROLLBACK 流水
   └─ 库存预警：available_qty < warn_qty 时生成供应建议（参考预测 + 当前库存）
       → 只做提醒，不自动创建供应计划

4. 库存超时释放定时任务
   ├─ Scheduled 每 5 分钟扫描：orders WHERE order_status='PENDING_PAY' AND expire_time < NOW()
   ├─ 释放逻辑：
   │   ① 查订单状态，确认还是 PENDING_PAY（防止与支付并发）
   │   ② UPDATE orders SET order_status='CANCELLED', cancel_reason='超时未支付'
   │   ③ 释放预占：stock.locked_qty -= qty + UNLOCK 流水
   │   ④ 写 order_status_log + operation_log
   └─ 关键：释放前必须再次查订单状态，只有 PENDING_PAY 才释放
```

### 风险规避

| 风险 | 来源 | 规避 |
|---|---|---|

## 七、Phase 4：购物车与订单

### 开发目标

购物车 + 订单创建（特色属性快照）+ 订单状态机 + 超时释放。

### 必读清单

| 序号 | 文档 | 必读章节 |
|---|---|---|
| 4-1 | 约束文档 | 4.3 订单快照约束 |
| 4-2 | 约束文档 | 5.2 订单状态 |
| 4-3 | 数据库设计文档 | 八、购物车 + 九、订单模块（表 17~20） |
| 4-4 | 风险规避文档 | 2. 数据一致性与状态机类问题 |

### 开发步骤

```text
1. 购物车
   ├─ POST /api/cart/items：加入购物车
   │   ├─ 存 sku_id + quantity + price_snapshot（加入时价格快照）
   │   └─ 校验库存：available_qty >= quantity
   ├─ PUT /api/cart/items/{id}：修改数量
   ├─ DELETE /api/cart/items/{id}：删除
   ├─ GET /api/cart/items：列表，按 user_id 隔离
   └─ 下单时重新查最新价格并提示"价格已变动"

2. 订单创建（核心！业务闭环起点）
   ├─ POST /api/orders：从购物车选中项下单
   │   BEGIN:
   │     ① 校验购物车选中项 → 重新查 SKU 最新价格
   │     ② 校验所有 SKU 在目标社区有库存（available_qty >= 数量）
   │     ③ 创建 orders（order_no=雪花算法，expire_time=当前+15min，status=PENDING_PAY）
   │     ④ 创建 order_item：每个购物车项一条
   │        存 product_name/sku_name/spec/price/quantity/subtotal → 商品快照
   │        存 attr_snapshot → 特色属性快照 JSON（从 product_attribute 拷贝 is_highlight=1 的项）
   │     ⑤ 扣减库存（预占）：stock.locked_qty += quantity + LOCK 流水
   │     ⑥ 清空购物车选中项
   │     ⑦ 写 order_status_log（from=NULL, to=PENDING_PAY）
   │   COMMIT;
   └─ 下单原子性：任一环节失败全部回滚

3. 订单状态机
   ├─ 状态流转规则（约束文档 5.2）：
   │   PENDING_CONFIRM → PENDING_PAY → PAID → FULFILLING → COMPLETED
   │   PENDING_PAY → CANCELLED
   │   PAID → REFUNDING → REFUNDED / CANCELLED
   │   COMPLETED → AFTERSALE → COMPLETED
   ├─ 实现：OrderStateMachine 统一状态机方法
   │   transition(order, targetStatus, operator, reason)
   │     → 校验 fromStatus → 更新 orders → 写 order_status_log
   ├─ 禁止直接 UPDATE orders SET order_status=...
   └─ 非法流转抛 BusinessException("订单已支付，无法取消")

4. 订单取消
   ├─ 用户主动取消 / 商家拒绝：
   │   ① 校验订单状态仍为 PENDING_PAY
   │   ② 更新订单状态为 CANCELLED
   │   ③ 释放库存：stock.locked_qty -= qty + UNLOCK 流水
   │   ④ 写 order_status_log + operation_log
   └─ 超时自动取消（Phase 3 定时任务已实现）
```

### 风险规避

| 风险 | 来源 | 规避 |
|---|---|---|
| 特色属性未进订单快照 | 约束文档 4.3 / 数据库文档 order_item.attr_snapshot | 下单时必须从 product_attribute 拷贝到 attr_snapshot JSON |
| 订单创建原子性被破坏 | 风险文档 #1 | 所有步骤在同一 @Transactional 内 |
| 直接 update 订单状态 | 约束文档 5.2 | 只能走 OrderStateMachine.transition()，代码 review 把关 |
| 先查后减库存 | 约束文档 6 | 下单时先校验后条件更新，两步都在事务内 |
| 购物车价格与下单不一致 | 风险文档 #3 | price_snapshot 存加入时价格，下单时重新查并提示差异 |

### 交付标准

- [ ] 完整下单流程：浏览→加购→选中→下单→订单创建→库存预占
- [ ] 订单详情页特色属性展示从 attr_snapshot 读（改商品属性后订单不变）
- [ ] 非法流转拦截：已支付订单无法取消
- [ ] 超时订单 15 分钟后自动取消并释放库存

## 八、Phase 5：模拟支付

### 开发目标

模拟支付 + 幂等回调 + 预占转实扣 + 超时释放并发安全。

### 必读清单

| 序号 | 文档 | 必读章节 |
|---|---|---|
| 5-1 | 约束文档 | 5.3 支付状态 |
| 5-2 | 数据库设计文档 | 十、支付模块（表 21~22） |
| 5-3 | 风险规避文档 | 2. 数据一致性类 + 风险文档 #2 #4 |

### 开发步骤

```text
1. 模拟支付接口
   ├─ POST /api/payments/mock：发起模拟支付
   │   ① 创建 payment（payment_no=雪花，pay_status=PENDING）
   │   ② 返回 payment_no + 模拟支付页面跳转 URL
   │   └─ 同时启动延时回调（模拟用户支付成功，1~3 秒后触发）
   ├─ POST /api/payments/{paymentNo}/callback：模拟支付回调
   │   BEGIN:
   │     ① 幂等校验：SELECT * FROM payment WHERE payment_no=? FOR UPDATE
   │        → 已是 SUCCESS/REFUNDED → 直接返回，不重复处理
   │     ② 更新 payment.pay_status = SUCCESS
   │     ③ 更新 orders.order_status = PAID（订单状态机）
   │     ④ 预占转实扣：
   │        stock.locked_qty -= qty, total_qty -= qty
   │        + DEDUCT 流水
   │     ⑤ 写 order_status_log（PENDING_PAY → PAID）
   │     ⑥ 写 operation_log
   │   COMMIT;
   └─ 回调失败重试：最多 3 次，每次间隔 5s，最终失败写 payment_callback_log

2. 退款接口
   ├─ POST /api/payments/{paymentNo}/refund：退款
   │   ① 校验 pay_status = SUCCESS 且未全额退款
   │   ② 校验退款金额 <= pay_amount - refunded_amount
   │   ③ 校验关联售后已审核通过（REFUNDING 状态）
   │   ④ 更新 payment.pay_status = REFUNDING → REFUNDED
   │   ⑤ 同步更新订单状态
   │   └─ 库存回库（如需退货）：stock.total_qty += qty + INBOUND 流水
   └─ 退款回调同样要幂等

3. 超时释放 vs 支付并发安全
   ├─ Phase 3 定时任务释放前二次校验订单状态
   ├─ 支付回调处理前二次校验订单状态
   ├─ 极端情况：释放和回调同时进来
   │   → 释放拿到锁（或状态校验 PENDING_PAY）→ 释放后回调再进来
   │   → 回调拿到锁（或状态校验 PENDING_PAY）→ 回调后释放再进来（校验非 PENDING_PAY → 跳过）
   └─ 用订单状态 + FOR UPDATE 行锁保证只有一个成功
```

### 风险规避

| 风险 | 来源 | 规避 |
|---|---|---|
| 回调不幂等 | 约束文档 5.3 / 风险文档 #4 | 先 SELECT FOR UPDATE 查状态，已是 SUCCESS 直接返回 |
| 释放与回调并发 | 风险文档 #2 | 释放和回调都校验订单状态，只有 PENDING_PAY 才处理 |
| 退款超实付 | 约束文档 5.5 / V1 DDL CHECK 约束 | CHECK (refunded_amount <= pay_amount) + 应用层双重校验 |
| 支付成功但订单状态没更新 | 约束文档 5.3 | 同一事务内更新 payment + orders，或用可靠事件 |

### 交付标准

- [ ] 模拟支付完整流程：下单→支付→回调→订单变 PAID→库存预占转实扣
- [ ] 同一支付回调重复触发，只处理一次（幂等）
- [ ] 并发场景：释放和回调同时进来，只有一个成功
- [ ] 退款正常联动订单状态


## 十三、Phase 10：测试与答辩

### 开发目标

并发测试 + 状态机测试 + 异常流程测试 + 答辩准备。

### 必读清单

| 序号 | 文档 | 必读章节 |
|---|---|---|
| 10-1 | 约束文档 | 13. 测试约束 |
| 10-2 | 约束文档 | 18. 答辩前自检清单 |
| 10-3 | 风险规避文档 | 7. 测试类 + 9. 演示与答辩类 |

### 测试清单

```text
1. 并发测试
   ├─ JUnit 多线程模拟 200 并发下单 → 断言库存 >= 0
   ├─ 断言：所有订单创建成功 OR 库存不足失败，无部分成功

2. 状态机测试（每一条流转都要有测试用例）
   ├─ 订单：PENDING_PAY → CANCELLED / PENDING_PAY → PAID / PAID → REFUNDING ...
   ├─ 非法流转：已支付订单 → 取消 → 断言抛异常
   ├─ 支付：PENDING → SUCCESS / PENDING → TIMEOUT / SUCCESS → REFUNDED
   └─ 履约/售后同理

3. 异常流程测试（比正常流程更重要）
   ├─ 库存不足时下单 → 失败 + 不扣库存
   ├─ 支付回调重复 → 幂等只处理一次
   ├─ 释放与支付并发 → 只有一个成功
   ├─ 退款超实付 → 拦截
   ├─ 越权访问 → 403 或空结果
   └─ 预测模型不如基线 → 有记录有说明

4. 业务闭环演示测试
   └─ 消费者登录 → 浏览 → 加购 → 下单 → 模拟支付 → 自提 → 评价 → 售后
      商家侧同步：商品 → 订单 → 库存 → 供应计划 → 经营分析
      管理员侧同步：审核 → 日志 → 全局统计 → 预测
```

### 答辩准备

```text
1. 材料清单
   ├─ ER 图（数据库设计文档附录）
   ├─ 状态机图（约束文档第 5 章）
   ├─ 权限矩阵（约束文档第 8 章 + 角色权限）
   ├─ 预测评估报告（forecast_metric + 基线对比）
   ├─ 测试报告（并发测试 + 状态机测试 + 异常流程）
   ├─ 演示数据 SQL 脚本（V2 + V3）
   └─ 核心代码片段（库存条件更新、状态机、幂等回调）

2. 演示彩排（至少 3 遍）
   ├─ 预演完整业务闭环，计时不超 5 分钟
   ├─ 预演异常场景：库存不足、支付超时、售后申请
   └─ 预判老师提问点（风险文档 #11 12 个翻车点）

3. 冻结后只修 bug（约束文档 26.4）
   └─ release/* 分支切出后不再加功能
```
