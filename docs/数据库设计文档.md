## 一、设计原则

1. **业务闭环驱动**：每张表对应业务闭环中的环节。
2. **状态机为核心**：订单、支付、履约、售后独立状态 + 日志表。
3. **快照保历史**：订单明细冗余商品信息。
4. **流水保审计**：库存、支付、履约、售后均有流水/日志。
5. **条件更新防超卖**：库存扣减用 `where available_qty >= qty`。
6. **逻辑删除**：商品、订单类数据不物理删除。
7. **幂等设计**：业务唯一键 + 状态判断。
8. **数据隔离**：消费者、商家、管理员数据范围在表结构可区分。
9. **金额精度**：`decimal(12,2)` + `BigDecimal`。
10. **版本化演进**：DDL 走 Flyway，字段只增不删。

## 二、ER 关系总览

```text
user ──< user_role >── role ──< role_permission >── permission
  │
  ├──< cart_item >── product_sku
  │
  ├──< orders ──< order_item >── product_sku
  │       │
  │       ├──< payment
  │       ├──< fulfillment
  │       ├──< aftersale
  │       ├──< review
  │       └──< order_status_log
  │
  └──< operation_log

community ──< pickup_point
    │
    └──< stock >── product_sku

category ──< product ──< product_sku
                │
                └──< product_attribute

product_sku ──< stock_record
orders ──< stock_record

forecast_task ──< forecast_result
forecast_task ──< forecast_metric

supply_plan ── product_sku
supply_plan ── community
supply_plan ──< stock_record
```

核心关系：

- 一个用户可有多个角色，一个角色可有多个权限。
- 一个商品可有多个 SKU，一个 SKU 在多个社区有独立库存。
- 一个用户一个 SKU 在购物车中唯一。
- 一个订单有多个订单明细，每个明细对应一个 SKU。
- 一个订单可有多次支付尝试，但只有一次成功支付。
- 一个订单对应一次或多次履约。
- 一个订单可有多次售后。
- 一个订单明细可有一条评价。

## 三、通用字段规范

所有业务表默认包含以下字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint | 主键，雪花 ID 或自增 |
| create_time | datetime | 创建时间，默认 CURRENT_TIMESTAMP |
| update_time | datetime | 更新时间，ON UPDATE CURRENT_TIMESTAMP |
| is_deleted | tinyint | 逻辑删除，0 未删除，1 已删除 |

约定：

- 金额：`decimal(12,2)`。
- 数量：`int`。
- 状态：`varchar(32)`，存枚举名。
- 时间：`datetime`，应用层用 `LocalDateTime`。
- 布尔：`tinyint`，0/1。
- 主键：`bigint`，禁止用业务字段作主键。
- 业务编号：单独字段 + 唯一索引，如 `order_no`、`payment_no`。

## 十八、关键设计说明

### 18.1 为什么订单明细要快照

商品会改价、改名、下架、删除。如果订单明细只存 `sku_id`，历史订单会随商品变化而变化，用户看到的订单和当时下单不一致。快照字段包括：商品名、SKU 名、规格、图片、分类、单价。

### 18.2 为什么库存按社区维度

社区团购通常按社区/自提点备货。总库存有货，不代表用户所在社区有货。因此库存表用 `sku_id + community_id` 唯一索引，保证每个社区独立库存。

### 18.3 为什么库存要流水

库存变更可能来自下单预占、支付扣减、取消释放、售后回库、人工调整。只有流水表才能对账、排查、追责。流水记录变更前后值、关联订单号、操作人。

### 18.4 为什么支付要幂等

模拟支付可能重复回调，用户可能重复点支付。支付表用 `payment_no` 唯一索引，回调处理前查状态，已成功直接返回，避免重复处理。

### 18.5 为什么状态变更要日志

订单、支付、履约、售后状态联动复杂。状态日志表记录前状态、后状态、操作人、原因、时间，方便排查不一致。

### 18.6 为什么预测独立表

预测是计划辅助，不是交易数据。独立表可以避免预测跑批影响交易，也方便展示模型版本、指标、区间。预测结果只读，不自动扣库存、不自动定价。

### 18.7 为什么用逻辑删除

商品、订单、售后等数据有历史价值，物理删除会破坏关联。逻辑删除 + 查询默认过滤，既保留历史，又不影响业务。

### 18.8 为什么金额用 decimal

`double`/`float` 有精度问题，金额计算会出现 0.1 + 0.2 != 0.3。统一 `decimal(12,2)` + `BigDecimal`，保证金额准确。

### 18.9 为什么 product_attribute 与 product_sku_attribute 分开

`product_attribute` 存商品公共特色属性（产地、品牌、保质期，同 SKU 所有变体共享），`product_sku_attribute` 存 SKU 固有属性（颜色=红/蓝、尺寸=120ml/200ml，定义 SKU 差异的维度）。两者职责不同：前者服务于分类检索、个性化展示、订单快照；后者服务于 SKU 规格选择。禁止混淆，避免同时改两张表或查不到属性。

### 18.10 为什么要 supply_plan 供应计划表

课题核心功能「供应与库存协同」。库存只知道当前有多少货，但不知道什么时候补、补多少、参考了什么。supply_plan 把供应计划与需求预测（forecast_qty）绑定，让商家在预测基础上人工调整后确认，到货时驱动库存入库（SUPPLY_IN 流水）。供应到货与库存入库在同一事务，保证双写一致。库存预警自动生成供应建议但不自动创建计划，决策权在商家。
