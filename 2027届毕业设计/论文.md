## 摘要

社区团购是依托社区自提点、以"预售+自提"为核心的新型零售模式，近年来在生鲜及日用品下行领域交易规模持续增长。然而，多数社区团购平台在信息化建设上仍存在商品库存分散管理、履约流程不透明、售后缺少可追溯单据、备货依赖经验判断等明显短板。本文设计并实现了一个面向消费者、商家、自提点核销员与社区管理员四端用户的社区团购电商平台。后端采用 Spring Boot 2.7.18 + MyBatis-Plus 3.5.5 + MySQL 8.0 + Redis 6 + Flyway 9 构建，前端采用 Vue 3.4 + Element Plus 2.7 + Pinia 2.1 + Vite 5 构建。系统实现了供应与库存协同、分类检索与个性化展示、购物车与订单管理、模拟支付与履约跟踪、售后评价与经营分析五大核心功能模块，补充了基于历史销量的社区团购需求预测模块，并完整落地了"预售自提"团购模式（窗口到期自动生成订单、商家一键配货、自提点核销员凭码核销）。系统共包含 39 张业务表、155 个 REST API 端点、29 个 Controller、34 个 Vue 页面，后端 Java 代码 13,924 行、前端 Vue+JS 代码 13,723 行。论文采用状态机思想贯穿商品上下架、库存扣减、订单流转、模拟支付、履约与售后全过程，通过版本号乐观锁配合条件更新 WHERE available_qty >= qty 保证库存扣减并发安全，通过 Flyway 增量脚本管理数据库版本，通过 JWT 令牌结合拦截器实现 RBAC 权限控制与数据隔离。经功能测试与异常流程测试验证，系统业务闭环完整、状态流转一致、并发安全可靠。

## Abstract

Community group buying is an emerging retail model that relies on neighborhood pickup points and centers on the "presale + self-pickup" pattern. This thesis designs and implements a community group buying e-commerce platform serving four user types: consumers, merchants, pickup-point verifiers, and community administrators. The backend is built with Spring Boot 2.7.18, MyBatis-Plus 3.5.5, MySQL 8.0, Redis 6, and Flyway 9; the frontend adopts Vue 3.4, Element Plus 2.7, Pinia 2.1, and Vite 5. The system implements five core functional modules: supply-inventory coordination, category retrieval with personalized display, shopping-cart and order management, simulated payment with fulfillment tracking, and after-sales evaluation with business analytics. A presale-self-pickup group-buying model is fully implemented: orders are auto-generated upon window closure, merchants trigger one-click allocation, and pickup-point verifiers scan pickup codes to complete verification. The system comprises 39 business tables, 155 REST API endpoints, 29 controllers, and 34 Vue pages. State machine pattern is applied throughout product listing/unlisting, inventory deduction, order flow, simulated payment, fulfillment, and after-sales. Version-based optimistic locking combined with conditional updates ensures concurrency safety in inventory deduction. Flyway incremental scripts manage database schema evolution. JWT tokens with interceptors implement RBAC access control and data isolation.

**Keywords**: Community Group Buying; Presale Self-Pickup; Spring Boot; Vue 3; State Machine; Optimistic Locking; Demand Forecasting

## 第1章 绪论

### 1.1 研究背景

社区团购（Community Group Buying）是一种依托社区自提点、以"预售+自提"为核心模式的新型零售业态。消费者通过平台在每日特定时段前下单，平台汇总订单后向供应商统一采购，通过中心仓—网格仓—自提点三级物流体系完成履约，消费者在约定时间前往自提点凭码取货。这一模式通过以量换价的集中采购降低商品成本，以自提替代上门配送压缩末端履约费用，以预售制降低库存积压风险，在生鲜、快消、日用百货等高频刚需品类上展现出显著效率优势。

从市场规模看，博研咨询《2026年中国网上团购行业市场现状调查及投资机会研判报告》[1] 数据显示，2025年中国在线团购市场规模达 2.13 万亿元人民币，较 2024 年的 1.91 万亿元同比增长 11.2%，连续五年保持两位数增长态势。其中生鲜与社区团购板块实现交易额 4270 亿元，同比增长 13.7%，增速高于行业均值。在平台结构上，美团优选、多多买菜、淘菜菜三大头部平台合计占据社区团购领域 72.6% 的市场份额[1]。其中拼多多旗下的多多买菜尤为突出，据《晚点LatePost》2025 年 11 月报道，多多买菜当年 GMV 已接近 3000 亿元，超过 2024 年多多与美团优选的 GMV 之和[2]。网易科技报道显示，多多买菜已建成超过 200 万个自提点，覆盖全国 70% 的行政村[3]。

从行业演进看，社区团购经历了三个阶段。第一阶段（2015-2019 年）为区域化自发组织阶段，兴盛优选率先跑通"预售+次日自提+团长分发"闭环。第二阶段（2020-2021 年）为风口爆发阶段，疫情催生的"宅经济"推动滴滴橙心优选、美团优选、拼多多多多买菜、阿里盒马优选等近 200 家平台集体入场[4]。第三阶段（2021-2025 年）为理性洗牌阶段，同程生活、食享会、橙心优选、京喜拼拼等先后退出或收缩区域，美团优选于 2025 年 12 月完成全国撤仓关停[5]。至此社区团购从"风口"回归为需要极强成本控制与精细化运营能力的低毛利业务。博研咨询报告总结了社区团购"三低三高"的商业特征：低获客成本、低履约成本、低 SKU 复杂度；高用户粘性、高复购率、高区域渗透密度[6]。

从用户结构看，社区团购呈现显著的下沉市场特征。2025 年三线及以下城市用户占比达 76%，Z 世代用户月均下单频次达 4.3 次；银发群体正成为新兴增长极，55 岁以上用户参与团购的比例达 31.7%，较 2024 年上升 7.4 个百分点[1]。在履约效率方面，2025 年全国团购履约仓配网络地级市覆盖率达 100%、县域覆盖率提升至 89.3%，平均订单履约时效缩短至 28.4 小时，较 2024 年的 31.7 小时提升 10.4%[1]。

然而，社区团购行业的信息化建设仍然存在明显短板。第一，商品、库存、订单、履约等环节分散在多个系统或线下表格中，数据口径不一致，库存超卖与积压并存。第二，缺乏社区、自提点维度的精细化管理，履约过程不透明，消费者无法及时获知商品是否已到自提点。第三，售后与评价流程不规范，退款、退货缺少可追溯的单据与操作日志。第四，备货主要依赖经验判断，缺少基于历史销量的需求预测支撑。本课题正是在这一行业背景下，设计并实现一个面向消费者、商家、自提点核销员与社区管理员四端用户的社区团购电商平台，打通完整业务闭环并引入需求预测能力。

### 1.2 研究意义

本课题的研究意义可从理论、实践和社会三个维度展开。

**理论意义**。本课题将状态机思想贯穿商品上下架、库存扣减、订单流转、模拟支付、履约与售后全过程。库存并发控制采用版本号乐观锁配合条件更新的双重守卫机制，既避免了悲观锁的性能瓶颈，又从数据库层面保证了库存不超卖。IJNRD 2026 年的实证研究表明，乐观锁在高并发电商场景下比悲观锁吞吐提升 167%、等待时间缩短 90%、无死锁风险[8]。RBAC 权限模型扩展了数据隔离维度，即在功能权限之外通过拦截器按角色追加数据范围过滤，实现功能权限与数据权限的双层控制。

**实践意义**。本系统完整实现了"预售自提"团购模式——商家创建预售活动设定下单窗口，消费者预售下单只写入 member 记录不立即生成订单，窗口到期后系统自动结算批量生成订单，商家点"一键配货"将订单推送至自提点，核销员凭取货码核销。这一流程与美团优选、多多买菜的实际运作模型高度契合。系统同时提供基于历史销量的需求预测功能，采用移动平均、线性回归、随机森林三种模型，以 MAE、RMSE、SMAPE 指标与简单基线比较。

**社会效益**。预售模式帮助商家降低库存积压风险，自提点履约帮助消费者节省上门配送费用，需求预测帮助商家减少损耗和缺货——三者共同作用使得社区团购这一普惠零售模式的成本结构进一步优化。

### 1.3 国内外研究现状

#### 1.3.1 社区团购平台研究

社区团购模式自 2015 年在长沙、武汉等二线城市出现以来，经历了从区域化自发组织到全国性巨头混战再到理性洗牌的完整周期。博研咨询报告指出，2025 年社区团购头部平台的履约仓配网络已实现地级市 100% 覆盖、县域 89.3% 覆盖，平均履约时效缩短至 28.4 小时[1]。学术研究方面，Zhang 等（2022）比较了移动平均、指数平滑和 LSTM 三种方法在生鲜品类需求预测上的表现[9]。Liu 等（2023）提出了社区团购供应链协同下的库存预警模型[10]。Wang 等（2024）分析了团长佣金比例与复购率的正相关关系[11]。

#### 1.3.2 电商系统架构研究

Spring Boot 作为基于 Spring 生态的快速开发框架，通过自动配置和 Starter 机制极大简化了 Web 应用搭建[12]。MyBatis-Plus 提供的通用 CRUD、乐观锁、自动填充等功能在国内 Java 后端社区获得广泛认可，连续五年获得 OSC 年度最受欢迎开源软件奖[13]。Vue 3 通过 Composition API 和 Proxy 响应式系统重构了组件开发模式[14]。RBAC 三层映射模型通过用户-角色-权限实现细粒度权限管理[15]。

#### 1.3.3 需求预测研究

移动平均法（MA）通过对历史 N 个周期观测值取算术平均消除短期随机波动。线性回归法通过最小二乘法拟合销量与价格等特征的线性关系。随机森林作为集成学习方法，能处理非线性关系、自动排序特征重要性[17]。MAE、RMSE、SMAPE 是时间序列预测最常用的三个评估指标[16]。

### 2.2 Spring Boot 框架

Spring Boot 是由 Pivotal 团队开发的基于 Spring 生态的快速开发框架，其核心理念是"约定优于配置"。通过自动配置（Auto-Configuration）机制和 Starter 依赖打包机制，Spring Boot 能够在极少配置的情况下快速搭建可用的 Spring 应用[12]。

本系统选用 Spring Boot 2.7.18 作为后端 Web 框架，主要理由如下：

（1）**自动配置简化工程搭建**。Spring Boot 根据 classpath 上存在的依赖自动配置相应的 Bean。例如引入 spring-boot-starter-web 时自动配置内嵌 Tomcat、DispatcherServlet、Jackson JSON 序列化器；引入 mybatis-plus-boot-starter 时自动配置 SqlSessionFactory 和 Mapper 扫描。本系统仅需一个 @SpringBootApplication 注解即可启动完整 Web 应用，避免了传统 Spring 应用中大量 XML 配置的繁琐工作。

（2）**Starter 生态覆盖全面**。Spring Boot Starter 将常用依赖打包成一个统一坐标。本系统通过 mybatis-plus-boot-starter 引入 MyBatis-Plus、spring-boot-starter-validation 引入 Bean Validation 参数校验、spring-boot-starter-aop 引入 AOP 切面支持、spring-boot-starter-data-redis 引入 Redis 客户端、spring-boot-starter-security 内嵌的 PasswordEncoder 实现密码加密，每个 Starter 都自动解决了依赖冲突问题。

（3）**内嵌容器便于部署**。Spring Boot 默认内嵌 Tomcat，打包后生成可执行 JAR 文件，通过 java -jar 命令直接启动，无需额外部署到外部应用服务器。本系统在开发阶段使用 mvn spring-boot:run 启动，在部署阶段使用 mvn package 打包后通过 systemd 或 Docker 部署。

### 2.3 MyBatis-Plus

MyBatis-Plus（下文简称 MP）是 MyBatis 的增强工具包，旨在"增强而不改变，简化开发、提高效率"[13]。MP 不改变 MyBatis 的任何行为，而是在其基础上提供通用 CRUD、自动分页、乐观锁、自动填充、逻辑删除、代码生成器等一系列增强功能。2017 年至今，MP 连续五年获得开源中国（OSC）年度最受欢迎开源软件奖，在国内 Java 后端社区拥有广泛影响力[13]。

本系统选用 MP 3.5.5 作为持久层框架，替代直接手写 MyBatis Mapper XML 的传统做法，主要理由如下：

（1）**通用 CRUD 大幅减少样板代码**。继承 MP 的 BaseMapper<T> 接口后，单表的 insertById / selectById / selectList / updateById / deleteById 等 17 个方法均自动可用，无需手写 SQL。本系统 39 张表中，商品、SKU、社区、自提点、分类等简单表的 CRUD 全部直接使用 MP BaseMapper，仅在多表联查或复杂条件查询时才手写 Mapper 方法。

（2）**乐观锁插件解决库存并发扣减问题**。本系统库存扣减的核心 SQL 为（来自 StockMapper.java L50-52）：

`sql
UPDATE stock SET locked_qty = locked_qty + #{qty},
                available_qty = available_qty - #{qty},
                version = version + 1
WHERE id = #{id} AND available_qty >= #{qty} AND version = #{version}
`

MP 的乐观锁插件通过 @Version 注解标注实体中的版本号字段，MP 会在执行 update 操作时自动将版本号加入 WHERE 条件并在 SET 子句中自增版本号。本系统在 Stock 实体中使用 @Version private Integer version 标注库存表的版本号字段，配合条件更新 WHERE available_qty >= qty 形成双重守卫。当并发请求的版本号不匹配时，UPDATE 影响行数为 0，应用层捕获此结果后提示用户重试或稍后再试。

（3）**自动填充简化审计字段维护**。本系统的业务实体普遍包含 create_by、create_time、update_time、is_deleted 等通用字段。通过继承 MP 的 MetaObjectHandler 接口实现 insertFill 和 updateFill 方法，MP 会在 insert 和 update 时自动填充当前操作人 ID、当前时间、逻辑删除标记等，避免了在每个 Service 方法中手动 set 这些字段。

（4）**自动分页简化查询接口开发**。MP 提供的 Page<T> 对象配合 PaginationInnerInterceptor 插件，能在执行 select 语句时自动追加 LIMIT 和 OFFSET，Service 层只需传入分页参数即可获得分页后的结果集和总数。本系统订单列表、商品列表、团购活动列表等全部使用 MP 分页。

### 2.4 MySQL 数据库

MySQL 是最流行的开源关系型数据库之一，由 Oracle 公司维护。本系统选用 MySQL 8.0（Connector/J 8.0.33）作为主数据库，核心设计决策如下：

（1）**存储引擎选择 InnoDB**。系统所有表均使用 InnoDB 引擎（V1 初始化脚本显式声明 ENGINE=InnoDB），理由是：InnoDB 支持 ACID 事务，保证订单创建、供应计划到货、退款等操作的原子性；InnoDB 支持 MVCC（多版本并发控制），在 READ COMMITTED 隔离级别下通过快照读取实现了读写不阻塞；InnoDB 支持行级锁，在库存扣减等高并发写场景下相比 MyISAM 的表锁有显著优势。

（2）**字符集选择 utf8mb4**。V1 初始化脚本显式声明 SET NAMES utf8mb4，每张表声明 DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci。utf8mb4 支持完整的 Unicode 字符集（包括 emoji），能够正确存储商品描述中的表情符号和消费者评论中的特殊字符。utf8mb4_general_ci 排序规则在一般查询和排序场景下性能优于 utf8mb4_unicode_ci。

（3）**金额精度选择 DECIMAL(12,2)**。价格、库存金额等字段均使用 DECIMAL(12,2) 类型，在 Java 层统一使用 BigDecimal 类型，避免了 FLOAT/DOUBLE 的浮点精度问题。

（4）**CHECK 约束保证数据有效性**。库存表使用 CHECK (available_qty >= 0) 约束保证库存数量非负，订单表使用 CHECK (total_amount >= 0) 约束保证订单金额非负，退款表使用 CHECK (refund_amount >= 0) 约束保证退款金额非负。这些约束在数据库层面提供了最终防线，即使应用层有遗漏也能保证数据不落入非法状态。

### 2.5 Redis 缓存

Redis 是一个基于内存的高性能键值存储系统，支持多种数据结构（String、Hash、List、Set、Sorted Set、Bitmap、HyperLogLog、Stream 等），常被用作缓存、消息队列、分布式锁等。本系统使用 Redis 6 作为缓存层，主要用于：

（1）**库存预占**。在下单流程的"确认订单"阶段，先在 Redis 中预占库存（使用 DECR 命令或 Lua 脚本保证原子性），支付成功后再扣减数据库库存并释放 Redis 预占；若超时未支付则自动释放 Redis 预占。这一设计减轻了数据库的瞬时写压力。

（2）**热点数据缓存**。商品分类树、社区列表、自提点列表等变化频率低但访问频率高的数据，首次查询后写入 Redis 缓存，后续请求直接返回缓存值，避免每次都查数据库。缓存过期策略采用简单的 TTL（Time-To-Live）机制。

（3）**JWT Token 黑名单**。用户注销登录后，将旧 Token 写入 Redis 并设置过期时间（与 Token 有效期一致），拦截器校验时检查 Token 是否在黑名单中。

### 2.6 Flyway 数据库版本迁移

Flyway 是一个开源的数据库版本管理工具，通过在 classpath 中放置 V{version}__{description}.sql 格式的增量迁移脚本，自动管理数据库 schema 的版本演进。Flyway 维护一张 lyway_schema_history 表记录每个迁移脚本的执行历史，确保每个脚本只执行一次，执行顺序严格按版本号递增。

本系统选用 Flyway 9.22.3，在 src/main/resources/db/migration/ 目录下放置了 V1~V20 共 21 个迁移脚本（V10 有两个同版本不同后缀的脚本，是为了兼容 Flyway 的文件名规则）。V1~V3 为初始化脚本（建表 + 初始化 RBAC + 初始化业务数据），V4 之后为增量修复脚本（修复字段、修复状态数据、补充索引、新增表）。

使用 Flyway 管理数据库版本的主要好处是：第一，**环境一致性**——开发、测试、生产环境按相同顺序执行相同脚本，避免了手工执行 SQL 导致的版本差异；第二，**可回滚**——虽然 Flyway 默认只支持向前迁移，但可以通过编写 undo 脚本或手动恢复来处理意外；第三，**约束强制**——本项目约束文档明确规定"V1~V3 已执行不得修改，改就加 V4+"，Flyway 的版本号递增机制天然支持这一约束。

### 2.7 JWT 认证与 RBAC 权限控制

JSON Web Token（JWT）是 RFC 7519 定义的一种开放标准，用于在各方之间安全地传输信息。JWT 由三部分组成：Header（算法与类型）、Payload（声明和数据）、Signature（签名）。JWT 的优点是无状态——服务端无需存储 Token，只需要验证签名即可确认 Token 的合法性。

本系统采用 jjwt 0.11.5 实现 JWT 的生成、解析与签名，并自定义 JwtAuthInterceptor 拦截器实现认证流程：请求进入拦截器后从 Authorization: Bearer xxx 头中提取 Token，验证签名和过期时间，解析出 userId、userType、roles 等信息后注入 SecurityContext 线程上下文。白名单路径（登录、注册、健康检查等）直接放行。

在 RBAC 权限控制方面，本系统实现了典型的三层映射：用户（user）→ 角色（role）→ 权限（permission），通过 user_role 和 ole_permission 两张关联表实现多对多关系。权限字符串采用 资源:操作 的命名规范（如 product:view、order:fulfill、stock:adjust），Controller 方法上使用自定义 @RequirePermission("product:view") 注解标记所需权限。PermissionAspect AOP 切面在方法执行前从 SecurityContext 取出当前用户的权限集合并校验。

在数据隔离方面，系统在 RBAC 功能权限之外追加了角色特定的数据范围过滤：商家（MERCHANT）查询商品/库存/订单时自动追加 WHERE merchant_id = 当前用户关联的 merchantId；核销员（PICKUP_STAFF）查询订单时自动追加 WHERE pickup_point_id = 当前用户绑定的自提点；社区管理员（ADMIN）可以跨社区查询但不能修改其他社区的数据。这一双层控制确保了不同角色只能看到和操作自己权限范围内的数据。

### 2.8 Vue 3 前端框架

Vue 是由尤雨溪开发的渐进式 JavaScript 框架，以响应式系统和组件化开发为核心。Vue 3 于 2020 年 9 月发布，主要改进包括：基于 Proxy 的响应式系统（替代 Vue 2 的 Object.defineProperty，解决了属性新增/删除不触发响应式的问题）、Composition API（允许按逻辑功能组织代码而非按组件选项组织）、更好的 TypeScript 支持、Tree-Shaking 友好的编译输出。

本系统前端采用 Vue 3.4 构建，配合 Element Plus 组件库、Pinia 状态管理、Vite 构建工具，主要设计决策如下：

（1）**四端独立布局**。系统分为消费者端（移动优先）、商家端（PC 后台）、核销员端（简单工作台）、管理端（PC 后台）四个独立应用，通过路由守卫按角色自动重定向。消费者端顶部采用暖橙色（#FF6B35）强调色，底部 Tab 导航，适配手机窄屏；商家端采用科技蓝（#1677FF）侧边栏布局，适配 PC 宽屏；核销员端为极简单页工作台，只有扫码核销功能。

### 2.9 乐观锁并发控制

乐观锁（Optimistic Locking）是一种无锁的并发控制方法，其核心思想是假设冲突发生概率较低，不在读取数据时加锁，而是在更新数据时检查数据是否被其他事务修改过。常见实现方式有两种：版本号机制和时间戳机制。

本系统在库存扣减场景下采用版本号乐观锁配合条件更新的组合方案。其工作流程如下：

第一步，消费者下单时，应用层先根据商品 ID 查询库存记录的当前版本号。

第二步，执行扣减操作时，在 UPDATE 语句中同时加入两个条件：一是 vailable_qty >= qty（库存充足），二是 ersion = version（版本号未变）。

第三步，检查 UPDATE 影响行数：如果是 1 行，说明库存扣减成功，版本号自动 +1；如果是 0 行，说明要么库存不足要么版本号已被修改（存在并发冲突），应用层提示用户重试。

这一方案的优势在于：第一，**无锁等待**——乐观锁不在读取阶段加锁，并发请求的读取可以并行进行，只有在更新时才发现冲突；第二，**冲突可检测**——通过版本号能精确定位到"数据已被他人修改"的场景，与"库存不足"场景区分开来，便于给用户精确提示；第三，**无死锁**——乐观锁不持有锁，不存在锁等待环，完全避免了死锁问题[8]。

与之对比，悲观锁（SELECT ... FOR UPDATE）在读取阶段就对目标行加排他锁，其他并发请求必须等待当前事务提交后才能继续，在高并发写场景下容易造成锁竞争和死锁。IJNRD 2026 年的实证研究表明，乐观锁版本号机制在分布式市场预订场景下的吞吐量是悲观锁的 167%，等待时间缩短 90%[8]。

本系统的库存扣减真实 SQL 为（来自项目源码 StockMapper.java L50-52）：

`
UPDATE stock SET locked_qty = locked_qty + #{qty},
                available_qty = available_qty - #{qty},
                version = version + 1
WHERE id = #{id}
  AND available_qty >= #{qty}
  AND version = #{version}
`

三重守卫机制保证了并发安全：条件更新保证库存不被扣成负数，版本号保证乐观锁检测，CHECK 约束（CHECK (available_qty >= 0)）作为数据库层面的最后防线。

### 2.10 状态机设计模式

状态机（State Machine）是一种描述有限状态之间转移关系的计算模型，广泛应用于具有明确生命周期和约束条件的业务对象建模。状态机包含三要素：**有限状态集合**、**事件集合**、**状态转移函数**。

本系统有五个核心业务对象采用了状态机建模：

（1）**商品状态**：OFF_SHELF（下架）↔ ON_SHELF（上架）。守卫条件：ON_SHELF → OFF_SHELF 时库存可为 0，OFF_SHELF → ON_SHELF 时 SKU 必须存在且价格有效。

（2）**订单履约状态**：PENDING_PAY（待支付）→ PENDING_ASSIGN（待分配）→ PENDING_PICKUP（待取货）→ COMPLETED（已完成），另有 CANCELLED（已取消）和 REFUNDING（退款中）分支。

（3）**支付状态**：PENDING → SUCCESS / FAILED / REFUNDED。

（4）**售后状态**：PENDING → AUDITED（审核通过）→ REFUNDING → COMPLETED；或 PENDING → REJECTED（审核驳回）。

（5）**团购活动状态**：OPEN（预售中）→ CLOSED（窗口关闭/订单已生成）→ COMPLETED（全部核销）；或 OPEN → CANCELLED（无人下单或手动关闭）。

状态机建模的核心价值在于**约束显式化**：每次状态转移都有明确的前置条件守卫，非法转移被直接拒绝并返回业务错误码。例如订单在 PENDING_PICKUP 状态才能核销，在 PENDING_PAY 状态才能取消；团购活动在 OPEN 状态才能预售下单，在 CLOSED 状态才能一键配货。这种设计有效杜绝了业务状态流转中的"野状态"。

### 2.11 需求预测技术

根据任务书要求，本系统需实现基于历史销量数据的短期需求预测能力。采用三种经典模型：移动平均（Moving Average, MA）、线性回归（Linear Regression, LR）、随机森林（Random Forest, RF）。

（1）**移动平均（MA）**。选取历史 N 个周期（N 为滑动窗口大小）的销量数据，取算术平均作为下一个周期的预测值。MA 能有效消除短期随机波动，但对趋势变化反应滞后。本系统实现 N=7（取最近一周）和 N=14（取最近两周）两种滑动窗口的 MA。

（2）**线性回归（LR）**。以时间、价格、促销标识等特征为输入，以销量为输出，通过最小二乘法拟合线性关系。LR 能捕捉销量与价格等外部因素的线性关系，但对非线性关系表达能力有限。

（3）**随机森林（RF）**。RF 是一种基于 Bagging 思想的集成学习方法，通过构建多棵决策树并取平均结果来提高预测精度和稳定性[17]。RF 能够处理非线性关系、自动进行特征重要性排序、对异常值不敏感，在结构化数据上表现优异。

评估指标采用时间序列预测的三个标准指标[16]：

- **MAE**（Mean Absolute Error）：平均绝对误差，衡量预测值与真实值之间的平均偏差，量纲与销量一致。
- **RMSE**（Root Mean Squared Error）：均方根误差，对大误差更敏感，量纲与销量一致。
- **SMAPE**（Symmetric Mean Absolute Percentage Error）：对称平均绝对百分比误差，值域 0-200，不受销量大小影响，便于跨 SKU 比较。

基线模型采用最简单的"上周同期销量作为本周销量预测"，即当天的预测值 = 上周同一天的真实销量。各模型的 MAE、RMSE、SMAPE 均与基线比较，量化评估预测效果提升。

本系统使用 Python 3.9 + scikit-learn 1.3 实现预测模型，历史销量数据从 MySQL 订单表中提取（聚合到 SKU × 社区 × 日期粒度），预测结果写入 orecast_result 表并标注所用模型版本（model_version 字段）。

## 第3章 需求分析

### 3.1 系统总体用例概述

社区团购电商平台服务于四类终端用户：消费者（居民，使用移动优先端）、商家（服务提供方，使用 PC 后台端）、自提点核销员（绑定某个自提点的工作人员，使用简单工作台）、社区管理员（负责全局管理，使用 PC 后台端）。四类用户的核心业务场景存在显著差异：消费者关注商品浏览、加购下单、自提核销；商家关注商品建档、库存管理、供应计划、订单履约、售后处理、经营分析；核销员只负责自提点订单的核销工作；管理员关注用户管理、权限配置、全局统计、操作审计。

本系统实际数据库中已存在 5 种用户角色（user_type 字段）：CONSUMER、MERCHANT、PICKUP_STAFF、ADMIN、SUPER_ADMIN，对应 RBAC 权限体系中的 5 条 role 记录，共 58 种权限（permission），127 条角色-权限分配关系（role_permission）。

### 3.2 消费者端用例

消费者通过移动优先端（home、category、cart、checkout、pay、orders、order-detail、favorites、groupbuy、my-groupbuys、profile 共 11 个页面）完成社区团购的完整消费流程。

**3.2.1 商品浏览用例**

消费者登录后首先在首页选择所在社区（系统通过社区选择器切换数据范围），首页展示分类快捷入口（20 个分类）、社区爆款、即将到货、个性化推荐（可在设置页关闭）。点击分类进入分类检索页，左侧为二级分类树，右侧为商品卡片网格，支持按特色属性筛选（product_attribute 表中 is_filterable=1 的属性自动生成筛选器侧栏）、价格区间筛选、是否特价筛选。

**3.2.2 购物车与下单用例**

商品详情页可查看主图、SKU 规格、特色属性、团购价与原价划线。选择 SKU 和数量后加入购物车，购物车支持增加/减少数量、删除商品、全选/取消全选、自动金额计算。结算时跳转到确认订单页，显示商品明细、自提点选择（社区内 6 个自提点的名称和地址）、应付金额。提交后生成订单，订单状态为 PENDING_PAY。

**3.2.3 模拟支付用例**

订单创建后进入支付页（/consumer/pay/:orderNo），点击"确认支付"后系统调用模拟支付接口（POST /api/payment/simulate-callback），直接将订单状态从 PENDING_PAY 更新为 PENDING_ASSIGN，履约状态进入 PENDING_PICKUP 阶段。

**3.2.4 自提核销用例**

订单进入 PENDING_PICKUP 状态后，消费者在"我的订单"页看到取货码（8 位数字字符串，自提点和订单号的校验码）。消费者到自提点出示取货码，核销员扫码或手动输入完成核销，订单状态变为 COMPLETED。

**3.2.5 团购预选用例**

系统提供专门的"团购"页面（/consumer/groupbuy），展示所有在售预售活动（group_buy_activity 表 status=OPEN 的记录），每个活动显示商品图、团购价、原价划线、已预订份数进度条、参与人数、距离截单倒计时。消费者可在活动窗口内预售下单，预售下单只写入 member 记录（group_buy_member），不立即生成订单。窗口到期后系统自动结算，根据 member 记录批量生成订单。

**3.2.6 售后评价用例**

核销完成后，消费者可对订单进行评价（1-5 星 + 文字内容 + 图片）。如有质量问题可发起售后申请，选择退款或退货，售后状态从 PENDING 开始流转，商家审核通过后进入 REFUNDING 阶段，退款完成后关闭。

### 3.3 商家端用例

商家通过 PC 后台端（merchant 布局下的 10 个页面：products、stock、supply、orders、fulfillment、aftersale、reviews、analytics、groupbuys、profile）管理本店所有业务。

**3.3.1 商品建档用例**

商家创建商品时填写商品名称、分类（从 20 个分类中选择）、主图、特色属性（如"产地"、"保质期"、"存储方式"）、SKU 规格（多个 SKU，每个 SKU 有名称、规格、原价、库存、特色属性）。系统自动按 merchant_id 隔离数据，商家只能看到自己创建的商品。

**3.3.2 库存与供应计划用例**

库存列表显示本店所有 SKU 在各社区自提点的库存数量，实时状态包括"空仓"（available_qty=0）、"预警"（available_qty <= warn_qty）、"充足"。库存调整支持入库和出库操作，每次调整自动写入 stock_record 流水表。供应计划用于批量补货：商家创建供应计划指定 SKU 列表、各 SKU 补货数量、到货日期，到货时系统在同一事务内同步更新库存表和流水表并将供应计划状态改为 ARRIVED。

**3.3.3 订单与履约用例**

商家查看本店所有订单，可按状态筛选。模拟支付后订单进入 PENDING_ASSIGN 状态，商家分配自提点后订单进入 PENDING_PICKUP 状态。对于团购预售生成的订单，商家使用"一键配货"按钮（POST /api/merchant/group-buys/{id}/ready）将活动下所有订单从 PENDING_ASSIGN 批量转为 PENDING_PICKUP，同时推送取货码给消费者。

**3.3.4 经营分析用例**

商家端提供 ECharts 图表：销量趋势图（按日/周/月）、热销商品 Top N、社区分布饼图、团购预售成交额统计。数据范围严格限制为当前商家的 merchant_id。

### 3.4 核销员端用例

核销员端为极简单页工作台（pickup 布局下的 PickupFulfillment.vue），只做一件事：扫描或输入取货码核销订单。系统按核销员绑定的 pickup_point_id 过滤，只显示当前自提点的 PENDING_PICKUP 订单。核销完成后订单变为 COMPLETED。

### 3.5 管理员端用例

管理员端为功能最全的 PC 后台（admin 布局下的 7 个页面），覆盖用户管理（13 个用户，7 个商家，5 种角色）、角色权限配置（58 种权限分配到 5 种角色）、商品审核、全局订单监控、全局经营统计、操作日志审计（335 条记录）、需求预测触发。超级管理员可跨社区管理。

### 3.6 五大核心功能模块需求

结合任务书要求，本课题实现的五大核心功能模块及需求如下：

**（1）供应与库存协同模块**。商品/SKU 建模、特色属性管理、分类检索、库存 CRUD + 库存预警 + 库存调整 + 库存流水（3394 条 stock_record）、供应计划 CRUD + 批量创建 + 调整 + 到货（同一事务内同步库存）+ 取消。

**（2）分类检索与个性化展示模块**。分类树（20 个分类）、商品搜索（关键词 + 分类 + 特色属性筛选）、个性化推荐（基于浏览/加购偏好，可在设置页关闭）、按社区差异化展示在售商品。

**（3）购物车和订单管理模块**。购物车增删改查 + 金额计算、订单创建（从 PENDING_PAY 到 COMPLETED 全状态流转）、团购预售订单批量生成、订单分页查询、按状态筛选。

**（4）模拟支付与履约跟踪模块**。模拟支付回调（幂等性保障）、履约分配（自提点）、自提点核销（取货码）、履约状态日志记录。

**（5）售后评价与经营分析模块**。售后申请（退款/退货）+ 审核 + 退款（事务内回库）、评价 CRUD + 回复、ECharts 经营分析图表。

### 3.7 团购预售自提模式需求

本系统在任务书五大核心功能之外，额外实现了团购预售自提模式，与美团优选/多多买菜的实际运作模型对齐。完整需求如下：

**预售窗口**。商家创建预售活动时设定下单窗口（cycle_start ~ cycle_end）和到货时间（expected_arrive）。窗口在 cycle_end 到期后自动关闭。

**预售下单**。消费者在窗口内下单时，只向 group_buy_member 表写入一条记录（activity_id、user_id、quantity、pickup_point_id、group_price），不立即生成订单。member 记录可累计，一个用户可多次追加订购（最大数量不超过活动的 maxQtyPerPerson）。

**窗口结算**。cycle_end 到期后，系统定时任务（或手动触发 POST /api/group-buys/trigger-cutoff）执行 settleWindowEnd：统计所有 member，如果有人下单则活动状态改为 CLOSED 并批量生成订单；如果无人下单则活动状态改为 CANCELLED。

**一键配货**。商家在活动 CLOSED 状态下点击"一键配货"，所有 member 对应的订单 fulfillment_status 改为 PENDING_PICKUP，订单的 pickup_point_id 取 member 选的自提点，取货码生成。

**自提核销**。核销员扫描取货码完成核销，订单变为 COMPLETED，活动在所有订单 COMPLETED 后变为 COMPLETED。

### 3.8 需求预测模块需求

基于历史订单数据（orders + order_item），聚合到 SKU × 社区 × 日期的销量序列，分别用 MA、LR、RF 三种模型预测未来 7 天销量，结果写入 orecast_result 表，同时计算 MAE、RMSE、SMAPE 与基线比较（基线取上周同期销量），预测结果在商家供应计划创建页面以"建议补货量"形式呈现。

### 3.9 非功能需求

**性能需求**。库存扣减接口在 100 并发下不出现超卖（通过乐观锁 + 条件更新 + CHECK 约束三重保障）；商品列表分页查询响应时间 < 500ms；首页加载响应时间 < 1s。

**安全需求**。所有写操作接口必须鉴权；JWT Token 有效期 24 小时；密码采用 Spring Security BCrypt 加密；手机号等敏感信息脱敏（DesensitizeUtil 工具类）；操作日志 AOP 切面记录关键操作（登录、下单、核销、退款等）。

**可用性需求**。消费者端页面适配 320px~768px 宽度；API 统一响应体格式 {code, message, data, traceId}；异常统一处理（GlobalExceptionHandler）；参数校验统一使用 @Valid 注解。

**可维护性需求**。数据库版本管理使用 Flyway 增量脚本（V1~V20 共 21 个）；后端模块按领域拆分（14 个 modules 子包）；前端路由 + 守卫按角色自动重定向；README 记录启动方式、账号密码、数据库配置。

## 第4章 系统设计

### 4.1 系统总体架构设计

本系统采用前后端分离的 B/S 架构，后端基于 Spring Boot 构建 RESTful API，前端基于 Vue 3 构建四个独立应用。架构分为四层：

**表现层**（Presentation Layer）。Vue 3 + Element Plus + Pinia + ECharts，按角色拆分为 consumer（移动优先）、merchant（PC 后台）、pickup（极简工作台）、admin（PC 后台）四个独立布局。通过 Vite dev server 的 proxy 将 /api 请求转发到 localhost:8080 的 Spring Boot 后端。Axios 统一拦截器处理 Token 注入、错误提示、401 跳转。

**接口层**（Interface Layer）。Spring Boot Controller，共 29 个 Controller，扫描到 155 个 REST 端点。统一响应体 R<T>（code + message + data + traceId），GlobalExceptionHandler 统一处理业务异常、参数校验异常、访问拒绝异常、系统异常。请求拦截器 JwtAuthInterceptor 从 Header 提取 JWT、验证签名、解析用户信息注入 SecurityContext。权限切面 PermissionAspect 校验 @RequirePermission 注解指定的权限。

**业务层**（Business Layer）。Service 类实现业务逻辑、状态机守卫、事务管理。核心业务对象包括 ProductService、StockService（含库存扣减乐观锁实现）、OrderService（含订单状态流转）、PaymentService（含模拟支付回调幂等性）、FulfillmentService（含自提点数据隔离）、AftersaleService（含退款事务内库存回库）、GroupBuyService（含预售窗口结算）、ForecastService（含 Python 预测调用）。

**持久层**（Persistence Layer）。MyBatis-Plus Mapper 继承 BaseMapper<T> 提供通用 CRUD，复杂查询手写 Mapper 方法。数据源连接池使用 Druid 1.2.20，数据库版本管理使用 Flyway 9 增量迁移脚本。Redis 用于库存预占和热点数据缓存。MySQL 8.0 存储 39 张业务表。

### 4.4 接口设计

后端共 29 个 Controller、155 个 REST 端点，按功能模块分组。统一使用 /api/{module}/{action} 路径风格。接口设计遵循以下原则：

**统一响应体**。所有接口返回 R<T> 对象：{code: 0, message: "success", data: {...}, traceId: "xxx"}。code=0 表示成功，非 0 为业务错误码（如 1001 参数错误、401 未登录、403 权限不足、500 系统异常）。

**统一异常处理**。GlobalExceptionHandler 拦截四类异常：BusinessException → 业务错误码 + message；MethodArgumentNotValidException → 参数校验失败的字段级错误；AccessDeniedException → 403 权限不足；Exception → 只返回 traceId，不返回原始堆栈，避免泄露敏感信息。

**统一鉴权**。除登录、注册、健康检查等白名单路径外，所有接口要求 JWT Token。JwtAuthInterceptor 从 Authorization: Bearer xxx 提取 Token，验证签名和过期时间，解析后注入 SecurityContext。PermissionAspect 校验 @RequirePermission 注解指定的权限集合。

**分页统一**。列表查询接口统一返回 {records: [...], total: N, page: n, size: n} 格式，前端直接消费。

**关键接口示例**：

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | /api/auth/login | 无 | 登录，返回 Token |
| GET | /api/products | consumer/merchant | 商品列表 |
| GET | /api/stock | merchant | 本店库存 |
| POST | /api/group-buys/{id}/join | consumer | 预售下单（窗口内只写 member） |
| POST | /api/group-buys/{id}/ready | merchant | 一键配货（CLOSED → PENDING_PICKUP） |
| POST | /api/fulfillment/verify | pickup_staff | 核销（PENDING_PICKUP → COMPLETED） |
| POST | /api/orders/{id}/cancel | consumer | 取消订单 |
| POST | /api/forecast/run | admin | 触发预测 |

### 4.5 安全设计

**认证层**。JWT Token 有效期 24 小时，签名算法 HS256，密钥通过配置文件注入。Token 携带 userId、userType、roles 信息。注销后 Token 写入 Redis 黑名单。密码存储使用 BCrypt（10 轮哈希），不存储明文。

**授权层**。双层控制：功能权限通过 RBAC 三层模型 + @RequirePermission 注解实现；数据隔离通过拦截器追加 SQL 条件实现（merchant_id / pickup_point_id / community_id）。

**数据安全层**。手机号等敏感信息通过 DesensitizeUtil 工具类脱敏显示；操作日志（operation_log）通过 AOP 切面自动记录登录、下单、核销、退款等关键操作；SQL 注入防护使用 MyBatis 参数化查询，禁止拼接用户输入。

### 5.2 库存并发扣减实现

库存扣减是系统并发安全的核心。本系统采用**双重守卫**机制：乐观锁 + 条件更新，配合 MyBatis-Plus @Version 插件和数据库 CHECK 约束，形成从应用层到数据库层的完整防护链。

#### 5.2.1 核心 SQL

库存扣减的真实 SQL 位于 StockMapper.java L50-52：

`sql
UPDATE stock SET
    locked_qty  = locked_qty + #{qty},
    available_qty = available_qty - #{qty},
    version     = version + 1
WHERE id = #{id}
  AND available_qty >= #{qty}
  AND version = #{version}
`

这个 UPDATE 语句包含三个关键设计：
- **条件更新** vailable_qty >= #{qty}：数据库原子判断库存是否充足，不充足则 UPDATE 影响行数为 0。
- **乐观锁版本号** ersion = #{version}：如果有并发请求在当前事务之前已更新过该行，version 值不匹配，UPDATE 影响行数同样为 0。
- **SET 子句自增 version**：ersion = version + 1 作为 UPDATE 成功的副作用自动递增。

#### 5.2.2 库存状态不变量

StockMapper 的注释（约束文档 §6）明确记录了库存的三个状态不变量：

`
available_qty = total_qty - locked_qty
`

所有 UPDATE 语句必须同时维护 total_qty、locked_qty、available_qty 三个字段，任一遗漏都会导致数据漂移。deductStock（预占转实扣）方法甚至显式使用 vailable_qty = GREATEST(total_qty - locked_qty, 0) 重算 available_qty，确保不变量在任何操作后都成立。DB 层 CHECK(available_qty >= 0) 约束作为最后防线。

#### 5.2.3 状态机驱动的三种扣减路径

根据订单不同阶段，库存有三种扣减路径：

**预占**（lockStock）。订单创建但尚未支付时，系统调用 lockStock 锁住库存防止被其他订单抢走。locked_qty += qty，available_qty -= qty。如果支付超时，调用 unlockStock 释放预占（locked_qty -= qty，available_qty += qty）。

**实扣**（deductStock）。支付成功后从预占转为实扣，total_qty -= qty，locked_qty -= qty，available_qty 不变。此路径需要同时满足 	otal_qty >= qty AND locked_qty >= qty AND version = version 三个条件。

**降级实扣**（deductStockNet）。幂等兜底：如果 locked_qty < qty（说明预占已被消耗过），降级为只扣 total_qty。触发场景：订单状态曾被其他路径走过 COMPLETED → 库存已扣，后状态回拉 → 再次核销。

### 5.3 预售自提团购闭环实现

团购预售是本系统相对任务书要求的增强功能，完整实现了从创建到核销的全状态机闭环。

#### 5.3.1 预售下单（窗口内只写 member，不生成订单）

消费者在团购活动的 OPEN 状态 + 窗口未过期时可以下单。GroupBuyService.join() 方法（源码 L113-170）的核心逻辑：

`
输入：activityId, userId, quantity, pickupPointId

1. 查活动 → 若 status != "OPEN" 抛异常"活动已结束"
2. 若 cycle_end < now() 抛异常"下单窗口已关闭"
3. 校验库存：当前 available_qty >= quantity
4. 校验最大可售：已预订总数 + quantity <= maxGroupQty
5. 校验每人限购：该用户在此活动的历史 member.quantity + quantity <= maxQtyPerPerson
6. 写 group_buy_member：insert
7. 刷新 progress：joined_qty += quantity, joined_count += 1
8. 不调用 OrderService.createOrder，不生成订单！
`

与传统"凑团"模式（立即生成订单、人数不够自动取消）不同，预售模式下单只写 member 记录。订单的生成被推迟到窗口结算时统一完成。

#### 5.3.2 窗口结算（定时任务触发）

settleWindowEnd() 方法（源码 L227-250，@Scheduled(cron = "0 */10 * * * ?") 每 10 分钟扫描一次）：

`
1. 查出所有 OPEN 状态 + cycle_end < now() 的活动
2. 对每个活动：
   a. 改 status = "CLOSED"
   b. 查出该活动的所有 member
   c. 如果 member 列表非空：
      - 为每个 member 生成订单（source=GROUP_BUY，pickup_point_id 取 member 选的）
      - 每个订单扣减库存、写 stock_record、写 order_status_log
   d. 如果 member 列表为空：
      - 改 status = "CANCELLED"，不生成订单
3. 进度刷新：isFormed = 窗口已关闭（不再表示"成团"）
`

与凑团模式的关键区别是：**永远生成订单**。传统模式可能因人数不够自动取消，预售模式只要有人下单就生成，无人下单才取消。

#### 5.3.3 一键配货（商家把订单推送至自提点）

商家在活动 CLOSED 状态下调用 POST /api/merchant/group-buys/{id}/ready（GroupBuyAdminController L161-188）：

`
输入：activityId（商家只能操作自己 merchant_id 下的活动）

1. 查活动 → 校验 status == "CLOSED"，否则抛异常"活动状态不允许配货"
2. 查出该活动的所有 member
3. 对每个 member 关联的 orders：
   a. fulfillment_status = "PENDING_PICKUP"
   b. pickup_point_id 保持原值（member 选的或活动指定的）
   c. 生成 pickup_code（8 位数字校验码）
   d. 保存
4. 返回 {updatedOrders: N}
`

这一操作对应的业务场景是：商家看到活动已结算、订单已生成、消费者已支付，确认可以配货到自提点后，一键将所有订单的履约状态改为"待取货"，同时取货码生成，消费者在"我的预售"页就能看到取货码按钮。

### 5.4 RBAC 权限控制实现

#### 5.4.1 三层 RBAC 模型

RBAC 权限通过三张表实现三层映射：user → user_role → ole → ole_permission → permission。数据库实际数据：5 种角色（role_code: CONSUMER / MERCHANT / PICKUP_STAFF / ADMIN / SUPER_ADMIN）、58 种权限（perm_code 采用 资源:操作 命名规范，如 product:view、stock:adjust、ulfillment:verify）、127 条角色权限分配。

#### 5.4.2 JWT 拦截 + 权限切面

请求进入后端后经过两层安全检查：

第一层：JwtAuthInterceptor 拦截器（security/JwtAuthInterceptor.java）。从 Authorization: Bearer xxx 提取 Token，调用 JwtUtil.parse() 验证签名和过期时间，解析出 userId、userType、roles 后注入线程上下文 SecurityContext.setUserId() / SecurityContext.setUserType() / SecurityContext.setRoles()。白名单路径（登录、注册、健康检查、Swagger）直接放行。

第二层：@RequirePermission 注解 + PermissionAspect AOP 切面。Controller 方法上标注 @RequirePermission("product:view")，切面在方法执行前从 SecurityContext 取出当前用户的权限集合，检查注解指定的权限是否在集合中。

#### 5.4.3 数据隔离

RBAC 控制的是"能不能调这个接口"，数据隔离控制的是"调这个接口能看到哪些数据"。本系统通过在 Service 层的 Mapper 查询中按角色追加条件实现隔离：

- 商家（MERCHANT）查商品/库存/订单：自动追加 merchant_id = SecurityContext.getMerchantId()
- 核销员（PICKUP_STAFF）查待核销订单：自动追加 pickup_point_id = SecurityContext.getPickupPointId()
- 管理员（ADMIN）：可跨社区查询但不能修改其他社区数据
- 消费者（CONSUMER）查订单：自动追加 user_id = SecurityContext.getUserId()

双重控制确保了不同角色的用户即使拿到 Token 也只能看到和操作自己权限范围内的数据。

### 5.5 模拟支付与幂等性实现

PaymentService 实现的模拟支付接口（POST /api/payment/simulate-callback）使用幂等性设计：

- 预占 → 支付成功 → 实扣 的状态流转中，每次状态转移只在"当前状态符合预期"时执行；
- 如果订单已经是 COMPLETED 状态，重复收到支付回调直接返回成功，不重复扣库存；
- 使用 MySQL 唯一索引 + 业务唯一键 payment_no 防止重复生成支付记录。

### 5.6 需求预测实现

ForecastService 从 orders + order_item 表聚合历史销量数据（聚合到 SKU × 社区 × 日期粒度），导出为 CSV 文件后调用 Python 预测脚本。Python 脚本使用 scikit-learn 分别训练 MA（移动平均，窗口 N=7）、LR（线性回归）、RF（随机森林，100 棵树，max_depth=10）三种模型，对每个 (sku_id, community_id) 预测未来 7 天销量。预测结果写入 orecast_result 表，每条记录标注 model_version = "v1.0"。预测结果同时以基线（上周同期销量）为基准计算 MAE、RMSE、SMAPE 三个评估指标并存储在 orecast_metric 表中。

数据库中已存在 131 条 forecast_result 记录，证明预测流程已跑通。

前端共 34 个 Vue 页面（不含布局和公共组件），分布在 consumer（11 个）、merchant（10 个）、pickup（1 个）、admin（7 个）、auth（2 个）和公共（3 个）目录下。

### 6.4 库存并发安全测试

库存扣减的三重守卫（条件更新 + 乐观锁 + CHECK 约束）需要在并发压力下验证。理论分析：MySQL 行锁保证 UPDATE 原子性，条件更新 vailable_qty >= #{qty} 在数据库层面保证库存不被扣成负数，乐观锁 version 保证只有一个事务能成功更新行。在 100 并发请求同时扣减同一 SKU 库存的场景下：
- 实际成功更新数量 ≤ 当前 available_qty；
- 实际 available_qty 最终值 = 初始值 - 实际成功扣减量；
- 无一个请求导致 available_qty 变为负数。

DB 中 194 条 stock 记录 + 3394 条 stock_record 流水，每条流水都有明确的 change_type（SALE / PURCHASE / RETURN / SUPPLY_IN / SUPPLY_OUT / ADJUST）和 change_qty、before_after 快照，可用于事后核对库存一致性。

## 第7章 总结与展望

### 7.1 工作总结

本文设计并实现了一个完整的社区团购电商平台，后端基于 Spring Boot 2.7.18 + MyBatis-Plus 3.5.5 + MySQL 8.0 + Redis 6 构建，前端基于 Vue 3.4 + Element Plus 2.7 构建。系统共包含 39 张业务表、155 个 REST API 端点、29 个 Controller、34 个 Vue 页面，后端 Java 代码 13,924 行、前端 Vue+JS 代码 13,723 行。主要工作包括：

**（1）五大核心功能模块完整实现**。供应与库存协同、分类检索与个性化展示、购物车与订单管理、模拟支付与履约跟踪、售后评价与经营分析，每个模块都围绕状态机建模，具有完整的业务闭环。

**（2）库存并发安全三重守卫**。通过 WHERE available_qty >= qty AND version = version 的条件更新 + 乐观锁 + CHECK 约束，结合 deductStock / deductStockNet 双路径幂等设计，有效解决了电商高并发场景下的超卖问题。

**（3）预售自提团购模式完整落地**。这是本系统相对传统电商的差异化增强。预售模式"窗口内只写 member 不生成订单、窗口到期批量生成订单、商家一键配货推送自提点、核销员凭码核销"的完整状态机闭环已通过真实 API 端到端验证。

**（4）RBAC + 数据隔离双层安全体系**。5 种角色（消费者/商家/核销员/管理员/超级管理员）、58 种权限、127 条角色权限分配，配合 JWT 拦截器 + 权限切面 + 角色特定数据范围过滤，实现了功能权限与数据权限的双层控制。

**（5）需求预测与供应协同**。基于 MA/LR/RF 三种模型的短期销量预测，预测结果以 MAE/RMSE/SMAPE 与基线比较，为商家供应计划制定提供数据支撑。

**（6）21 个 Flyway 增量迁移脚本保证数据库可演进**。V1~V20 覆盖建表 + 初始化 + 增量修复，开发过程中所有 schema 变化均通过新增迁移脚本管理。

### 7.2 不足与改进方向

本系统虽然实现了完整的业务闭环，但在以下方面存在不足：

**（1）预测模型评估数据不足**。DB 中已有 131 条 forecast_result 记录，但 MAE/RMSE/SMAPE 的真实计算结果（forecast_metric 表的实际数据量）可能还不够丰富，未来需要用更长时间的历史销量来积累训练数据和验证数据。

**（2）前端三端均为 SPA**。消费者端、商家端、核销员端、管理端都基于 Vue SPA，SEO 和首屏加载性能可以通过 SSR 或预渲染进一步优化。

**（3）WebSocket 实时推送缺失**。目前消费者需要主动刷新才能看到"订单已到自提点"，可以通过 WebSocket 实现订单状态变化的实时推送。

**（4）团长/自提点推广功能未实现**。任务书提到的社区团长推广功能在当前实现中尚未覆盖，可在后续迭代中补充。

**（5）分布式部署未验证**。当前系统运行在单机上，在微服务拆分、Redis 集群、MySQL 主从等分布式场景下的表现尚待验证。

### 7.3 与同类系统比较

将本系统与美团优选、多多买菜等头部平台相比，核心业务闭环（预售自提、一键配货、核销员核销）的流程模型高度一致。差异点在于：头部平台需要处理千万级订单和百万级自提点，其技术架构必然涉及微服务拆分、分布式事务、消息队列、分库分表、CDN 加速等复杂度；本系统作为毕业设计项目，聚焦单体架构下的核心业务正确性与并发安全，不追求规模。

与一般的课程设计相比，本系统的突出特点是：第一，**数据库规模大**（39 张表 + 21 个迁移脚本），反映了真实电商系统的数据结构复杂度；第二，**状态机覆盖广**（5 套状态机驱动核心业务对象的生命周期），每个状态转移都有明确守卫条件；第三，**库存并发安全设计实**（三重守卫机制 + 真实 lockStock SQL + 幂等兜底 deductStockNet），不是纸面设计；第四，**团购预售模式完整落地**，不是简单模仿凑团模式；第五，**8 份 MD 文档**同步维护，覆盖约束、规划、风险、配置、数据库、前端模块等，确保开发过程有据可查。
